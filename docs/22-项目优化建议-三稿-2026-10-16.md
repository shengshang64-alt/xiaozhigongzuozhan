## 0. 一句话结论

**门禁现在是红的，而红的那一条，恰好守着用户最痛的那个 bug。**

`npx vitest run` 实测 **1 failed | 3236 passed | 2 skipped**——失败的是 `proseFallbackWiring.test.ts`，也就是"标书大纲一直生成不了"那次修复的接线守卫。它红的原因不是业务回归，而是 **CRLF 行尾**让正则匹配不到源码；**但代价是一样的：这条链现在没有守卫**。

同时，真实库读数给出了本项目**第一个业务漏斗数字**：25 个项目里，**废标检查只跑过 2 个（8%）**，**9 个（37.5%）从未产出大纲**。

> **⚠️ 本条此处原写有"整文解析只用 14,000 字符、最大招标 762,209 字覆盖率 1.8%"——该判断已被 R54 证伪**（`MAX_TENDER_CHARS` 位于一条**无生产调用者**的死路径；活链路阈值是 60,000 / 45,000×20 段 ≈ 90 万字全量覆盖）。详见 §2 P0-2 的更正，那里保留了误判全过程。

给决策的一句话：**先修门禁的红、再修真缺陷、然后才谈拆 God Hook。**
理由：God Hook 之所以从 R38 被点名到今天还没拆，不是没人想拆，而是**它的"回归网"是 12 个把源码当字符串 grep 的哨兵测试**——那些哨兵反过来锁死了重构（见 §3.1）。**在行为测试网建起来之前拆它，只会得到一堆爆红的哨兵和一个仍然没有回归网的半成品。**

**另外两条"便宜且立刻见效"的**（详见对应章节，都是本轮新发现、都已复核）：

- **一处零风险重复**：`bidTypes.ts:5665` 的 `repairJsonCandidate` 与 `lib/jsonTolerant.ts:67` 的 `repairJsonStructure` **逐字节同源**——库本来就是从标书抽出去的，但标书留了副本没删。**删 29 行、零行为差异**（§3.2(2)）。
- **一处结构性隐患**：`bidTypes.ts` 的 7101–8295 行 barrel 再导出，让 **25 个 prompt 模块与它形成运行时循环依赖**，那个 282 KB chunk 里因此塞进了 **28 个 prompt 模块**的代码，**250+ 个 importer 全被拖进整层 prompt**。**先断这个环，是单点收益最大的改动**（§3.2(1)）。
- **lint 有一个 5 行换 6 条 error 的快赢**：把 ref 声明移到首次使用之前（§4 Step 0）。

**同时纠正我自己最初的两个误判**（写在这里以免误导决策）：① `preserve-manual-memoization` 的 25 条**不是**陈旧闭包风险，实测全是无害超额声明（§4）；② 备份文件**不是**"纯垃圾"——里面有一个**被 386 文件批量提交 `d54a848` 带走的、活代码已经没有的功能实现**（§3.3）。

## 2. P0（三条，按"不做会怎样"排序）

### P0-1　门禁已红：大纲守卫被 CRLF 打成假红（**当天可修**）

**证据链（逐条可复算）**

1. `src/pages/BidWorkspace/proseFallbackWiring.test.ts:42` 断言 `expect(outlineCalls).toBe(7)`，实测**收到 2**。
2. 该计数来自 `test.ts:40`：`/\n\s*"bid-outline",\n/g` 的匹配数 + `role: "outline"` 的匹配数。
3. 用同一份源码、换成 `/\r?\n/` 口径在 PowerShell 里复算：**scope 独占一行 = 5，role: outline = 2，合计 7**；`expectJson: true` 实测 **7 处** —— 即**业务口径完全没回归**（测试自己的注释就是"缺一个就少一处自愈"）。
4. 根因是行尾：`useBidWorkspace.ts` 实测 **CRLF=9700 / LF-only=0**；三个守卫测试文件实测 **LF-only**（`proseFallbackWiring.test.ts` 45、`promptVisibilityWiring.test.ts` 103、`bidVisibility.test.ts` 291）。
5. 环境：**`.gitattributes` 为空**（存在但 0 内容）+ `git config core.autocrlf = true`。
6. 全仓 `src` 行尾实测：**351 个 CRLF 文件 / 394 个 LF-only 文件 / 21 个文件内部混合**。

**为什么这条要排在第一位**

- 它让**用户的真实故障**（"标书大纲一直生成不了"）**失去守卫**。假红和真红在 CI/人眼里是一个颜色；连续几次之后，所有人都会开始忽略红色 —— 这正是 `docs/19/20` 花整轮修的"门禁诚实性"（R41a）在另一个方向上的复发。
- 影响面不止一个文件：全仓**34 个"读源码扫描型"测试**（`readFileSync` + 正则）共用同一行尾假设。今天只有 1 个红，属于**运气**，不是设计。

**修复（两条都做，成本极低）**

- (a) 新增 `.gitattributes`：`* text=auto eol=lf`（+ 关键二进制显式 `binary`），然后 `git add --renormalize .` 归一化一次。
- (b) 守卫测试的行锚正则一律改 `/\r?\n/`，或改用 `split(/\r?\n/)` 后按行遍历——**不要依赖文件行尾**。

**出口标准（可机检）**

- `npx vitest run` → **0 failed**（3239 全绿）；
- `git ls-files --eol` 中 `.ts/.tsx` 不再出现 `mixed`；
- 34 个扫描型测试逐个确认不依赖 `\n` 字面量。

> **⚠️ 本条初稿的根因判断是错的，已于 R54 用「谁真的调用它」证伪并就地更正。** 保留原文与更正过程，因为**误判本身比结论更有参考价值**——它正是本稿反复强调的那条纪律（对文本做推断 ≠ 对行为做验证）的现场样本。

**初稿当时写的是**（错误）：

- ~~`MAX_TENDER_CHARS = 14000` 是整文解析的上限~~；
- ~~`tenderParse.ts:32` 的 `clipText(tenderText, MAX_TENDER_CHARS)` 使 762,209 字的招标只被看到 1.8%~~；
- ~~"parse_report ÷ tender_text"= 2.90%~87.81% 说明解析质量随文件变大而崩塌~~。

**R54 核验后的真实情况**

1. **`tenderParse.ts` 在生产链路里没有调用者。** 全仓 `buildTenderParseMessages` 的引用只有：它自己、`bidTypes.ts:7092` 的 barrel 再导出、2 个测试、2 个工具脚本（`split-prompts.mjs` / `r50_bidtypes.mjs`）。**前端运行时不走这条路。** 已在 `tenderParse.ts` 顶部加显著注释钉死这一点，防止下一个人重犯。
2. **活链路的阈值是**（`prompts/wholeParse.ts:24-38`）：`WHOLE_FILE_LIMIT = 60000`（≤6 万字整文直读）→ 超限走 `PARSE_SEGMENT_CHARS = 45000` **切段 + 跨段 AI 合并**，段数上限 `PARSE_MAX_SEGMENTS = 20`（关键项 `PARSE_MAX_SEGMENTS_CRITICAL = 24`），即覆盖 **90 万 / 108 万字**。
   - 最大的真实标书 762,209 字 → **17 段 ≤ 20 → 全量覆盖**，不是 1.8%。所有已知真实项目都落在全量覆盖区间内。
3. **而且这个问题在 R288+（2026-10-13，"我审计的两天前"）已经被修过**，证据就写在代码注释里：原值 6 段使 38 万字标书的 17/22 个通用项**全部回落检索**（实测产出约 3 万字、覆盖率 8%，且「响应文件要求」「投标文件目录要求」直接为空 → 撞大纲硬依赖 → 大标书走不完链路），提到 20 才解决。**我审计时未读这段注释就下了结论。**
4. **`parse_report ÷ tender_text` 不是截断指标。** parse_report 是**抽取后的要点摘要**，本来就该远小于原文——比值低是正常语义，不是丢字证据。我把它当截断信号是**误读**。

**仍然成立、且在 R54 被修掉/确认的部分**

| 项 | 状态 |
|---|---|
| `clipText` 原为**纯保头**（`slice(0, max)` 后整段丢弃） | ✅ **R52 已修为保头+保尾** —— 它真的影响的活链路是 `sectionParse` 的两个分支与 `eval` 的评标摘要 |

**修正后的结论**

- **解析链路（招标 → parse_report）不是瓶颈，不要再去"接检索"或"加预算"**——它已经能全量覆盖 90 万字。
- 真正需要攻的是 **`bidVisibility` 的 20,000 字证据预算**（B25）：那是"用 13 条证据判 133 条条款响应性"的业务问题，候选解法（章内二次摘要 / 按模型上下文动态定预算 / 两阶段取证 / 章节摘要树）已由 R51 登记，属**设计变更**而非快速修复。
- 本条的**净收获**是两条：① 修掉一个真实的静默失真缺陷；② 给一条死路径立了墓碑。**没有**去改 `MAX_TENDER_CHARS`（那会是在修一条没人走的路）。

**出口标准（已达成）**：`clipText` 保尾有测试（`clipText.test.ts` 7 例，删实现 4/7 变红）；`mode` 契约一致性有测试（`sectionParse.test.ts` 新增 4 例，删实现核心例变红）；四门全绿。

### 3.1　God Hook 的真正问题不是"长"，而是**它没有行为测试网**

**实测规模**（比二稿记录的又长了）

| 指标 | 实测值 |
|---|---|
| `src/pages/BidWorkspace/useBidWorkspace.ts` | **9,700 行 / 494 KB**（505,789 B） |
| `useState` | **118** |
| `useCallback` | **238** |
| `useEffect` | 14 |
| `useMemo` | 39 |
| `useRef` | 28 |
| **返回对象 key** | **371** |

**致命事实（本轮最重要的一条）**

- 271 个测试文件里，**`renderHook` = 0**。
- 只有 **12 个**文件 import `@testing-library/react`（`BidTeamList` / `DeptChecklistPanel` / `DeviationPanel` / `GateChecklist` / `TechParamResponsePanel` / `ModelSelect` / Discount 三张 / `QuoteEditorMoney` / `TabbedOutlet` / `BidCheckConfigDialog`）——**没有一个测这个 hook**。
- 这 9,700 行、承载**全部产品主流程**的模块，其"回归网"实际是 **12 个把源码当字符串 grep 的哨兵测试**：`clauseOutlineAlignment` / `factSourceWiring` / `priceScoreWiring` / `promptVisibilityWiring` / `proseFallbackWiring` / `proseLintWiring`（已列出的 6 个文件、共 12 处 `readFileSync` 断言）。
- 它们**钉死的是字面量**，例如：`const runVoidCheck = useCallback`、`confirmOutline` 的**精确依赖数组** `}, [outlineDraft, updateProject, writeStageSnapshot]`、`const [quoteRefs, setQuoteRefs] = useState<QuoteTotalRef[]>([])`、`applyOutlineWithChapters(next)` 出现次数 ≥4、`"bid-outline"` 计数 = 7。

**由此得出两条推论（这解释了"为什么一直没拆"）**

1. **运行时行为回归无网可兜** —— 这 9,700 行里任何一处 async 竞态、防抖错序、ref/state 镜像不同步，测试都不会红（能红的只有 tsc 与那 12 处文本模式）。
2. **这些哨兵反过来锁死重构** —— 一旦把 `runVoidCheck` 或 `confirmOutline` 挪出根文件，哨兵立刻爆红；而**哨兵红了并不代表业务错了**（正如 P0-1 的假红所证明的）。于是"拆"这件事的**每一步都要先改守卫**，成本高、回报不可见，自然就一直不拆。

**其中"跨文件计数"是最脆的一条**（也正是 P0-1 那个红灯所在）：


> ~~"编译器没跑，手写依赖数组就是唯一的正确性来源——所以这 25 条 `preserve-manual-memoization` 应当按**潜在陈旧闭包**对待。"~~

**这条是错的。** 25 条实测**全部是"无害的超额声明"（benign over-specification），真陈旧闭包 = 0**。三条独立证据：

1. **逐条看 eslint 的 payload**：25 条里 **23 条**的"推断依赖 − 手写依赖"差集**只有一个 `useState` setter**（例：`useIntelCenter.ts:1194` 推断 `setItemList`、手写 `[]`；`useCustomerManagement.ts:1740` 推断 `setAiSuggestions`、手写 `[userId]`）。React 官方保证 setter 身份稳定，**少写它不可能陈旧**，这些手写数组反而比推断更保守。
2. **与 `exhaustive-deps` 零交集（我独立复算过）**：25 条位置去重后 = **18 处**，12 条 `exhaustive-deps` 警告位置，**交集 = 0**。`exhaustive-deps` 只认真实的响应式值——若这 18 处真有漏掉的 state/prop，它必然同时报；它一处都没报。
3. 另 2 条（`useIntelCenter.ts:507`、`useSolutionStudio.ts:765`）是另一种消息：**"源码里有 memo、但编译输出里被丢掉了"**。它们**确是真缺陷，但属于"声明顺序"（TDZ）类，不是陈旧闭包**：
   - `useIntelCenter.ts:474` 调用 `loadSources`，而该 `const` 在 **`:507`** 才声明 → 编译器无法推理前向引用而放弃 memo（同处另有 `immutability` 报"声明前访问"）。运行时今天安全（只在 effect/interval 里调），**但将来一旦开编译器并上调 `panicThreshold`，`loadSources` 失去 memo → `[loadSources]` 每次渲染都变 → `setSourcesLoading(true)` → 无限渲染。**
   - `useSolutionStudio.ts:432-433` 写 `autoSaveResetRef` / `saveTimerRef`，而它们在 **`:719-720`** 才声明。

**`set-state-in-effect` 的 73 条同理：0 个自触发死循环。** 逐个检查 C 组 effect 的依赖数组，**没有任何一个把自己设置的 state 写进依赖**。真实代价只有两条：① 每次依赖变化多一次提交渲染；② **dev 下双请求**——`main.tsx:20` 开了 `<StrictMode>`，挂载期 effect 双跑，约 22 个 A 组 loader 会打两次 HTTP（多数有 `xxxSeqRef` 丢弃陈旧响应，但请求仍到服务端）。**生产环境零影响。**

> **结论：不要为了消这 119 条去装 React Compiler。** 三条硬理由：
> ① **装了也消不掉**——eslint 插件自带编译器校验 pass，规则触发与是否开 codegen 无关；默认 `panicThreshold: 'none'` 下这些函数只是被**跳过**，既不优化、也照样报。
> ② **上调 `panicThreshold` 会让 119 条直接变成构建失败。**
> ③ 在一个**没有行为测试网**（§3.1）的 9,700 行 hook 上，引入会重写全站 memo 语义的编译器，风险与收益完全不成比例。

**处置顺序（按"每改动一行消掉几条错误"排序）**

| 步骤 | 动作 | 消掉 | 风险 |
|---|---|---|---|
| **Step 0** | **把 ref 声明移到首次使用之前**（`useSolutionStudio.ts:719-720` → 提到 431 之前；`useIntelCenter.ts:507-517` → 提到 464 之前并补进 deps） | **6**（4 immutability + 2 preserve） | **极低，纯重排序——全表性价比最高** |
