## 一、问题：本轮起点是「校准误报率」，但校准结果把这条建议本身否掉了

上一轮遗留建议要我先量**误报率**。照做，第一步就把结论拿出来了（见 §三）：

| 语料 | 字数 | 命中 |
|---|---|---|
| 安中医真实投标正文（脱敏子集 + `.probe` 全量） | **185,913** | **0** |
| 同一份文件里的招标原文（表格 / OCR 抽取文本） | 32,957 | 6（**全部误报**，且全在「过短行」族） |

即：**误报率实测为 0，12 条 `BROKEN_PAIRS` 全族零命中**。「校准误报率」这条建议没有错，但**已经没有油水**。

于是把注意力转向同一份源码的另一半 —— **召回**。逐个把模块头部注释里写明的 BUG-101 真实样本当断言跑，抓到本轮的真缺陷：

> 模块头部第 4 条样本是 `"日均门诊患 15000 以上"  缺"者"字`，
> 而旧模式是 `/门诊患\s+(人次|以上|数量)/` —— 它要求**缺字处紧跟量词**，
> 于是这条**写在注释里的真实样本，代码从来没有命中过**。

同类的第二、三处问题（都属"用户看得见但用不上"）：

- **丢字命中无法定位**：R-301 的丢字检测只给一条不可点击的 tooltip（红字「丢字?」+ 一句总结）；而 R-302 的文风 lint 已经做到「命中入库 → 徽标 → 一键跳到命中字符」。**同一个成稿自检里两个检测器体验不一致**，且丢字 `hits` 里本来就有 `offset`，只是被丢掉了 —— 用户面对 3 万字正文无从下手。
- **标记不会失效**：R-301/R-302 的字段注释都写着「人工修订后随 `updateChapter` 清空」，**实现里只在重新生成时清空**。人工改完正文，徽标永远红着；更坏的是 `offset` 还锚在旧正文上 —— **跳到错位置比不跳更坏**。

### 1. 召回：只补有依据的位置，不放宽会误伤正确正文的位置

```diff
- { pattern: /门诊患\s+(人次|以上|数量)/g, expect: "门诊患者$1", reason: "疑似缺'者'字" }
+ { pattern: /门诊患(?!者)\s*(?:\d[\d,，.]*|人次|以上|数量)/g,
+   expect: "门诊患者（+数字/量词）", reason: "疑似缺'者'字" }
```

- 覆盖三种真实形态：`门诊患 15000`、`门诊患15000`（无空白）、`门诊患 人次`；
- **反向验证（删实现即变红）**：整条退回旧模式 `/门诊患\s+(人次|以上|数量)/` 后，
  `bidTextSanity.test.ts` 的「注释即契约」用例变红，报文原文：
  `"日均门诊患 15000 以上" → 期望含「缺'者'字」，实得 []` —— 这条修复确实被测试守住了。
- **关于 `(?!者)` 的诚实记录**：去掉这个断言后，相关 17 例**全绿** —— 因为四个候选中没有一个以「者」开头，
  所以它今天是**冗余的意图声明**（真正拦住「门诊患者」的是候选本身，不是这个 lookahead）。
  保留理由：后人若往候选集里加「者X」类量词，它是第一道防线；**删除它不会有任何行为变化**。
  这条已写进源码注释，避免下一个人把它当成"防误报的关键"而误判风险。
- **真实语料自证（零误报的实证，不是推断）**：185,913 字里共 13 处「门诊患」，**全部**是正确写法「门诊患者」
  （`门诊患者人次达15000` / `门诊患者15000以上` / `门诊患者 15000 人`），新模式一个都没误报 → 0 误报。

**明确不放宽的四条**（写进了源码注释，防后人"顺手"改坏）：

| 模式 | 放宽成 `\s*` 会命中 |
|---|---|
| `整体采\s+用` | 「平台整体**采用**微服务架构」✅ 正确正文 |
| `系统提\s+供` | 「系统**提供**统一认证」✅ 正确正文 |
| `能够实\s+现` | 「系统能够**实现**数据汇聚」✅ 正确正文 |
| `系统支\s+持` | 「系统**支持**多院区管理」✅ 正确正文 |

> 放宽这四条 = 把绝对正确的句子判成丢字，属灾难性误报。它们的"无损位置"已登记入 backlog `B26`，**不在本轮猜测性扩召回**。

### 2. 定位：`summary` 的「最严重」名副其实，`hits[0]` 兼作跳转锚点

模块内新增类别优先级并稳定排序：

```ts
const KIND_PRIORITY: Record<LostCharHit["kind"], number> =
  { missing_modifier: 0, broken_pair: 0, single_char_end: 1, short_line: 2 }
```

排序后 `ranked[0]` 既生成 `summary`（"最严重"），又作为徽标跳转的锚点 —— 两者**同源**，不会出现"总结说的和跳的不一致"。

### 3. 失效：人工改正文即作废两类本地标记

`flushEditingContent`（`useBidWorkspace.ts:5715+`）在**正文真的变化**时一并清空四个字段（`sanityWarning` / `sanityFirstHit` / `proseLintWarning` / `proseLintFirstHit`），**且仅在确实存在标记时才写补丁**（避免每次编辑都往 `bid_chapters` json 里塞 4 个 `undefined`）。

> 未动 `underlength`：它不是 offset 型标记（是长度口径），失效条件与位置锚点无关。

### 4. 顺手修两处源码级失真

- `short_line` 的用户文案里**直接印着未替换的占位符**「第 N 行」→ 现在显示真实行号（新增 `lineNumberAt()`）；
- 模块头部用法注释仍写 `updateChapter(nodeId, { genError: r.summary })` —— 而 `genError` 是 **R280「生成失败原因」**字段（`composeGates.ts` A2 用它判「failed 未写原因」违规，`genFailureSummary` / `solDeliveryCheck` 也按它做失败归因聚合）。照注释抄会**污染失败归因**，已改正并加守卫断言「sanity 写入块不得出现 `genError`」。

## 九、回滚方式（**注意：本轮涉及的文件不能用 `git checkout` 回滚**）

先看 git 事实（本轮收尾实测）：

```text
 M src/components/bid-workspace/ComposeStep.tsx        (+117 / -7  ← 含前几轮在途，非本轮独有)
 M src/pages/BidWorkspace/useBidWorkspace.ts           (+93  / -8  ← 同上)
 M src/pages/SolutionStudio/solutionTypes.ts           (+1573/ -783 ← 同上)
?? src/pages/BidWorkspace/bidTextSanity.ts             (未跟踪，R-301 起就没入库)
?? src/pages/BidWorkspace/bidTextSanity.test.ts        (未跟踪)
```

**所以两条禁令**：

1. `bidTextSanity.ts` / `bidTextSanity.test.ts` 是**未跟踪文件** —— `git checkout --` 会直接报
   "did not match any file(s) known to git"，**无法回滚**；删掉它们则等于丢掉 R-301 起的全部丢字检测能力（绝不可接受）。
2. 另外 3 个 tracked 文件里**同时躺着 R-52 / R-54 / R-301 / R-302 的未提交改动** ——
   `git checkout --` 会把**别人的在途工作一起抹掉**。这也是本仓长期"只改不提交"的代价（B22 记过一次）。
