## 二、问题 → 根因 → 修法 → 验证

### 问题 1（S0）：小计在「恰好半分」处系统性少 1 分

- **现象**：`itemSubtotal` 对 `15 × 599,729.21 × 90%` 给出 **8,096,344.33**，而手算与 Excel 都给 **8,096,344.34**。
- **根因**：`src/pages/PptQuote/pptQuoteTypes.ts` 旧写法 `Math.round(raw * 100) / 100`。真值 8,096,344.335 元在二进制浮点里存成 `…3349999999`，×100 后是 `…33.4999…`，`Math.round` 于是向下——**恰好半分**的那一侧永远被吃掉。客户侧 Excel 的 `ROUND`、计算器、人工复核都给另一侧。
  同一份报价单出现两套数字，正是 R-0281 判定过的「被质疑/废标级」风险，只是当年只补了公式的 ROUND，没补 JS 这一侧。
- **规模（不是个例）**：`node docs/evolution/_r34_amount_drift_audit.mjs`
  → `{ badItem: 16600, badGroup: 0, badTotal: 0, trials: 200000 }`
  即 **20 万组真实量级随机行项里 8.3% 少 1 分**；组小计/总计层无额外漂移（错在行项层，往上原样累加）。
  另外三例可手算核对：`5 × 30,553.70 × 95% = 145,130.075`（旧 .07 / 新 .08）、`3 × 87,456.70 × 95% = 249,251.595`（旧 .59 / 新 .60）。
- **修法**：金额链路改为**整数分**单一口径，不再让小数乘积经过二进制浮点。
  - `src/lib/money.ts:54-83` 新增 `productCents(factors)` / `centsToYuan(cents)`：每个因子按最多 6 位小数取「微元」整数，BigInt 精确相乘，分位做远离零舍入（与 Excel ROUND 同侧）。
  - `src/pages/PptQuote/pptQuoteTypes.ts:207-249`：`itemSubtotalCents → groupSubtotalCents → quoteTotalCents` 全程整数分累加；`itemSubtotal / groupSubtotal / quoteTotal` 变成它们的分→元包装，**函数签名与语义不变**，所有既有调用点零改动。
  - 顺手消灭两处并行写法：`src/pages/PptQuote/usePptQuote.ts:1485,1810`（回写商机 expected_amount 的内联 `Math.round(… * 100) / 100`）改调 `quoteTotal()`；`usePptQuote.ts:1793-1799` 总计 memo 同理；`src/pages/PptQuote/PptQuotePage.tsx:32-33` 列表统计卡走 `quoteTotalCents` 累加。
  - 折扣归一（R285）、`normalizeDiscount`、缺量按 0 等口径**一律未动**——只换舍入，不换产品语义。
- **验证**：
  - 修复后同一批 20 万用例：`npx vite-node docs/evolution/_r34_new_chain_check.ts`
    → `{ badItem: 0, badGroup: 0, badTotal: 0, trials: 200000, first: [] }`
  - 边界回归锁：`src/pages/PptQuote/quoteTotalCapital.test.ts`（本轮新增，17 例全绿），含
    「旧写法确实偏小」对照例（`.33/.07` vs `.34/.08`）、4,000 例随机「结果恒为整分」例、
    300 行大表「总计 === 逐行分位求和」例、脏值（折扣 0/负/NaN、数量 0）口径不变例。
  - Excel 侧不变：`quoteItemSubtotalFormula` 仍是 `ROUND(E*G*折扣/100,2)`，现在 JS 与该公式重算逐分一致
    （既有 `quoteExports.test.ts` / `quoteExcelNumFmt.test.ts` 未改，仍全绿）。

### 问题 2（S1）：交付物里没有「合计（大写）」

- **现象**：投标报价表 / 报价单的硬性组成项「合计金额（大写）」在 Word、Excel、界面三处**全部缺失**
  （`grep -rln 大写 src/pages/PptQuote` 命中 0 处）。已有的 `cnyToUpper`（R-0184 建，`src/lib/currencyCn.ts`）只被标书正文体检用到，报价域从未接上。
- **根因**：报价域只输出小写金额；大写要么由人手填，要么干脆没有。手填的失效模式很具体：改了数量后小写重算、大写停在旧值——大小写不一致是评标现场一眼就能抓的问题。
- **修法**：大写**只能由总额派生**，不给手填入口。
  - `src/pages/PptQuote/pptQuoteTypes.ts:242-248` 新增 `quoteTotalUpper(groups)` = `cnyToUpper(quoteTotalCents(groups)/100, {prefixRmb:true})`。
  - Word：`src/pages/PptQuote/quoteExports.ts:341,354-366` 表格下方新增段落「合计金额（大写）：人民币…　（小写：¥…）」。
  - Excel：`quoteExports.ts:156-159` 总计行下方新增一行「总计（大写）」+ 大写串（D/E 列，行锚点接在总计行之后，不影响既有金额单元格锚点）。
  - 界面：`src/components/ppt-quote/QuoteEditor.tsx:725` 总计卡在小写下方一行显示大写。
- **验证**：拆真实产物文件，不看源码看内容。
  - Word：`exportQuoteDocx` 产出的 Blob 解 zip 取 `word/document.xml`，实测含
    `合计金额（大写）：` / `人民币叁万贰仟玖佰壹拾捌元伍角壹分` / `小写：¥32,918.51`
    （测试名：「Word：真实 .docx 产物拆包后 document.xml 里确有该行大写」）。
  - Excel：截获传给 `XLSX.writeFile` 的 workbook，实测 `H8=32918.51`、`D9="总计（大写）"`、
    `E9="人民币叁万贰仟玖佰壹拾捌元伍角壹分"`。
  - 互逆性：`parseCnyUpper(quoteTotalUpper(...)) === quoteTotal(...)`（测试断言）；改单价后大写跟着变（10 万 → 9 折 = 玖万元整）。

## 三、非程序员怎么自己复核（3 步，不用读代码）

1. 打开 http://localhost:5173 → 进入「PPT 报价」→ 任意报价 → 编辑视图，看右下角「报价总计」：
   现在小写 ¥ 下面多了一行中文大写（例：人民币叁万贰仟玖佰壹拾捌元伍角壹分）。
2. 同一份报价点「导出 Word」，打开生成的 .docx：表格下面第一行就是「合计金额（大写）：…　（小写：¥…）」；
   点「导出 Excel」：总计行下面多一行「总计（大写）」。
3. 验分位修复（最关键的一条，拿手机计算器按三下）：在报价里加一行 数量 **15**、单价 **599729.21**、折扣 **90**。
   - 第一步 15 × 599,729.21 = **8,995,938.15**
   - 第二步 × 90% = **8,096,344.335**
   - 第三步 四舍五入到分 = **8,096,344.34** ← 界面/Word/Excel 现在都显示这个；本轮之前显示 8,096,344.33（少 1 分）
   换一组更好按的：数量 **5**、单价 **30553.70**、折扣 **95** → 5×30,553.70×0.95 = **145,130.075** → 应为 **145,130.08**（本轮前为 145,130.07）。
4. 命令行复核（可选）：
   - `node docs/evolution/_r34_amount_drift_audit.mjs` → 旧写法 8.3% 行项少 1 分（缺陷复现）
   - `npx vite-node docs/evolution/_r34_new_chain_check.ts` → 新写法 0 处偏差（修复证据）
