## 2 · 问题 → 根因 → 修法 → 验证

### 2.1 问题：同一笔钱，五条算路各算各的，且都走裸浮点

建设清单的金额在代码里有**五条互不相干的算路**，全部是 `qty * unit_price` 直接浮点：

| # | 位置 | 用途 |
|---|---|---|
| 1 | `checklistTypes.ts:223` `calcTotal` | 底部「合计」 |
| 2 | `checklistSummary.ts:24` `subtotalOfLines` | 一组行的小计 |
| 3 | `checklistSummary.ts:39` 分类小计 | 详情面板分类小计行 |
| 4 | `checklistExports.ts:203/208` | Excel 的「小计」列与「分类小计」行 |
| 5 | `ChecklistDetailPanel.tsx:148` | 详情面板表格的「小计」列 |

单价一旦带 3 位以上小数，真值落在半分处会被二进制浮点存成 `…49999…`，按分四舍五入就少 1 分；再叠加「三条算路各自独立累加」，导出的 Excel 会出现**逐行小计加起来 ≠ 合计格**。这与 R034 判定的风险等级相同：**报价单出现两套数字，属被质疑/废标级风险**。

### 2.3 根因

不是「算法错」，是**口径分裂**：项目在 R034 已经为报价域立了单一真源 `src/lib/money.ts`（`productCents` 微元整数精确相乘 + 分位远离零舍入、`centsToYuan`），但建设清单域**从未接进来**，一直用自己的裸浮点。R034 只覆盖了报价域，建设清单域被显式留到了下一轮。

### 2.4 修法（最小改动，复用既有 money.ts，不新增依赖）

`checklistTypes.ts` 新增两个纯函数并把 `calcTotal` 改为它们的组合：

```ts
/** 单行小计（元）：qty × unit_price，精确到分，与报价域同一口径 */
export function lineSubtotalYuan(l: ChecklistLine): number {
  return centsToYuan(productCents([Number(l.qty) || 0, Number(l.unit_price) || 0]))
}

/** 任意一组行的小计（元）：逐行精确到分后以整数分累加，避免二次浮点漂移 */
export function sumLinesYuan(lines: ChecklistLine[]): number {
  return centsToYuan(
    (lines ?? []).reduce(
      (cents, l) => cents + productCents([Number(l.qty) || 0, Number(l.unit_price) || 0]), 0),
  )
}

/** 勾选行合计（元）：剔除未勾选行后按 sumLinesYuan 口径累加 */
export function calcTotal(lines: ChecklistLine[]): number {
  return sumLinesYuan((lines ?? []).filter((l) => l.checked !== false))
}
```

其余四条算路全部改为调用这两个真源：`checklistSummary.subtotalOfLines` → `sumLinesYuan`；`summarizeChecklistCategories` 改为**先分组、再按整数分一次算清**（保证「各分类小计之和 === 合计」严格成立）；`checklistExports` 的逐行小计 → `lineSubtotalYuan`、分类小计 → `sumLinesYuan`；`ChecklistDetailPanel` 行小计 → `lineSubtotalYuan`。

**语义未变**：无折扣概念、未勾选行仍剔除、`NaN`/`undefined` 仍按 0 计、`checked !== false` 的判定不变。改的只是「怎么算到分」。

新增单测 `src/pages/SolutionStudio/checklistMoney.test.ts`（6 例）：钉住定点案例的逐行值与合计、导出三条算路一致、未勾选/NaN 边界、以及**「整数与 2 位小数单价的结果与旧实现逐分一致」**（证明对存量数据零影响）。
