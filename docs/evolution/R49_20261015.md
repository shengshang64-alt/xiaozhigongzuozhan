## 一、问题：报价单的「钱」有三处显示，此前没有任何测试钉住它们互相自洽

报价编辑器（`src/components/ppt-quote/QuoteEditor.tsx`）在同一屏上显示三个层级的金额：

| 位置 | 来源 |
|---|---|
| 行「小计(元)」 | `QuoteEditor.tsx:674` `const sub = itemSubtotal(item)` |
| 分组标题右侧「XX 小计」 | `groupSubtotal(group)` |
| 页面底部「报价总计 ¥」 | `totals.total`（线上由 `usePptQuote` 的 `quoteTotal(groups)` 算出） |

金额单一真源是 `src/lib/money.ts` 的 `productCents`（BigInt 微元整数精确相乘 + 分位远离零舍入），
R034 已用它立下口径。但**R42 建立的 UI 回归网只覆盖了 DiscountCell / NumCell / DiscountIntentDialog / GateChecklist 四张**，
「改一个输入框 → 三处金额是否同步且逐分正确」这条最常被用户触碰的往返链路**没有网**。

R42 的账本原话就是：「剩余可补：报价行编辑→小计/总额往返、导出前门禁拦截」。本轮做前半张。

## 二、探针行：选 R034 的经典反例，而不是随便一行

`15 × 599,729.21 × 90%`

- 精确值（逐行按分、分位远离零舍入）：**8,096,344.34**
- 裸浮点 `Math.round(qty * price * discount / 100 * 100) / 100`：**8,096,344.33** —— 差 **1 分**

即：只要有人把 `itemSubtotal` 换回裸浮点写法，这条用例**必然变红**。这让测试不是「存在性断言」，而是**能拦住具体回归的哨兵**。

### 3.1 六条用例

1. **首屏逐分对账**：探针行小计必须是 `8,096,344.34`，并显式断言页面上**不存在** `8,096,344.33`；
2. **三处同源**：组小计 = 组内各行小计之和；总计 = 所有组小计之和；
3. **改数量** 15 → 10：行小计与总计同步；
4. **改折扣** 90 → 50（`change` + `blur`，走 `DiscountCell` 的落值路径）：三处同步；
5. **改单价** 5,000 → 8,000：三处同步；
6. **连续编辑**：三次改完不残留任何旧值。

harness 是**状态化**的：`totals` 由 `groupSubtotal` / `quoteTotal` 从最新 state 重算 ——
等价线上 `usePptQuote` 的 `mutateQuote`，不是把数字喂死。驱动的是**真实的三个输入框**
（`getAllByLabelText("数量" / "单价（元）" / "折扣（百分比）")`），不是调用内部函数。

## 八、长教训 / 纪律（写死以免再犯）

- **账本陈旧是本项目的高发形态**：本轮一次核对出 3 处「早已完成却仍挂在待办上」的项。
  **每轮开工第一件事应当是「抽查待办池前几条的真实落地状态」，而不是直接相信优先级排序。**
- **同一工作区两个执行者并发 = 账本会被覆盖**：写账本的脚本必须**先重读、再断言期望的 round 值**
  （本轮即用 `assert(round === 48)` 兜住），否则并发写会静默互相覆盖。同一时刻只应有一个执行者写仓库。
- **全量测试的绝对数可能混着别人的在途文件**：报告必须点名区分「本轮贡献」与「在途增量」，
  并**不提交**（`git add -A` 会把别人没写完的改动一起提交）。
- **「开工时 git status 干净」不代表整轮干净**：本轮验证期间另一进程开始写仓库，直接造成 1 次全量测试假失败
  （`Snapshots 1 failed`）。时间戳比对：并发批次在 **01:14** 改写 `promptsSnapshot.test.ts.snap`，
  而该次全量跑在 **01:13:51** —— 是并发在途改动，与本轮无关；随后连跑 3 次全绿、两个快照测试单独连跑 3 次全绿（45 passed）。
- **UI 回归网的正确做法是「驱动真实组件 + 真实输入框 + 断言真实渲染文本」**，
  而不是调内部函数 —— 后者会在「组件不再渲染这个值」时依然全绿（假绿）。
