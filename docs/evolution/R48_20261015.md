## 一、问题：两处源码在同一件事上自相矛盾（改前取证）

| 位置 | 旧口径 | 危害 |
|---|---|---|
| `prompts/factSettings.ts` 旧第 4 条 | 要求把「招标要求工期不超过 90 天」**改写成**「本项目工期：90 天（满足招标不超过 90 天要求）」 | 把**未拍板的取值写成已定承诺句**；商务根本没报价、没定工期，正文却已经「承诺」了 |

要点：**「招标要求」不是「我方承诺」**。前者是采购人给定的上限/下限（硬约束），后者才是需要商务拍板的取值。
旧第 4 条把两者合并，等于让模型替商务拍板。

## 二、判定口径（唯一真源，提示词与代码同源）

### 2.1 来源优先级（冲突时高者压过低者，禁止越级）

1. 本项目招标文件原文与解析报告明确的硬性要求
2. 本项目材料中已明确写出的确认事实（项目名称 / 编号 / 采购人 / 地点等）
3. 需商务拍板才能承诺的取值（工期、报价、人员数量、质保与响应时限等）
4. 历史标书范本 —— **只提供写法与表述范式，不是本项目事实**

### 2.2 需商务拍板的主题（`FACT_COMMITMENT_TOPIC_RE`）

工期 / 交货期 / 交付期 / 项目周期 / 服务期 / 运维期 / 质保期·年限·时长 /
响应时间·时限 / 到场时间 / 故障响应 / 解决时限 / 驻场（人数）/ 人员配置 / 项目团队 /
实施人员 / 投标报价 / 报价 / 投标总价 / 总价 / 付款方式 / 付款比例。

### 2.3 三态判定（`normalizeFactSourceLine` / `factSourceTierOf`）

| 输入形态 | 判定 | 处置 |
|---|---|---|
| 招标原文比较口径（`不超过 / 不得超过 / 不少于 / 不低于 / 不低于 / 至少 / ≤ / ≥ / < / >` 开头） | `constraint` | **原样保留、不标记** —— 正文按「不超过 90 天」响应是安全表述 |
| 需拍板主题 + 已定承诺形态（`工期：90 天`） | `pending` | **补 `【需人工确认】`**（本次唯一的自动改写） |
| 已带 `【需人工确认】` | `pending` | 原样返回（**幂等**，人工确认过的口径不被重复改写） |
| 其余（项目名 / 采购人 / 地点 / 验收标准 / 项目经理…） | `settled` | 原样返回 |

## 三、为什么**刻意不标记**「预算金额 / 最高限价 / 控制价」

这三个主题看着像「金额」，其实是**招标方给定的约束值**，不是我方承诺：

- `bidTypes.ts:4360 priceCeilingFromFacts` 从全局事实里取报价天花板；
- 既有单测 `bidFormatCheck.test.ts:424-428` 断言 `预算金额：3500万元【需人工确认】` → `null`。

若把「预算金额」也并进需拍板主题，报价天花板会**静默失效**（超限价不自知）。
故 `FACT_COMMITMENT_TOPIC_RE` 不含这三项，并在 `factSources.test.ts` 与
`factSourcePriority.test.ts` 双侧写死反例守卫。

## 四、边界：规范化只作用于「AI 输出 → 编辑态」这一步

- 规范化点在 `runGenerateFactSettings` 里、`setFactDraft` **之前**，只处理模型刚生成的那批行；
- **用户手工编辑的行、已保存的 `global_facts` 一字不改**（系统不得静默改写人工确认过的口径）；
- 零 AI、零 schema、零新 collection、不动已保存数据。

## 八、长教训 / 纪律（写死以免再犯）

- **`split-prompts.mjs` 本轮禁止执行**：该生成器与母文档已存在**既存漂移**，
  跑它会顺带冲掉 `01-标书工作台.md` §2.27 与 `08-站内助手.md` 的手补修订说明（本轮已实测复现并还原）。
  派生手册一律**手工同步**；要修生成器需单开一轮。
- **「需人工确认」的标记面必须与下游消费方对齐**：`priceCeilingFromFacts` 依赖
  `预算金额` 行**不被标记**，所以「什么算我方承诺」不能凭语义直觉决定，必须**先查消费侧**。
- **`promptsSnapshot.test.ts` 是改字的闸门**：提示词一改 `.snap` 必红 ——
  这是设计意图（B 类流程：`PROMPT_VERSION`+1 + 更新 `.snap` + 核对 diff 只动预期那几条），不是噪声。
- **规范化只能发生在 AI 输出 → 编辑态**：对「已保存数据」做静默改写＝系统篡改人工结论，
  任何后续类似需求都按此边界执行。
- **`git status` 的 ` M` 不一定真改**：`docs/提示词手册/08-站内助手.md` 一直显示 ` M` 但
  `git hash-object` 与 index blob 完全相等（`15b696f`）—— CRLF 统计伪差异，**不要据此回滚文件**（本轮已澄清 R48 交接单里的这条疑点）。
