### 2. 文件大小与失败的实测关系（对审计 §2 P0-3 悬置问题的答复）

| 招标字数 | 项目数 | 无大纲 |
| --- | --- | --- |
| < 10 万 | 4 | **0** |
| ≥ 10 万 | 20 | **9**（45%） |

## 三、做法（四处改动，只动 4 个源文件 + 1 个面板组件）

### 1. 诊断记录：失败与被拦都落一条可诊断记录（新文件 `outlineDiagnostics.ts`）

复用**已有的** `bid_stage_snapshots`（工作记录）通道 → 不需要动 PocketBase 的集合定义、不需要新表、每项目自动保留 60 条、本来就在 UI 里可见：

```ts
writeStageSnapshot("outline", outlineDiagLabel(diag), { [SNAPSHOT_DIAG_KEY]: diag })
```

记录内容（只要规模与原因，**不落任何正文片段**）：

- `kind`：`blocked_no_report` / `blocked_dependency` / `blocked_critical` / `auth` / `empty_reply` / `non_json` / `json_parse` / `empty_outline` / `timeout` / `network` / `model_api` / `unknown`
- `reason` / `detail`（错误名+报文，截断 200 字）
- `at` / `durationMs`（从点击到失败）
- `tenderChars` / `parseChars`（**规模取证**：这一条就是为了让「大文件是否致败」下次可答）
- `criticalMissing` / `criticalMissingTitles` / `coveragePct`（拦截那条的判据输入）
- `staged` / `outlineLevel` / `leafGoal`（走到哪一步失败的）

分类判据全部取自本仓真实报文（不是编的），并且**由测试锁死**：`runGenerateOutline` 里每条 `throw new Error("…")` 都必须能被分类，将来新增失败文案而忘了归类会直接变红。

去重只做「同因 5 秒内」：连点两次同一次失败只留一条；**跨时间的重复失败全部保留**——重复本身就是证据。

### 2. 空名单拦截：判据与清单同源（`parseCoverage.ts` + hook）

抽出唯一判据 `isSectionMissing`，`missingCriticalSections`（判定用）与新增的 `missingCriticalSectionTitles`（取名用）**共用它**，口径不可能再漂移。未知 key 回落成 key 本身，保证「有缺项 ⇒ 名单非空」这条不变量恒成立。

### 3. 非成果行不得被当成「可恢复版本」（`bidTypes.ts` + `restoreSnapshot`）

`bid_stage_snapshots` 同时装着「可恢复成果」和「环节留痕」。真实库 255 条里 **3 条** `stage=chapter`、`payload={}` 的事件行（`文本审计完成`×2、`编排配图补齐`×1）此前只是**侥幸**没出后果（`restoreSnapshot` 里的 `chId` 检查挡了一下，但提示文案说成「该快照对应的章节已不在当前大纲中」——把「本来就没有成果」说成了「章节没了」）。
新增的 `stage="outline"` 诊断行没有这层侥幸：不判可恢复的话，点「恢复此版本」不勾清空下游会**假报「已恢复该历史版本」**，勾了清空下游会**清空正文与各报告却仍不恢复大纲**。
现新增 `isRestorableSnapshot({stage,payload})`（含 `hasSnapshotDiag`）作为统一契约，5 处恢复按钮一律以它为准。

### 4. 面板：诊断行看得见、恢复按钮不给（`StageHistoryPanel.tsx`）

- 诊断行徽标改 `warning` + 「大纲诊断」（不再是普通阶段徽标）；
- 行内与「查看」弹窗都不再提供「恢复此版本」，改显示「留痕·不可恢复」；
- 「查看」弹窗显示 `describeOutlineDiag` 的完整原因（分类 / 规模 / 缺失项 / 覆盖率 / 耗时），而不是原来那句「环节产物快照」。

## 六、未覆盖边界 / 已知不做

- **无法追溯**：本轮只能让**之后**的失败可诊断。那 9 个项目的历史原因是永久未知的（当年没有记录），报告里的任何归因都只能是「今天的判据算什么」，不是「当年发生了什么」。
- **今天的判据更严**（13/25 被拦，其中 11 个已有大纲）：这是**待确认的候选发现**，不是本轮结论。它意味着「被守卫拦住」不能解释存量失败，也意味着守卫的阈值可能需要按真实成功率重校（未做，需要新的取证）。
- **未做浏览器点击实测**：本轮验证是源码级 + 单测/集成测 + PB hook 落库路径通读（`rec.set("payload", body.payload)` 原样透传，`label` 上限 200 未被触碰）。端到端点击复验步骤见 §七。
- **未写进库的形状**：只在「点击生成大纲且失败/被拦」时留痕。AI 解析本身的失败、生成中途关页面，都不会留下记录。
- **保留策略共用**：诊断行与普通快照共用「每项目最近 60 条」的清理（超删最旧非 `reset` 行）。连续大量失败理论上可能挤出旧成果快照——考虑到 5 秒同因去重与「每次失败都要用户点一次」，实际风险低，但这是既有策略的取舍，本轮未改。
- **多操作者**：快照按 `rh_user_id` 归属（既有语义），同一项目的另一位操作者看不到我的诊断记录。
- **刻意不做**：不把诊断写进 `bid_projects` 的新字段（会改 schema 与迁移，且不留时间序列）；不改拦截阈值；不自动重试生成（失败原因未知时重试＝烧钱）。
