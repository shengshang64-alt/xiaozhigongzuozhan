## 二、问题 → 根因 → 修法 → 验证

### 问题 1：整站核心交付动作（导出投标文件 / 偏离表 / 全套）没有行为级契约

`exportBidWord`（`useBidWorkspace.ts:9014`）、`exportDeviationWord`（`:9055`）、`exportAllDocs`（`:9122`）是「把本地产物落成可交付 Word」的出口，也是本项目核心价值「产出可对外交付的标书 / 方案 / PPT」的最后一步。这三条路径此前只有 `bidFiles.test.ts` 的**逐字节 docx 正确性**测试，没有 hook 级的**接线**测试——「点了导出，到底调没调对导出器、按什么顺序、传了哪个项目」没有任何行为断言。

**根因**：B32 按簇推进，导出排在最后一簇，此前轮次尚未轮到；且 `exportBidDocx` 等导出器只被**动态 import**（`bidFiles` 连带 docx + pdf worker 重依赖，见 `useBidWorkspace.ts:10200` 注释），比静态 import 更容易被测试漏掉接线。

**修法**：新增 `useBidWorkspace.export.test.tsx`（7 例），mock `./bidFiles` 只为**记录调用**（与 mock `pbJsonRequest` 网络汇同一性质；docx 正确性仍由 `bidFiles.test.ts` 兜底），被测对象是 hook 的导出接线（预检 / busy 流转 / 提示 / 顺序）。

**验证**：7 例全绿（见 §四）；反向验证 A/B/C 各自「删实现即变红」（见 §五）。

### 问题 2：无正文 / 无偏离表时，导出会「空手而归」却没有任何前置提示

`exportBidWord` 在 `cur.bid_chapters` 全空时直接 `return`（`:9018`），`exportDeviationWord` 在 `normalizeDeviationTable(cur.response_map)` 为空时直接 `return`（`:9059`）——这两条预检都在动态 import 之前，但此前只有 grep，用户若真触发（空项目点导出）只会看到「没反应」。

**根因**：预检分支容易被当成「文案」而非「契约」，从未行为级验证；且它们发生在 `await import("./bidFiles")` 之前（不白加载 docx 重依赖），值得钉死。

**修法**：用例①（无正文）、用例④（无偏离表）分别断言「给一句能照做的原因 + 零导出调用 + exportBusy 落回空」。

**验证**：用例①④绿；反向验证 A/B 各自让用例①/④红。

### 问题 3：资质硬拦截是「交付红线」，却只有 grep

`warnExpiredQuals`（`:8986`）在导出前核验资质台账：`localStorage["qual_hard_block"] === "1"` 且存在过期/30 天内到期证书时**硬阻断导出**（严谨要求下宁可不能导也不能带病交付）。这条「安全语义」此前只有 grep，grep 分不清「软警告」与「硬阻断」两条分支。

**根因**：这条红线藏在「导出前核验」的中间件里，容易被一并跳过行为化。

**修法**：用例③ `qual_hard_block=1` + 过期证书 → 断言 toast 含「已阻断导出」+ 零导出调用。

**验证**：用例③绿（含软警告分支的对照：默认无告警时正常放行，见用例②）。

### 问题 4：全套导出的「五闸门全确认」与「已就绪五件顺序」没有行为级契约

`exportAllDocs` 五闸门（parse/outline/compose/check/eval）任一未确认就拦截（`:9126`）；全确认后按「投标文件→偏离表→解析→检查→评标」顺序导出**已就绪**的部分（`:9133-9138`）。这条顺序与「仅包含已就绪部分」的语义此前只有 grep。

**根因**：全套导出是「多件导出器 + 条件导出」的组合，顺序与条件各自有测试但组合没有，组合错误（如顺序颠倒、或漏导某件已就绪文档）不会让任何现有测试变红。

**修法**：用例⑥（闸门未确认 → 零导出 + 「还有 5 个」原因）、用例⑦（五闸门全确认 + 五件全就绪 → 精确断言五件导出顺序 `bid→deviation→parse→dup_void→eval`）。

**验证**：用例⑥⑦绿；反向验证 C 让用例⑥红。
