## 0 · 一句话结论

技术参数响应表在 400 条参数时会往 DOM 里塞 **5635 个节点 / 800 个按钮**，是编制页最重的子树，而用户 90% 的时间只是扫一眼。改成每页 100 条后，首屏节点降到 **1444（−74%）**、渲染耗时 **342ms → 142ms（−58%）**，数据与统计口径完全不变。

## 1 · 问题 → 根因 → 修法 → 验证

### 问题

`src/components/bid-workspace/TechParamResponsePanel.tsx:226`（改动前）用 `rows.map()` 一次性渲染全量行，`rows` 上限为 `ROW_CAP = 400`。每行渲染两个可点 `<button>`（原文列 + 响应列）+ 3 个状态徽标，且带 `line-clamp-2`（触发浏览器布局计算）。

**这不是猜测**——用 400 条参数夹具在 jsdom 里实测（脚本见 §3）：`{tbodyRows: 400, totalNodes: 5635, buttons: 800, ms: 342}`。

### 根因

面板只做了「行数上限」（`ROW_CAP=400`，防止超大文本炸表），但**没有做渲染切片**。「400 行上限」解决的是数据量，没解决同时挂到 DOM 里的节点量。而该表在 S3（R3 轮）被搬进独立 Tab 后仍全量渲染——切回这个 Tab 就要重建整棵子树。

### 修法

`src/components/bid-workspace/TechParamResponsePanel.tsx`：

1. 新增常量 `PAGE_SIZE = 100`（带实测依据的注释：为什么是 100 而不是 50/200）。
2. 新增本地 UI 态 `page`（0 起）。
3. 派生出 `pageCount` / `safePage` / `pageRows`：
   - `safePage = Math.min(page, pageCount - 1)` —— **页码夹取**，避免「看到第 3 页 → 换成 20 条的来源 → 空白表」。
   - `pageRows = rows.slice(safePage * PAGE_SIZE, ...)` —— 只切渲染切片。
4. `gotoPage()` 在翻页时 `setExpandedKey(null)` —— 否则展开态会跟着 `r.index` 漂到新页的某一行上，读起来像「自己跳了」。
5. 表下新增分页条（`<nav aria-label="技术参数响应表分页">`）：区间文案 + `«` / 上一页 / `N / M` / 下一页 / `»`，首末页对应按钮 `disabled`，全部带 `focus-visible:ring`。
6. **仅在 `pageCount > 1` 时渲染分页条** —— ≤100 条时零视觉变化，行为与改动前逐字一致。

关键边界：`rows` 本身**没有被切**。`summary` / `coverage` / `onExport` 全部仍用全量 `rows`，所以统计数字、覆盖点名、Word 导出都不受影响。

### 验证（实测，非推断）

**DOM 规模对比**（400 条参数夹具，jsdom，同机同轮次）：

| 指标 | 改前 | 改后 | 变化 |
|---|---:|---:|---:|
| `<tbody>` 行数 | 400 | **100** | −75% |
| DOM 节点总数 | 5635 | **1444** | −74.4% |
| `<button>` 数量 | 800 | **204** | −74.5% |
| 首屏渲染耗时 | 342 ms | **142 ms** | −58.5% |

**真实语料验证**（`test_results/审查正文-三明.txt`，47,046 字，非合成夹具）：

```
{"corpusChars":47046,"ms":149,"tbodyRows":100,"nodes":1378,
 "pageInfo":"第 1–100 条/共 222 条（每页 100 条）«上一页1 / 3下一页»"}
```

→ 真实三明标书正文解析出 **222 条参数行**，自动分 3 页，首屏只挂 100 行 / 1378 节点。

**行为测试**（`TechParamResponsePanel.test.tsx` 新增 8 例，全部通过）：

| 用例 | 钉住什么 |
|---|---|
| 250 条 → 只渲染 100 行 | 切片生效；统计仍报「共 250 条」 |
| 分页条显示 `1 / 3` + 区间 | 页码与区间文案正确 |
| 点下一页 → 首条是 `101.101` | 不是重复第 1 页（防「分页假实现」） |
| 末页只剩 50 行 | 尾页行数 = 总数 % 每页 |
| 首页/末页按钮 disabled | 边界不可点 |
| ≤100 条不出分页条 | 零视觉噪音回归 |
| 翻页收起展开行 | 展开态不跟随 index 漂移 |
| 换来源致行数变少 → 非空 | 页码夹取生效，不出现空白表 |

## 5 · 用户 3 分钟验收

**这轮做了什么（一句话）**：技术参数响应表不再一次性渲染 400 行，改成每页 100 条 + 翻页条，首屏 DOM 减少约 74%。

**怎么验证**：

1. 启动 `start-local.cmd`，打开浏览器进「标书工作台」→ 选一个已有项目 → 第 3 步。
2. 点 `📋 偏离与响应表` Tab，滚到「技术参数响应表」。
3. **若该项目参数行 > 100 条**：表格下方应出现分页条，显示「第 1–100 条 / 共 N 条（每页 100 条）」和 `1 / 3` 这类页码；点「下一页」表格内容整体换一批，点「末页」跳到最后一页且只剩余数行。
4. **若 ≤100 条**：表格下方**没有**分页条——这是正确的，行为与改动前完全一致。
5. 顺手核对：表头「共 N 条」的数字应与分页条「共 N 条」一致，翻页时两个数字都不变（证明统计走全量、未被打折）。

**改坏的风险：低**

- 唯一行为变更是「>100 条时分页」。≤100 条路径是本轮唯一没改的代码路径，且有用例钉住（「≤100 条不出分页条」）。
- 已知小瑕疵（已处理）：翻页会收起已展开的行——这是刻意的，避免展开态跟着行号漂移；如果希望「翻页保留展开」，需要改用行 id 而非 index 作为展开键，属下一轮可选优化。
- 未触碰任何数据写入路径：`rows` 计算、`summary`、`coverage`、`onExport` 全部保持全量，导出 Word 的内容条数与改动前一致。
