## 0 · 一句话结论

本轮最有价值的发现不是"某个按钮坏了"，而是三类**静默失真**：用户看不到的错误（422/922 条情报永远不显示）、
报了"成功"但实际没做成（格式没同步、版式没解析）、以及把故障说成"没有"（检索失败 → 没有找到）。
这三类的共同点是**界面不报错**，所以只能靠审计与实测挖出来，且都补了「删实现即变红」的反向验证。

## 2 · 关键实证

### 2.1 情报列表分页失真（第 11 项，最严重）

真实库 `intel_items` 922 条。旧实现 `findRecordsByFilter(..., 500, 0, ...)` 固定截断：

```
可见条目总数: 922
旧口径 totalItems（列表里能翻到的）: 500
新口径 totalItems: 922
被旧口径丢掉、永远看不到的: 422
排序口径一致: true（前 5 条 id 逐一相同）
```

**取证方式**：把 `pb_data` 副本放到 `.scratch/pb_verify`（含 `-wal`/`-shm`，否则数据不全），
用**改动后的 hook** 在独立端口 7099 起只读实例，未触碰用户正在用的 7000：

| 实例 | totalItems | 深翻页 |
|---|---|---|
| 旧（7000） | **500** | 第 51 页即空 |
| 改后（7099） | **922** | 第 92 页满 10 条、第 93 页 2 条，合计 922 |

取证后已关实例、删副本；7000 与 8000 健康检查仍 200。

### 2.2 接口耗时实测（补齐上一轮"没实测就下结论"的账）

用户问"取全会不会变慢"，此前的说法没有出处，本轮补测（5–7 次取中位）：

| 场景 | 中位耗时 | totalItems |
|---|---|---|
| 无筛选 page=1 | **145ms** | 922 |
| 关键词「医院」 | 127ms | 597 |
| 类型+地区 | 99ms | 17 |
| 深翻页 page=92 | 141ms | 922 |

结果集 17 → 922 只差 44ms，说明**大头是固定开销不是扫描行数**；按此线性外推到扫描上限 5000 条约 0.8s，
且触顶时返回 `truncated=true`（界面可知，不会假装数据已全）。结论：当前规模无性能问题，
真到几千条再考虑给 `intel_views` 建可 join 的 raw SQL 查询路径（`kb_search.pb.js` 已有先例）。

### 2.3 隐私外发（第 8 项）

不是"可能泄漏"而是**已经在发**：真实样本 `_r69_intel.json` 里就有
「供应商联系电话：13330076038」「联系方式：0832-22561202」，而 `buildTagMessages` 把它原样发给第三方模型。
修法后测试**直接断言最终 messages**（不是中间变量）：

```
expect(text).not.toContain("13330076038")
expect(text).toContain("0832-******02")   // 掩码保留头尾，不影响模型判断
expect(text).toContain("内江市第一人民医院") // 业务正文不误伤
```

## 3 · 方法记录（可复用的教训）

1. **「界面不报错」的缺陷只能靠三条线挖**：先复现（浏览器/真实数据），再找代码路径，最后做反向验证。
   本轮 12 项里没有一项是靠"读代码觉得不对"定案的。
2. **反向验证必须记录"红了几条、剩下哪条绿"**。多项修复里我都保留了 1 条对照用例（真·空库、表单仍存在、
   成功提示仍在），删实现时它必须**继续绿**——否则说明测试本身是真空断言。
3. **"测试红了"不等于"代码坏了"**。第 2 项就是断言没跟着口径改（120 → 300）造成的假红，先修断言不是妥协。
4. **判断分页/截断类缺陷，要问"总量是多少"而不是"页面显示多少"**。第 11 项如果只看界面（500），
   会以为正常；只有查库（922）才发现少报 46%。
5. **PB hook 不热加载**。涉及 `pb_hooks/*.pb.js` 的改动必须重启 7000，本轮按纪律标注而未擅自结束进程；
   验证时用独立端口只读副本，既拿到真实证据又不干扰用户。
