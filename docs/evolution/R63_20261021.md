## 一、本轮做什么（一句话）

B25 记着「安中医 13.8 万字正文 / 133 条条款，clause_hit 只有 13/133 = 9.8%」，并列了 4 个候选解法。本轮**没有直接照着候选解法动手**，而是先把「漏掉的到底漏在哪」量出来——量完发现候选解法里有两条是错的，真正有效的第三条改动量最小。

## 二、问题 → 根因 → 修法 → 验证

### 问题 1：漏召回不是「检索不到」，是「算出了分数但装不进预算」

**取证**（安中医全量夹具 `.probe/az-fixture/azhongyi.full.json`：138,810 字 / 18 章 / 56 块 / 133 条款 / 预算 20,000 字）：

```
改前：命中 50 | 未命中 83 | 注入 6 块 | 覆盖章 4/18
对 83 条未命中逐条复查它在全部 56 块上的最高分：
  · 词表完全零命中（怎么选都选不到）：2 条
  · 有分数、只是没被选中（预算装不下）：81 条   ← 97.6%
```

**根因**：`selectBidEvidence` 的选择逻辑是「按条款轮转、先到先得」（原 `bidVisibility.ts` 的 4 轮 × 133 条款循环）。它逐条条款去抢块，**没有任何一处代码在优化「一共能让多少条条款拿到证据」这个目标**。于是 20,000 字预算装下 6 块就停了，剩下 127 条的诉求根本没进入决策。

### 问题 2（否掉候选解法①：把证据粒度切细）

B25 列的候选解法里有「压缩单位证据（章内二次摘要后再取证）」。我先按「块 → 段」把粒度从平均 2,681 字降到 200 字左右做了模拟，实测**反而更差**：

| 语料 | 现状（块） | 粒度下沉到段 |
| --- | --- | --- |
| 安中医全量 | 50 | 67 |
| 安中医子集 | 110 | **68** |

原因：块级方案里**一块可以被多条条款共用为证据**（6 块就覆盖了 50 条），把粒度切细正好把这种共享破坏了。这条候选解法被实测否掉，本轮不做。

### 问题 3（接受候选解法③：两阶段取证）

**修法**：新增 `selectEvidenceChunks`（纯函数，`bidVisibility.ts`），把选择拆成两个各自回答一个问题的阶段：

- **阶段①「这 20,000 字该放哪些块？」**：按「每字能新增多少条有证据的条款」贪心。这一步把原轮转算法的**意图**（每条条款都该有可见证据）变成可优化的**目标**本身。
- **阶段②「省下来的预算给谁？」**：覆盖饱和后，按「能让多少条款拿到自己最强的那块」贪心，把余量用于加固证据质量，而不是继续堆覆盖（此时再堆等于浪费预算）。

保持不变的（刻意不动的契约）：命中判据（任一检索词命中）、`input_complete` 语义、【输入可见性】说明块、来源 id 格式 `第N章 …/块K`、首块允许超预算、同一输入必得同一输出（同分按块序号，无随机）。

**验证（三份真实语料，旧 → 新，同一预算 20,000）**：

| 语料 | 规模 | 命中（旧→新） | 未命中 | 覆盖章 |
| --- | --- | --- | --- | --- |
| 安中医全量 | 138,810 字 / 56 块 / 133 条 | **50 → 131** | 83 → 2 | 4/18 → 7/18 |
| 安中医子集（入库夹具） | 47,103 字 / 21 块 / 133 条 | **110 → 123** | 23 → 10 | 5/18 → 9/18 |
| 建阳总医院（第二份样本） | 131,906 字 / 75 块 / **184 条** | **115 → 171** | 69 → 13 | 7/34 → 10/34 |

注入字数基本不变（安中医全量 19,822 → 19,773）。安中医全量新旧覆盖的章也对得上有业务含义的差别：旧算法完全没进「第9章 技术参数实质性响应评审」，新算法进了。

## 三、口径诚实性：宽松命中 ≠ 证据够判

`clause_hit` 的判据是「任一检索词命中该条款」（与生产一致）。它衡量的是「这条条款有没有证据落在本次注入范围内」，**不等于「证据够不够判」**。所以本轮额外用了一套更严的判据（命中 ≥2 个不同检索词 **且** 该块得分 ≥ 该条款自身最高分的 50%）对同一份数据复算：

| 安中医全量 | 宽松命中 | 严格命中 | 最佳块被选中 |
| --- | --- | --- | --- |
| 改前 | 50 | 33 | 13 |
| 改后 | 131（= 天花板） | **86** | **74** |
| 上界（全部 56 块都注入） | 131 | 120 | — |

结论要照实说：**宽松口径已经饱和**（131/133，剩下 2 条是词表真没命中，靠改选块策略永远补不上）；**真正的剩余瓶颈从「选哪几块」变成了「证据深度」**——严格口径只有 86/133，且全量注入仍只占正文约 14%。这条口径同时写进了测试（`bidVisibilityRealBid.test.ts` §7 新增严格判据断言），防以后有人把「随便命中一个词」说成召回已解决。

### 第 ③ 条的方法说明（必须照实写）

本会话跑在 Linux 沙盒里，**只有 2 核 / 3.9 GB 内存**，而单次工具调用上限约 175 秒。该仓测试有 301 个文件、其中 28 个是 jsdom（单个文件的测试环境初始化实测约 60 秒），**整包一次跑不完**（实测单跑 4 个 jsdom 文件就超过 175 秒）。

因此改为**分片实测，覆盖全部 301 个文件**：按「jsdom 28 个 / 纯 node 273 个」分成两组，jsdom 组 2 文件一片、node 组 34–50 文件一片，共 15 片；每片单独跑并记录「Test Files / Tests」计数，最后用文件清单做集合校验：

```
已跑文件: 301 / 全部: 301
未覆盖的文件（应为空）: （空）
```

合计 **3513 passed / 7 skipped / 0 failed**。三处要点：

1. **没有任何一个文件失败**。分片过程中出现过 3 个红，全部查清是环境相关、与代码无关，见 §九。
2. 关键文件另外用**默认配置**单独复跑确认（不依赖分片结果）：`bidVisibility.test.ts` 30 例、`bidVisibilityRealBid.test.ts` 27 例、`bidVisibilityCorpus2.test.ts` 5 例、`outlineGuardRealDb.test.ts` 1 例、`DeviationPanel.test.tsx` 15 例，以及 4 个 God Hook 行为测试 24 例。
3. 7 个 skip 中，**5 个是本轮新增的「本机夹具 / 本机路径缺失」保护**（见 §九），2 个是既有的。

**没有做自我豁免**：301 个文件全部实际跑过，失败数为 0；不是「本轮文件 pass / 全仓被挡」。

## 九、顺带修的四处「本机路径」测试（以及为什么算本轮相关）

这四处都**不是产品代码**，都只改测试自身，但因为它们让「四门」在任何非本机环境里**永远红**（或往仓库里拉屎），修掉才算把门禁做实：

1. **`outlineGuardRealDb.test.ts`**：真实库用普通只读方式打开，在「不支持文件锁的挂载点」（VM 沙盒 / 部分网络盘）上会抛 `disk I/O error`。对照实验（同一份库）：
   ```
   挂载点 普通打开      → FAIL disk I/O error
   挂载点 immutable=1   → OK  bid_projects=26
   VM 本地副本 普通打开 → OK  bid_projects=26
   ```
   改为「普通打开失败才回退 `immutable=1`」，宿主行为完全不变。
2. **`generate-format-materials.test.ts`**：硬编码读 `C:/Users/Administrator/Downloads/测试导出-…docx`，沙盒访问不到 C 盘 → 必然 ENOENT。
3. **`pdfScanLayer.test.ts`**：扫 `D:/重要文件/A重要客户情况/友商公司产品/招标材料及方案/` 下的真实 PDF 样本，沙盒没有 D 盘 → 收集阶段就 ENOENT。踩到一个坑并写进注释：**`describe.skipIf` 只跳过用例执行，工厂函数照跑**（Vitest 靠它收集用例名），所以 `collectPdfs` 必须自带存在性判断。
4. **`generate-ppt-kb-materials.test.ts`**：往 `C:/Users/…/Downloads/测试材料` 写 PPT。在 Linux 上那不是盘符路径而是**相对路径**，`mkdirSync` 会在**仓库里**造出 `C:/Users/…` 目录（本轮实测踩到，已在工作区清理干净）。改用 `path.isAbsolute(OUT_DIR)` 判本机是否真把它当盘符路径：Windows 上照旧写 Downloads，其它平台整块跳过。

四处都按仓内既有惯例（`tenderStructureRealBid.test.ts` 早就是这个形状）加 skip 门：**夹具/盘符不在就跳过，在时行为一模一样**。
