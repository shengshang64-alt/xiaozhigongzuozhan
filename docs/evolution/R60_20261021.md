## 一、本轮做什么（一句话）

R58/R59 把「项目 CRUD」「正文精修」从 grep 升级成行为测试后，B32 报出的扩展顺序是「… → 正文精修 → 体检与评标 → 导出」。本轮做**体检与评标**这一簇里**不依赖 LLM**的半边：交卷体检（`startSubmissionCheck`）与模拟评标（`startAiReview`）的成功路径要打多路 LLM，不在三旁路纪律内（只 mock 网络/提示条/路由，不 mock 业务逻辑），留给后续专做；本簇先钉住它们**在 LLM 之前的**六条用户能感知的契约。

**本轮零生产代码改动**（`useBidWorkspace.ts` 一个字节没动，反向验证的临时改动已字节级还原）。只新增 1 个测试文件 + 修 1 处既有测试的竞态。

## 二、问题 → 根因 → 修法 → 验证

### 问题 1：整站最贵的两个操作（交卷体检 / 模拟评标）没有行为级计费红线

`startSubmissionCheck`（`useBidWorkspace.ts:8610`）一次交卷体检 = 覆盖审计 + 全局事实核对 + 逐章内容护栏（多路 LLM）；`startAiReview`（`useBidWorkspace.ts:8336`）一次三路评标 = 3 次 LLM 调用。这两条路径此前只有 R57 给「大纲生成」钉过「先弹费用确认、取消不落库」，体检/评标这条更贵的计费红线只有源码 grep。

**根因**：R57 行为网第一张只覆盖了 `generateOutline`，体检/评标排在 B32 第三簇、尚未轮到。

**修法**：行为网用例①②分别从 `startSubmissionCheck` / `startAiReview` 入口触发，断言先弹费用确认、取消后零写请求。

**验证**：用例①②绿（见 §四）。

### 问题 2：无正文 / 无评分项时，体检/评标会白烧 LLM 且给不出能照做的原因

`runSubmissionCheck`（`useBidWorkspace.ts:8455`）在 `bidChaptersFor(cur)` 无任何非空正文时应直接拦下；`runEvalAll`（`useBidWorkspace.ts:8275`）在 `scoringItemsFromReport(cur.parse_report)` 为空时应直接拦下。这两条预检都在 LLM 调用**之前**，但此前没有任何行为断言钉住「预检命中即返回、零写请求」。

**根因**：这两条预检是纯本地判据，容易被当成「文案」而非「契约」，从未行为级验证。

**修法**：用例③确认费用后（无正文）→ 断言 toast 含「投标文件还没有正文」+「再做交卷体检」且零写请求；用例④确认费用后（`parse_report=null` 无评分项）→ 断言 toast 含「该评标依赖「技术评分要求 / 商务评分要求」解析项」+「勾选并解析」且零写请求。

**验证**：用例③④绿；反向验证 B（把无正文预检改成恒假）→ 用例③红。

### 问题 3：人工打分表是「本地生成、零 AI」，却没有人验证它真的落库

`initManualReview`（`useBidWorkspace.ts:8406`）按评分办法本地生成 `manual_review`（零 AI、零费用确认），是模拟评标链路里唯一不花钱的正向路径，此前只有源码 grep。

**根因**：这条路径与「评标要花 3 次 LLM」混在一个簇里，容易被一并跳过行为化。

**修法**：用例⑤给 `parse_report` 塞 3 个评分项（40/30/20），断言 `initManualReview` 不弹计费框、PATCH 落 `manual_review`（items 3 条、`scoring_item/max_score/manual_score/comment` 逐字段、`total_score=0`）、toast 含「人工打分表已按评分办法生成」。

**验证**：用例⑤绿；反向验证 C（删 `initManualReview` 的 `updateProject({ manual_review: review })`）→ 用例⑤红。

### 问题 4：归档只读硬锁在体检/评标三入口是「点了也不落库」，没人验证它真拦得住

`startAiReview` / `startSubmissionCheck` / `initManualReview` 三个入口都有 `if (blockIfArchived()) return`（归档项目只读，不写 `ai_review` / `submission_check` / `manual_review`）。这条安全语义此前只有 grep（且同样的 `if (blockIfArchived()) return` 行在文件里出现 10+ 次，grep 分不清哪处管哪个入口）。

**根因**：归档只读是「安全语义」，grep 只能证明有这行字，不能证明「归档项目上点了这三处都不落库」。

**修法**：用例⑥ `archived=true` 后依次调三个入口，断言 `costConfirmOpen` 仍为 false、零写请求、三条「已归档项目为只读」提示各给一句（不是静默吞掉、也不是「禁用按钮」）。

**验证**：用例⑥绿；反向验证 A（删 `startSubmissionCheck` 的 `blockIfArchived` 拦截）→ 用例⑥红。

### 问题 5（顺带发现并修复）：R59 行为测试有本地状态竞态，全量并行下会假红

全量 vitest 首跑时 `useBidWorkspace.chapterRefine.test.tsx` 的用例①（`activeChapter?.content`）与用例②（`activeChapter?.sanityWarning` 等）交替假红（两次跑红的位置不同），隔离单跑全绿——是竞态不是业务回归。

**根因**：正文编辑走 1s 防抖，`flushEditingContent` 在 `act()` 之外触发 → `setActiveProject` 的重渲染与 PATCH 落地（`h.calls` 里同步记下）可能错开一拍。测试只 `waitFor(patchCalls().length > 0)`（等的是 mock 记录，不等 React 重渲染），随后立刻读 `result.current.activeChapter`（由 `activeProject` 的 `useMemo` 派生），于是偶发读到旧渲染。R59 单跑时靠运气绿，本轮新增第 298 个文件把并行时序拉偏，暴露了这条潜在竞态。

**修法**：把用例①（`chapterRefine.test.tsx:129` 附近）与用例②（`:158` 附近）读本地状态的断言包进 `waitFor`——等「本地状态真正刷出来」再断言，与等 PATCH 的两个 waitFor 各司其职。

**验证**：修后全量连跑两次 298 files / 3497 passed 全绿（见 §四）。
