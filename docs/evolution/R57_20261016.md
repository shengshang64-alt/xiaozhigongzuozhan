## 一、问题：价值最集中的那个文件，是全仓唯一**没有任何行为测试**的地方

`src/pages/BidWorkspace/useBidWorkspace.ts`：**9,828 行 / 494 KB**，118 个 `useState`、238 个 `useCallback`、
14 个 `useEffect`、39 个 `useMemo`、28 个 `useRef`，**返回 371 个句柄**——`/bid-workspace`（25 个投标项目 /

- 全仓 **271 个测试文件里 `renderHook` 出现 0 次**——这个 hook 的行为**从未被直接跑起来过**；

  于是「搬一个簇」要同时改 9 处路径数组（审计 §3.1 的 `hookSources()` 建议正是指这件事）。

**这就是本轮的靶子**：先把「读源码」收敛成一条缝，再让这个 hook 第一次真的跑起来。

## 三、做法（4 个新增文件 + 9 个哨兵迁移，生产代码 0 改动）

### 1. `src/testing/hookSources.ts`（103 行）：唯一的「读源码」入口

```ts
REPO_ROOT                     // 由 import.meta.url 推仓库根，不再靠各文件自己算
HOOK_PATH                     // "src/pages/BidWorkspace/useBidWorkspace.ts"，全仓唯一字面量
normalizeEol(text)            // CRLF/CR → LF（导出，可被直接测）
sourceText(relPath)           // 仓库相对 POSIX 路径读取 + 进程内 Map 缓存 + EOL 归一化
hookSources(...extra)         // God Hook 文本；带参时与额外文件拼成一份文本
countMatches(text, re)        // 带 g 标志的计数（无 g 直接抛，防静默返回 1）
resetSourceCache()            // 缓存显式失效
```

两个刻意的设计：

- **错误文案带修复指引**：路径越界（`../`）抛「源码哨兵读取越界」；文件不存在抛
  「源码哨兵读取失败 + 解析后的绝对路径 + 请同步 src/testing/hookSources.ts 的 HOOK_PATH」——
  搬文件时**报错本身告诉你改哪一行**，而不是一个 `ENOENT`。
- **`countMatches` 拒绝无 `g` 的正则**：`String.match` 无 `g` 时返回首个匹配对象而非全部，
  在哨兵里区分不出「1 处」和「7 处」，是本族最容易踩的静默陷阱。

### 3. `src/testing/hookSourcesConvergence.test.ts`（5 例）：「守哨兵的哨兵」

收敛本身必须有守卫，否则下一个人两分钟就能把路径字面量写回去。它扫 `src/` + `scripts/` 下所有
`.ts/.tsx`，逐条强制：

1. `useBidWorkspace.ts` 这个文件名**在非注释代码里只能出现一次**，就是入口的 `HOOK_PATH` 行
   （注释里出现不算——两处解释性注释仍提到它）；
2. 每个 `from ".../testing/hookSources"` 的文件里**都不许再有 `readFileSync(`**；
3. 入口本身能用：`sourceText(HOOK_PATH)` 不抛、`hookSources()` 含 `export function useBidWorkspace()`、
   `HOOK_PATH` 形如 `src/**.ts`；
4. 地板检查（扫描文件数 > 100、名单里确实含入口与 hook）+ 用入口的文件名单里含
   `clauseOutlineAlignment.test.ts`——防止「扫了个空目录也全绿」。

> 写这个守卫时踩了自己的坑：第一版里写了 `const HOOK_LITERAL = "useBidWorkspace.ts"`，
> 规则①立刻把它自己抓住。改成从 `HOOK_PATH` 派生 `path.posix.basename(...)` 之后，
> **改 hook 文件名也只需要改入口那一行**——守卫与被守卫对象同源。
