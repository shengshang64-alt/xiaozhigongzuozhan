## 一句话结论

DS-R07 让系统「不确定就留空」了，但留下两个断头：**候选算出来却看不见**、**人工选了却不记住**。
本轮把这两头接上，并修掉「取消付费就白输一遍清单」的坑。

**你要的闭环现在真正跑通了**：第一次人工确认 → 自动写进映射库 →
第二次遇到同样措辞，界面直接标「历史映射」命中，**不再请求 AI、不再花钱**。

## 做了三件事

### ① 候选从「算出来没人用」变成「可见可一键采纳」

**问题**：DS-R07 把中把握（0.75~0.95）判为 `suggest`，但只在内存里算了一遍，
视图层拿不到——用户看到的还是「留空待人工」，只能从 579 条公司条目里手翻。

**修法**：

- `MatchRow` / `MappingCompareRow` 新增 `suggestion` 字段，带 product_id、标签、分数、**理由**（为什么建议它）
- `buildInitialRows` 把 suggest 带进行上
- `toCompareRows` 传递到视图；**已落定的行自动清空建议**（否则用户以为还有待选项）
- `ProductMappingPage.tsx` 在原「留空待人工」位置渲染成可点按钮：

```
留空待人工   [ ✨ 建议：院感管理系统 88% ]
```

鼠标悬停显示理由：`core-sim：客户核心「医院感染」↔ 公司核心「院感」（module_name）`

**实测**（浏览器，输入 6 条真实措辞后取消付费）：

```
hasSuggestion: true
suggestions: ["建议：院感管理系统", "建议：合理用药系统"]
```

### ② 人工采纳即沉淀，不再等「保存到建设清单」

**问题**：`upsertMapping` 早就写好了，但只在点「保存到建设清单」时才对
`kind==="manual"` 的行触发。用户不点保存就离开 → 白选，映射库永远是 0 条
（实测改造前 `check_mappings` 确实是 0 条）。

**修法**：`setMatchProduct`（人工指定/采纳候选共用的入口）在用户做出选择的那一刻
就调 `upsertMapping` → 写库 → 重载映射列表。

实现细节：`upsertMapping`/`loadMappings` 定义在 `setMatchProduct` 下方，
直接引用会踩 TDZ 并让 setter 身份不稳定（表格整表重渲染）。
用 `upsertMappingRef` / `loadMappingsRef` 承接，**且必须在 `useEffect` 里赋值**——
渲染期写 ref 违反 React 规则（`react-hooks/refs` 报 "Cannot access refs during render"，本轮实际踩到并已修）。

**实测（完整闭环验证）**：

```
点「建议：院感管理系统88%」
  → 该行变「人工指定」          ✅
  → 发起 POST /api/check_mappings 200   ✅
  → 数据库 check_mappings: 0 条 → 1 条   ✅
     "医院感染管理系统" → "院感管理系统" (命中 1 次)

第二次输入同样措辞「医院感染管理系统」
  → 表格显示：历史映射 | ... | 院感管理系统
  → 出现「历史映射」标记        ✅
  → 仍需 AI = false             ✅
```

**这一条就是你说的「后面再有类似的可以自动去匹配」。**

### ③ 取消付费后不再丢结果

**问题**：旧代码只在「全部命中」时才 `setRows(initial)`；有未命中时把结果挂在
AI 回调里。用户在费用确认里一点取消 → 界面回到初始态，**本地已经算好的命中全丢**，
等于请他重输一遍清单。（DS-R07 轮报里已记为遗留项，本轮修掉。）

**修法**：先落本地结果，再问 AI。文案也从「将对 N 条未命中条目做 AI 匹配」
改成「本地已对照 N 条（命中 M 条，可先直接使用）。是否再对剩余 K 条做 AI 语义匹配？」

**实测**：

```
付费确认前已有表格 = {hasTable: true}
点「取消」后     = {hasTable: true, rows: 6, hasSuggestion: true}
旧版此处 → 回到「选择来源并「开始一一对照」后…」的空态
```

## 数据副作用（如实说明）

我在真实验证「采纳 → 沉淀」时，**往用户真实库里写了 1 条映射记录**：

```
check_mappings: 医院感染管理系统 → 院感管理系统 (命中 1 次)
```

**我选择保留它**，理由说清楚让你判断：

- 这是一条**真实正确**的映射（医院感染管理系统 就是 院感管理系统），不是脏测试数据
- 删掉它反而有害：你以后遇到「医院感染管理系统」还得再手选一次
- 若你想清掉，命令是删 `check_mappings` 里 `customer_norm = "医院感染管理系统"` 那一行

改造前 `check_mappings` 是 **0 条**，现在是 1 条，且这条来自真实使用路径。

## 下一轮建议

1. **DSB16（原计划）：用你那 549 行标准文件重建公司标准库。**
   现在库里 579 条来源杂，与标准文件 549 行不一致，会让对照基准漂移。这是质量根因。
2. **DSB18（新）：映射库要能看见和清理。**
   现在沉淀了但界面没有「映射库」入口——用户看不到系统记住了什么，也没法删错的。
   一个记错的映射会永久污染后续所有对照。
3. **DSB19（新）：AI 匹配那一段本轮未动。**
   本地匹配已经把「需要 AI 的条数」从多条压到 1~2 条，但 AI 返回的结果仍走
   `applyAiPairs`（只在候选标签精确命中时才落）。这部分准不准，下轮单独实测。
