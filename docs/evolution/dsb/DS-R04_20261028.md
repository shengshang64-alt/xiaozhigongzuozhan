## 一句话结论

**标书检查页对「空标书」盖了合格章。** 18 个有效项目里有 17 个、正文为空（或没有章节），

它们全都会被判成「**可直接导出 · 未发现问题（或均已通过）· 0 处问题**」。这是最危险的一类缺陷：
用户以为检查通过就能交卷，实际那份文件里一个字都没有。本轮同时堵住回收站项目混入检查列表的问题。

## 问题 → 根因 → 修法 → 验证

### 问题 ①（P0）：空标书被判「可直接导出」

**实测复现步骤**（浏览器真实操作，非读代码想象）：

1. 登录后进入 `/bid-check`
2. 「检查对象」选「选择标书项目」，下拉里选 `贵港`（或 `【演练】R01-bid-20261004`、`56`）
3. 点「开始检查」

**修复前实测输出**（三份空项目结果完全一致）：

```
必须整改 0   丢分风险 0   建议整改 0   提示 0    可直接导出   Excel  HTML  标注版 Word
章节导航   共 0 章
段落 0 · 章节 0 · 页数≈0
无可渲染正文（项目未填章节或文件无正文）
问题清单   0 处
未发现问题（或均已通过）
```

**同一屏上，中间写着「无可渲染正文」，右上角却是绿色的「可直接导出」。** 用户只会看到绿的。

### 根因

`src/pages/BidCheck/runCheck.ts:144`（修复前）：

```ts
const expected = tech.length               // 技术章数
const complete = expected === 0 || withText.length >= expected
//                    ^^^^^^^^^^^^^^ 0 个技术章被判为「覆盖完整」
```

设计者当初的意思是「上传文件形态 expected=0 不适用」，但**项目形态下 expected=0 是真实情况**：
库里 17 个归档项目的 `bid_chapters` 就是空数组 `[]`。于是：

```
bid_chapters = [] → expected = 0 → complete = true → 顶栏显示「可直接导出」
```

已有的覆盖完整性保护（`cov.complete`，2026-10-24 P0-5 加的）**被这个 `expected === 0` 短路穿透了**。

### 修法

`runCheck.ts`：项目形态下 `expected === 0` 不再算完整，并给出专用文案。

```ts
// 2026-10-28（DS-R04）：项目形态下 expected===0 不等于「覆盖完整」
const complete = expected > 0 && withText.length >= expected
note: expected === 0
  ? "该项目还没有任何技术章正文（0 个技术章），本次检查没有可检查的内容——本结论不能作为交卷依据"
  : complete ? `已覆盖全部 ${expected} 个技术章` : `已检查 ${withText.length}/${expected} 章（…）——本结论不能作为交卷依据`
```

上传文件形态（`project === null`）在函数开头已单独 return，不受影响。

### 验证

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 贵港（空） | 可直接导出 / 0 处问题 | **检查范围不完整** + 「没有可检查的内容——不能作为交卷依据」 |
| 【演练】R01-bid-20261004（空） | 可直接导出 / 0 处问题 | **检查范围不完整**（同上） |
| 安徽中医药大学第一附属医院一体化核心（有正文） | 已检查 8/9 章 | 已检查 8/9 章（文案不变，判定不变） |

第三行是**回归对照**：修复没有把「本来就没问题」的项目误伤成不完整。

> 注：安中医项目 8/9 章是**真实数据缺口**，不是判据问题。库中第 11 章
> 「数据价值闭环核心能力设计」`content` 长度确实是 0，其余 8 个技术章 8,969~20,034 字。
> 检查器如实报告「1 章无正文，不在检查范围内」是正确的。

### 问题 ②（P1）：回收站项目混进「选择标书项目」下拉

**实测**：下拉共 26 个选项，其中 **8 个是回收站项目**：

```
56 · 霍邱县人民医院智慧医院（T14实测）· 福州全民健康信息平台（T14实测docx）· 13131 · 313131 · 13431
三明市中西医结合医院（回收站件）· 安中医项目
```

这些项目 `deleted_at` 非空、`bid_chapters` 为空。用户一旦选中，触发问题 ①的假放行。

### 根因

两层原因叠加：

1. **后端** `pocketbase/pb_hooks/bid_projects.pb.js:239-246`：列表路由只按 `rh_user_id` 过滤，
   **不过滤 `deleted_at`**。回收站过滤一直由各页面在客户端自己做。
2. **前端** `src/pages/BidCheck/BidCheckPage.tsx:82`：只做了去重/排序/搜索，**漏了剔除回收站**。
   对照标书工作台 `useBidWorkspace.ts:1833-1835` 是有这一步的（`listView === "trash"` 分支）。

### 修法

`projectOptions.ts` 新增纯函数 `excludeDeletedProjects`，页面按 **先剔回收站 → 再排序 → 再去重 → 再过滤** 的顺序调用。

顺序是有讲究的：`dedupeProjectOptions` 是「同名保 updated 最新」，
如果先做去重，**回收站里更新的同名记录会把正常项目顶掉**——真实数据里正好有这种情况
（「三明市中西医结合医院」回收站件 updated `10-27 07:02` 比正常件 `10-15 06:02` 新）。已补用例钉住这个顺序契约。

同时把计数文案从「共 26 个」改为「共 18 个项目 · 按最近更新排序（已隐藏回收站）」，让用户知道少的是哪些。

### 验证

| | 修复前 | 修复后 |
|---|---|---|
| 下拉选项数 | 27（含「请选择」） | **19**（含「请选择」） |
| 回收站脏项 | 8 个 | **0 个** |
| 计数文案 | 匹配 26 / 共 33 个项目（同名已合并） | **共 18 个项目 · 按最近更新排序（已隐藏回收站）** |
| 正常归档项目 | 保留 | **保留**（归档是已完成件，仍需可复查，故只剔回收站） |

### 问题 ③（P2）：界面文案漏出 markdown 星号

**实测**：检查范围告警条直接显示 `响应问题**不会被发现**`，星号原样呈现。
另在 `/bid-workspace` 大纲覆盖面板有 `会**自动跳过**它们`、`**已生成的正文不受影响**`。

**根因**：JSX 文本节点里写了 markdown 加粗语法，React 不做 markdown 解析，星号原样输出。

**修法**：改成语义化 `<strong className="font-semibold">`（`ReadingView.tsx:335`、`OutlineCoverage.tsx:105/124`）。

**验证**：见下方四门后的浏览器复验。

## 关于 `/intel-center` 第一轮探针报的 9 个错误

首轮巡检时 `/intel-center` 捕获到 9 条 `console: Failed to load resource: net::ERR_NETWORK_CHANGED`。
**重跑 4 轮（整页 goto / SPA 侧栏点击 / 长时间等待）全部 0 错误、`requestfailed` 0 条、HTTP ≥400 0 条。**

结论：`ERR_NETWORK_CHANGED` 是 Chromium 在请求进行中网络栈发生变化时的环境噪声（当时机器刚唤醒），
**不是产品缺陷**。按证据纪律如实记录，不写成「已修复」，也不据它改代码。
