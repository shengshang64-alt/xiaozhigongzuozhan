## 二、问题 → 根因 → 修法 → 验证

### 问题 1：正文编辑是标书产出的核心路径，却没有一条行为断言

`/bid-workspace` 的章节编辑器是用户写标书正文的主战场：选中章节 → 打字 → 1s 防抖自动保存 → PATCH 落库。这条路此前只有 `sanityJumpWiring.test.ts` 里的「读源码 + 正则」哨兵（钉 `flushEditingContent` 的字段名），从没验证过「打字真的会落库、且不会误改兄弟章」。

**根因**：R57 之前全仓 `renderHook` 命中 0 次，行为网从零铺起，项目 CRUD（R58）排在第一顺位，正文精修排在第二、尚未轮到。

**修法**：新增 `src/pages/BidWorkspace/useBidWorkspace.chapterRefine.test.tsx`（5 例），沿用 R57/R58 的 3 旁路 mock（`pbJsonRequest` / `sonner` / `MemoryRouter`），不 mock 业务逻辑、零 AI、不触网。

**验证**：5 例全绿（见 §四）。

### 问题 2：R55 的「标记随正文失效」契约只有源码级钉住，没有行为级钉住

R55 修过：正文一经人工改动，成稿期算出的丢字（`sanityWarning`/`sanityFirstHit`）与版式（`proseLintWarning`/`proseLintFirstHit`/`proseLintSeverity`）本地标记必须作废——它们的 offset 锚在旧正文上，不失效会「人已修好还红着」且跳转跳到错位置。当时用 `sanityJumpWiring.test.ts` 从源码文本钉住字段名，但从没在真实 hook 上跑过「编辑正文 → 标记确实被清空」。

**根因**：`flushEditingContent`（`useBidWorkspace.ts:6182-6219`）是这条契约的唯一实现，但它不是 hook 返回句柄，此前只能靠读源码间接验证。

**修法**：行为网用例②给章节塞满 5 个 stale 标记 → `selectChapter` → `setEditingContent` → 等 1s 防抖 → 断言落库的章节里标记 key 整个消失（`JSON.stringify` 丢 `undefined` 值）、本地 `activeChapter` 的标记同步为 `undefined`。

**验证**：用例②绿；反向验证 A（删掉 `flushEditingContent` 的 `stale ? {清标记} : {只改正文}` 三元里的清标记分支）→ 用例②红。

### 问题 3：归档只读硬锁在正文编辑入口是「静默拦截」，没人验证它真拦得住

`blockIfArchived`（`useBidWorkspace.ts:2090-2094`）是循环 5 A3 的归档只读硬锁。`setEditingContent`（`useBidWorkspace.ts:6235-6250`）入口用 `blockIfArchived(true)`（silent）拦：归档项目上打字应当「状态不变、零写请求、不弹提示」。

**根因**：这条是安全语义（防止误改已归档项目），此前只有源码 grep 钉 `if (blockIfArchived(true)) return` 这一行（且该行在文件里出现 10+ 次，grep 根本分不清哪处管正文编辑）。

**修法**：行为网用例④：`h.project.archived = true` → 挂载 → `selectChapter` → `setEditingContent("试图改动")` → 断言 `editingContent` 原样不动、等过防抖窗口仍零写请求、不弹「只读」提示。

**验证**：用例④绿；反向验证 B（删 `setEditingContent` 里那一条 `if (blockIfArchived(true)) return`）→ 用例④红。

### 问题 4：章节生成的「占位态」是本地态、不落库，这条契约从没被行为级钉过

`runGenerateChapter`（`useBidWorkspace.ts:6742`）在真开跑前先 `updateChapter(nodeId, { gen_status: "generating", genError: "" }, { persist: false })`——把章标记成「生成中」纯属本地 UI 状态，不该发一次写请求（真正落库要等生成产出）。而 `openProject`（`useBidWorkspace.ts:3416-3422`）会反过来把「generating 残留」复位成 failed 并落库——两个口径必须分清。

**根因**：`updateChapter` 不是返回句柄，其 `{persist:false}` 语义（`updateProject` `useBidWorkspace.ts:2069` 的 `opts?.persist !== false` 才 `persistProject`）此前没有任何行为断言。

**修法**：行为网用例⑤：`updateProject({ bid_chapters: [c1 改 generating] }, { persist: false })` → 断言零写请求 + 本地 `activeProject.bid_chapters` 已是 `generating`。

**验证**：用例⑤绿。

## 三、新增测试守的 5 条契约（用户点几下就能对应上）

| # | 契约 | 断言（`useBidWorkspace.chapterRefine.test.tsx`） |
| --- | --- | --- |
| ① | 正文编辑自动保存 | `selectChapter("c1")` → `setEditingContent("人工修订后的正文")` → 1s 后 PATCH `/api/bid_projects/p1` 的 `bid_chapters` 里 c1.content 更新、标题不变、兄弟章 c2 不变 |
| ② | 标记随正文失效（R55 契约） | 给 c1 塞 5 个 stale 标记 → 改正文 → 落库章节里 `sanityWarning`/`proseLintWarning`/`proseLintSeverity` key 消失，本地 `activeChapter` 同清空 |
| ③ | 正文没真变化不落库 | `selectChapter` 后 `setEditingContent(与原文相同)` → 等 1.2s → 零写请求 |
| ④ | 归档项目正文编辑静默拦截 | `archived=true` → `setEditingContent` → `editingContent` 不变 + 零写请求 + 不弹「只读」 |
| ⑤ | 生成占位是本地态不落库 | `updateProject({bid_chapters:[c1 改 generating]}, {persist:false})` → 零写请求 + 本地已 `generating` |

关键前置事实：本机 jsdom 默认域是 `localhost`，`decodeRhToken()` 走本地自用分支返回 `sub="local-user"`，`requireLogin()` 放行、`loadProjects` 真发请求——与 R57/R58 同一个「不 mock 业务逻辑」的前提；`gen_status` 初始用 `done`（不用 `generating`），否则 `openProject` 的「中断复位」会在挂载时多发一次 PATCH、污染「零写请求」断言。
