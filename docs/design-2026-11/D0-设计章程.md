## 1. 背景与为什么要有本轮章程

小智工作站业务内核（方案 / 标书七步 / PPT / 报价 / 客户 / 情报）已深，但日常体感「多处半残」：AI 超时与误报、大纲易丢、知识库问答不稳、局域网 sidecar 不可达、无真正账号隔离、移动端从未做成产品。

仓库里**并非没有设计**（2026-09 起已有 PRD/SDD/EDD/UI 与路线图），半残主因更接近：

- 原设计按「单机自用」，需求已漂向「约 10 人团队 + 局域网/移动体感」；
- 平台层（身份、部署壳、失败可感知）规范写了却未按优先级落地；
- 巨型模块 + 多 AI 代理并行改仓，缺少冻结的「先能用」顺序。

因此本轮选择：**完整顶层设计优先于写代码**，用增量方式对齐目标，避免再「堆功能不止血」。

## 5. 技术方向（预锁，细节见 D2）

- **前端**：React 19 + TypeScript + Vite + 现有路由/壳。  
- **数据与 API**：PocketBase（SQLite + pb_hooks）+ 模型网关 Key 在服务端。  
- **增强层**：Node sidecar（LibreOffice / 大文档 / AnyTXT / 生图），可降级。  
- **客户端形态**：Web 为主；可选轻 PWA；Electron/Tauri 仅当未来强需求且不迁业务进壳。  
- **模型**：Open Design 为主通道（默认 flash，难点 pro）；平台「内置 gpt-5.5」本地不可用问题在方案中写明处理原则。

## 9. 风险（设计阶段就要认的）

1. **设计过厚、日常仍半残**：用「冻结前禁止改业务代码 + 冻结后立刻按 D5 止血」对冲；禁止无验收的顺手功能。  
2. **需求继续漂移**：以 D0 非目标为准；新想法进「以后」池，不插入冻结前文档除非你改章程。  
3. **多代理并行改仓**：开发期 **仅 Harness 改业务代码**；本 Bot 与其他代理禁止并行改同一仓。  
4. **Harness / 微信推送**：本轮设计只定边界；转发器在 box `/home/box/wechat/grokbot-wechat/`，属后续期。
