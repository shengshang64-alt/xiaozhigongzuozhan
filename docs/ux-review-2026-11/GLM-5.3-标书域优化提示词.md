# 第三组：生成质量优化（S11-S12，用户追加反馈）

## S11：AI 生成标书去 AI 味（句式级，治本+兜底+主动精修三层）

**背景**：项目已有 PROSE_LINT_RULES（`src/pages/BidWorkspace/bidTypes.ts:7794` 起）管单词级黑名单（赋能/抓手/闭环）和部分句式（综上所述/响应结论为）。但实测真实生成正文（`test_results/审查正文-三明.txt`）发现 AI 味大头是**句式和段落结构级**——这些一个词都不在黑名单，组合起来却是浓浓 AI 腔。

**实测发现的 4 类漏网 AI 腔（黑名单管不到）**：
1. "不是……而是……"式升华（"这不是单一系统的采购，而是……体系重构"）
2. "一是……二是……三是……"排比（AI 凑结构感，真实工程师直接列条款）
3. "这一定位决定了……""上述技术参数均为……我公司已全部逐项应答响应"元话语收口
4. 宏观政策堆砌（"为贯彻落实健康中国战略""作为……策源地"等与具体技术实现无关的政策表述）
5. 补充："充分知悉/充分理解/高度重视"等态度词（评标看措施不看态度）

**改成（三层）**：

**A. 提示词补句式黑名单（治本）**——在 `bidTypes.ts` 的 `PROSE_LINT_RULES` 数组追加一组规则（注意保持数组语法与现有风格一致，且同步检查 `promptsSnapshot.test.ts` 快照是否需要更新）：
```
"禁升华句式：正文不得出现「不是……而是……」式对比升华（如"这不是……而是……"）——直接陈述事实（"本项目为……"），不给项目定性拔高；",
"禁排比凑结构：正文不得用「一是……二是……三是……」式排比——分点一律用「（1）（2）（3）」条款列，一条一个独立措施，不靠排比制造结构感；",
"禁元话语收口：段落/章节末尾不得用「这一定位决定了……」「上述技术参数均为……」「我公司已全部逐项应答响应」「充分知悉/充分理解/高度重视」等收口或态度词——收尾只写可核验的落地承诺（量化指标/责任分工/时限）；",
"禁政策堆砌：正文不得出现与具体技术实现无关的宏观政策表述（如"为贯彻落实……战略""作为……策源地""助力……高质量发展"）——标书写"怎么做系统"，不写政策学习心得；确需引用标准时只写标准编号与名称（如"电子病历分级评价五级"），不写政策口号；",
```

**B. 事后校验器补检测（兜底）**——在 `src/pages/BidWorkspace/bidProseLinter.ts`（若不存在则先 `glob`/`grep` 找实际 lint 文件）增加句式级检测规则，命中上述 4 类句式即标 warn，供"一键重写该段"调用。

**C. 「🧹 去 AI 味」主动精修动作**——在章节编辑器工具区（复用现有 refineChapter 通道）加一个按钮，传入专门精修提示词：把该章正文按上述句式黑名单逐句改写为工程师口吻（直接、具体、无升华、无排比、无政策堆砌），**保持技术参数与事实不变，只改表述**。

**验收**：
- [ ] 4 类句式黑名单进 PROSE_LINT_RULES，promptsSnapshot 快照同步
- [ ] 校验器能命中"不是而是""一是二是三是"并标 warn
- [ ] 「去 AI 味」按钮触发精修，改后正文无上述句式且技术参数不变
- [ ] 用一段真实含 AI 腔正文做改写前后对照，存 `_shots/`

## S12：招标文件主观分逐条确认机制

**背景**：招标文件里主观分（`isSubjective: true`，含"得 N-M 分"、优秀/良/一般/差、方案质量/完整性/合理性评判词，见 `bidTypes.ts:2269 classifySubjective`）是评标专家**人工打分**的部分——AI 能帮你写，但**每一分要拿几分、拿什么材料支撑，必须人逐条确认**，不能 AI 默认就过了。

**改成**：

**A. 主观分清单面板**——新建 `src/components/bid-workspace/SubjectiveScorePanel.tsx`：
- 从 `parse_report` 提取所有 `isSubjective: true` 的评分项（复用 `scoringItemsFromSection` / `classifySubjective` 现有逻辑）
- 逐条展示：评分项名 / 分值 / 评分标准原文（criteria）/ 当前覆盖状态（是否已落点章节）
- **每条一个"确认"动作**：用户点开该条，看到"这条评分专家会怎么看"的提示 + "已确认应对策略"勾选框 + 备注输入框（写"我们怎么拿这条的分"）

**B. 确认状态持久化**——确认状态存到项目数据（在 `bid_projects` 记录加一个 `subjective_confirmations` JSON 字段，或用现有 stage_gates 类似机制；**先读 bidTypes.ts 确认是否有可复用字段，没有再新增**）。未确认的主观分项在面板顶部显示计数徽标（"还有 N 条主观分未确认"）。

**C. 交卷闸门联动**——在第 7 步交卷清单（S9 阻断项）里加一条：「主观分未逐条确认」为待办项，全部确认后才勾掉。不强制阻断（主观分策略属人工判断，不卡死流程），但必须显式提醒。

**D. 入口**——面板挂在第 3 步「偏离与响应表」Tab 内（与 S3 同区），同时在第 2 步解析报告的评分项明细里给每条主观分加「主观」徽标 + 点击跳确认。

# 执行纪律（更新）

1. **顺序**：S1→S2→S3→S4 先做完编制页（用户直接反馈），再 S5→S10，最后 S11→S12（生成质量）。每完成一个切片跑门禁，绿了再做下一个
2. **每切片输出简报**：改了哪些文件 / 门禁结果 / 遗留问题
3. **遇到不确定的数据结构**（如 bid_chapters 的 part 字段、响应表待确认数字段名、主观分确认存哪个字段），先 `read` 读 `src/pages/BidWorkspace/bidTypes.ts` 确认，**禁止凭猜**
4. **S3 联动是最大风险点**：jumpToResponseNode 切 Tab 的逻辑要实测——从偏离表点定位，必须切回编制 Tab 且滚动到章
