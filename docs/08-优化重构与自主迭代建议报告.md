## 2. 需要重构的内容

### 重构地图总览


### P0 · 两个必须先做的重构

**2.1 pb_hooks 抽公共 CRUD 工厂**
- 36 个 hook 每个都手写 list/get/create/update/delete + 属主校验（`X-Rh-User-Id`）+ `rec.set` 字段白名单；
- 抽 `_lib_crud.pb.js`：`makeCrud({ collection, ownerField, writableFields, beforeWrite })`，各 hook 只声明差异；
- 顺带统一解决：速率限制（1.2）、字段级写入（1.5）、totalItems 口径 bug（B-04）；
- **这是纯搬迁式重构，不改任何接口行为，风险低收益大。**

**2.2 PocketBase schema 纳入版本化迁移**
- `pb_migrations/` 目前是空目录，schema 靠 pb_data 快照 + 后台 UI 手点维护——**换一台机器、丢一次 pb_data，整个系统不可复现**；
- 用 PB 的 JS migration 从现有库导出首版全量迁移，之后所有 schema 变更必须走 migration 文件进 git。

### P1 · 提示词抽离（打破"红线 vs 重构"的治理冲突）

这是当前**性价比最高的重构**，但有个矛盾要先解决：

> docs/07 说"唯一现在就该动的重构是提示词抽离"，而 AI-ITERATION.md 红线说"禁止重构 bidTypes.ts / useBidWorkspace.ts"。**最高 ROI 的动作被自己的流程堵死了。**

解法（建议直接采纳）：**拆文件 ≠ 改结构**。
- 把 `bidTypes.ts` 里 32 个 `build*Messages` 提示词构造器**原样搬迁**到 `src/pages/BidWorkspace/prompts/` 目录（按任务分文件：`prompts/tenderParse.ts`、`prompts/outline.ts`、`prompts/wasteCheck.ts`、`prompts/scoreMatch.ts`……），`bidTypes.ts` 只留 re-export；
- 给每个提示词加 `PROMPT_VERSION` 常量（如 `tenderParse@2026-09-22.1`），随 LLM 请求落库——**这是"提示词改了之后新老内容口径是否一致"的唯一可追溯手段**；
- 零行为变更：import 路径不变、函数签名不变、提示词文本一字不动；
- 搬完之后：单测可以打、提示词 diff 可以看、红线"禁改语义"依然生效（改语义仍需问你）。

### P2 · 巨型 hook 拆分（长线，不急）

- 模式统一为三层：**接口层**（纯 fetch/PB 调用）→ **纯逻辑层**（无 React 依赖的业务函数，可单测）→ **状态层**（薄 hook，只做 state 接线）；

- `useBidWorkspace.ts`（99 个 useState）**永远最后动**，且只做"函数外提"，不重组状态。

### 明确不建议动的（守住红线）

## 3. 标书与方案模块：必须做好的"限制"

这一节回答你的核心问题：**招标文件解析、参数生成这些 LLM 出口，该上哪些硬限制。** 原则一句话：**提示词管"意图"，代码管"底线"——所有影响废标/评审的约束，必须有一层代码硬校验，不能全靠 prompt 自觉。**

### 3.1 招标文件解析（当前缺口最大的地方）

**现状**：`buildTenderParseMessages`（`bidTypes.ts:3829`）已有"提取铁律/要点化铁律/分块铁律"，但全部是软约束；输出是"要点摘要"，**没有原文逐字引用、没有证据定位**。

**建议加的四层硬限制**：

| 层 | 限制内容 | 实现位置 |
|---|---|---|
| L1 输出 schema | 每个解析项定义 JSON Schema（类型/最大条数 25/单条最大 60 字），**代码校验**，不合格直接进修复重试而不是放行 | `bidTypes.ts` sanitize 函数升级（现有 sanitize 只做字段裁剪，不验约束） |
| L2 证据锚定 | 数值类字段（金额/天数/比例/份数/期限）强制输出 `evidence` 字段：原文片段（≤80 字逐字引用）+ 所在页/段序号；解析完成后**代码层做子串匹配**（引用必须能在原文中原样找到），找不到 → 标黄"待人工确认"，不得静默入库 | 提示词加约束 + 解析后本地 validator |
| L3 分块合并对账 | 分块解析（>14000 字切块）合并时，记录每个字段来自第几块；同一字段多块冲突 → 全部保留并标记冲突，禁止代码擅自二选一 | `useBidWorkspace.ts:394` parseTenderChunked |
| L4 完整性兜底 | 缺失字段清单由系统统一生成（现有铁律已禁止模型输出"未提及"），但**建议再对照解析项清单硬核对**：模型没输出且原文确实没有的才进"缺失清单"，防止分块漏解析被当成"原文没有" | 合并阶段新增 cross-check |

> 这正好对齐你自己的硬规则：逐字引用（verbatim quotes）+ 字符级 diff，禁止改写。目前解析链路是"模型复述要点"，离你的规则还差一层证据链。

### 3.2 招标参数生成 / 响应参数生成

**现状**：方案三模式 strict/moderate/full（`solutionTypes.ts:459`）已有"未知值写【待填写】、禁止编造不同数值"的约束，方向正确。

**建议补的限制**：

1. **参数值来源分级**（写入提示词 + 输出格式）：
   - 每个生成的参数值标注来源：`[招标原文]` / `[产品基线]` / `[行业惯例]` / `[AI 建议]`；
   - `[AI 建议]` 类参数在导出 Word 时**自动标黄**，交付前必须人工确认——防止"看着很像真的"的编造参数混进标书（废标级风险）；
2. **★/▲ 实质性条款闭环校验**：响应参数生成后，代码层逐条对照解析出的 ★/▲ 条款清单，检查"每条是否都有响应点"，漏一条 → 阻断导出并列出清单（纯本地逻辑，零 AI 调用，你已有 starText 注入的基础：`bidTypes.ts:3885`）；
3. **数值一致性检查器**：同一数值（预算金额、工期、质保期）在大纲、正文、偏离表、报价中必须一致——生成完成后跑一遍正则扫描对账（docs/06 九项新能力里的"全文一致性检查器"就是这个，建议提到最高优先级）；
4. **长度与结构硬限**：章字数 400–2000（已有 `sectionWords` 钳制 `bidTypes.ts:3901`）之外，再对"单章 <400 字""叶子节点超目标 ±20%"在代码层告警，目前只靠提示词约束（`bidTypes.ts:3902-3903`）。

### 3.3 方案生成（SolutionStudio）

1. **KB 素材引用率上限**：现有"禁止整段照抄"是软约束（`solutionTypes.ts:529`）。建议生成后代码层算一次"与注入 KB 素材的 4-gram 重复率"，>15% 的段落标记"疑似照抄"提示重写——防查重、防客户发现"这是别家方案改的"；
2. **事实基线冲突检测**：`stableUser` 已注入医院项目事实基线（`solutionTypes.ts:522`），生成后本地扫一遍：正文中出现的医院名称/床位数/系统名称与基线不同的 → 标红（防模型把 A 医院的方案写成 B 医院的数据，这是售前最丢分的错误）；
3. **模式边界硬校验**：strict 模式下生成了"超出需求清单的功能点"→ 提示；full 模式下章节数超上限 → 提示。让"三模式"从提示词人设变成可验证的输出约束。

### 3.4 通用护栏（所有 LLM 任务适用）

- **输出不入库原则**：AI 原始输出永远先存草稿区，人工确认后才进正式记录（现在基本如此，保持）；
- **每次生成留痕**：prompt 版本号 + 模型 + 输入哈希 + 原始输出全文落库（`generation_log` 集合），三个月后你能回答"这份标书这段话是哪个版本提示词、哪个模型生成的"；
- **单次任务成本上限**：一次解析/生成的预估 token 超阈值（如 200K）先弹确认——`costConfirm.ts` 已有每日确认机制，扩展到单任务级。

## 5. 大模型自主迭代：现状评估与升级方案

### 5.1 现状：机制设计好，工程地基缺

你的 AI-ITERATION.md v2 已经具备：唯一入口手册、三来源账本、七条发现通道、A/B/C 三类放行门、六视角轮换、无人值守落盘、19 轮实际执行记录。**流程设计可以给 90 分。**

但 LLM 自主迭代的安全公式是：**自主度 = 机制设计 × 工程护栏**。你的机制 90 分，护栏大约 30 分：

| 缺口 | 后果 | 证据 |
|---|---|---|
| 零测试网 | LLM 改错代码只能靠 build+lint+实机截图发现；类型正确 ≠ 行为正确 | 全仓 0 个 test/spec 文件 |
| 账本并发竞态 | 已实际发生两进程同时推进 round 互相覆盖 | `.workbuddy-ai/memory` 记录 |
| health-loop.sh 本地跑不了 | "健康检查循环"在 Windows 开发环境形同虚设 | `scripts/health-loop.sh:7,20-21` 写死 Linux 路径 |
| 最大代码债被红线豁免 | 循环只能修小毛病，结构性问题永远留给人类 | AI-ITERATION.md §5 红线 |
| 提示词改动无回归手段 | 红线"禁改提示词语义"只能靠 LLM 自觉判断"语义是否变了" | 无提示词测试集 |
| 无成本审计 | 自主迭代每轮都在烧 token，没有用量落库就看不出"哪轮烧钱异常" | token 用量不落 PB（§1.3） |

### 5.2 升级方案：三层护栏架构

```
┌─────────────────────────────────────────────────┐
│ 第 1 层 · 机器硬门（不过就停，LLM 无解释权）        │
│   pnpm build → pnpm lint → vitest 提示词回归集     │
│   → git diff 行数上限（如 >500 行强制转人工）       │
├─────────────────────────────────────────────────┤
│ 第 2 层 · 分类放行（沿用现有 A/B/C，收紧 B 类）     │
│   A 修 bug：自动；B 优化：自动但 diff≤100 行；      │

├─────────────────────────────────────────────────┤

│   每轮 token 成本；MORNING.md 异常成本标红         │
└─────────────────────────────────────────────────┘
```

**具体落地动作（按顺序）：**

1. **vitest + 提示词回归集**（一切的地基，§4.6）：有了它，LLM 才配动提示词；没有它，红线只能靠自觉。
2. **账本并发修复**：`.loop/ledger.json` 改为"写入前重读 + round 号乐观锁"（写时校验 round 未被推进，被推进则合并重试），或干脆改成 append-only 的 `.loop/events.jsonl` + 按需物化视图——append-only 天然免疫并发覆盖。
3. **health-loop 本地化**：写一个 `scripts/health-loop.cmd`（Windows）：起服务 → 轮询 8000/7000 端口 → 跑 build+lint → 失败写 `.loop/health-fail.log`。接入每日定时任务。
4. **diff 预算机制**：在 AI-ITERATION.md 第 8 节验证门禁里加一条："本轮 diff >500 行或涉及 >5 个文件 → 强制拆分或转人工确认"。LLM 自迭代最大的事故模式就是"一次改太多无法归因"。
5. **D 类提示词变更流程**（新加进 AI-ITERATION.md §6）：改提示词 → 版本号 +1 → 跑回归集 → 金标准关键字段对比 → 通过才记账；关键字段变动 → 报告里**逐字 diff 列出来**给你看。
6. **成本看板**：`llm_usage` 落库（§1.3）后，MORNING.md 加一行"昨日迭代消耗 X tokens / 约 ¥Y"，异常（超均值 3 倍）标红。
7. **每周一次"架构债专项轮"**：把 P1/P2 重构清单（本文 §2）作为 C 类方案逐条喂给迭代循环，让 LLM 自己写搬迁方案、你点头、它执行、测试网兜底——**用迭代机制本身来还代码债**，而不是指望某次大重构。
