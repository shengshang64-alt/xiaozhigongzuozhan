即：闸门的目的是**防止 AI 乱加功能**，不是**防止 AI 把已有能力修到能交付**。本次授权正是把这两件事分开。

## 三、依赖白名单（原红线第 6 条「不引入依赖」的例外）

### ✅ 允许引入，但**必须同时满足全部 5 个条件**

1. **许可证已核实且为宽松/弱著佐权**：MIT / Apache-2.0 / BSD / ISC / MPL-2.0。
   **禁止** GPL / AGPL / SSPL / 商业授权不明 / 无许可证。
2. **在 `docs/10-GitHub开源补强选型报告` 中已核实过**（含许可证、体积、本机可行性实测），
   或按第三节同等标准**新做一次核实并写入报告**。
3. **离线/本地优先**：不得引入必须联网才能工作的运行时依赖；不得引入按次计费的云服务。
4. **可回退**：必须记录安装方式与卸载方式；引入后若验证不通过，本轮内回滚干净。
5. **在报告中列明**：包名、版本、许可证、体积增量、替代方案、为何无更轻的方案。

### 当前已核实可用的白名单（源自 docs/10）

| 依赖 | 用途 | 许可证 | 接入位置 |
|---|---|---|---|
| **OCRmyPDF** | 给扫描 PDF 加文字层（离线命令行） | MPL-2.0 | 输入侧解析链路，`delivery-p0-01` |
| **transformers.js** | 文档级向量粗排（两阶段检索第一阶段） | Apache-2.0 | `kbCore.ts`，`delivery-p1-01` |
| **funNLP 词表** | 中文停用词/同义词表（纯数据，非运行时依赖） | 见仓库声明 | 检索分词，`delivery-p1-01` |

> 注：`docs/10 §4.1` 已实测否决「全库块级向量化」（268ms/292MB，本机不可接受），
> **不得**因引入 transformers.js 而重走该方案。两阶段（文档级粗排 → 现有 BM25 精排）是唯一已核实路径。

### ❌ 仍禁止

- 引入会**替换**现有技术栈的依赖（换 UI 框架、换构建器、换数据库驱动等）
- 引入需要改 PocketBase schema 才能用的依赖
- 引入体积超过 100MB 的运行时依赖（本机 C 盘仅 ~13-14GB 可用）
- 引入任何需要 `git push` 到外部仓库才能工作的依赖

## 五、授权后的放行判定流程（替换原第 6 步）

```
选题完成
  └─ 判定类别
       ├─ A/B 类 ──────────────────────────→ 直接执行（原逻辑不变）
       ├─ C 类
       │    └─ 是否落在第二节「已解锁」范围？
       │         ├─ 是 → 需要依赖？
       │         │        ├─ 不需要 → 直接执行
       │         │        └─ 需要 → 依赖在第三节白名单？→ 是 → 直接执行（报告中列许可证/体积）
       │         │                                    → 否 → 只写方案 + 等确认
       │         └─ 否 → 只写方案 + 等确认（原闸门）
       └─ D 类 ─────────────────────────────→ 记账本，不动手
  └─ 是否触碰第四节红线？→ 是 → 停下问用户（红线优先级高于本授权）
```

**红线优先级始终高于本授权。** 本授权只解开了「必须等确认」这一道流程锁，没有解开任何一条红线。

4. 本轮是否触碰任何红线：是 → 必须写明处理方式。
