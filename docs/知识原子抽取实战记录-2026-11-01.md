## 三、踩过的坑（按严重度）

### 坑 1：导入脚本把正文截断在 50000 字（最严重）

**现象**：1205 篇文档正文长度恰好都是 50000，抽取时只能看到前半部分。

**根因**：`scripts/import-vault-office.mjs` 写的是 `text.slice(0, 50000)`，
而 `kb_docs.content` 字段上限是 **500000**（`src/lib/anytxtIngest.ts` 用的是正确值）。
**差 10 倍**。

**修法**：已改为 500000。但**已导入的 1226 篇仍是截断状态**，需要重新导入才能恢复
（源目录 `D:\重要文件\A重要客户情况` 还在，抽查 5 篇能找回 3 篇）。

### 坑 2：INSERT 漏了 3 个字段

**现象**：`valid_from` / `attributes` 全部为空（2549 条里 2527 条）。

**根因**：`scripts/extract-atoms-bulk.mjs` 的 INSERT 语句漏了这 3 列。
影响：
- `valid_from` 缺失 → 生成时无法判断政策新旧（检索会同时给出「2019 年要求 3 级」
  和「2025 年要求 5 级」而不加区分）
- `attributes` 缺失 → 数值冲突检测失效

**修法**：INSERT 补齐。存量用 `scripts/backfill-attributes.mjs` 回填了 359 条
（metric 类覆盖 50%）；`valid_from` 无法回填（只有 6% 能从正文提取年份）。

### 坑 3：Zod schema 过严，合法内容被拒

实测被误拒的三种情况：

| 字段 | 原限制 | 问题 | 改为 |
|---|---|---|---|
| `title` | max 40 | 中文陈述句 45-50 字很常见 | **80** |
| `source_quote` | max 200 | 真实长句摘录 200-350 字 | **400** |
| `attributes.*` | `.optional()` | 模型对「不适用」会输出 `null`，整段 18 条被丢 | **`.nullish()`** |

### 坑 4：`minimax-m3` 的额度是按单次请求 token 预算限制的

**现象**：`max_tokens=2500` 以上立即返回 `429 quota exceeded`（33ms 秒拒），
但 `max_tokens=2000` 正常。**不是速率限制，是单次请求额度**。

**识别方法**：真限流会恢复且带 `Retry-After`；额度耗尽会一直秒拒。

### 坑 5：关键词判定 polarity 完全不可靠（已放弃）

尝试过用关键词回填 `attributes.polarity`，实测误判率太高：

```
"集成平台支持按 WS 445 标准完善数据集与数据元"
  正文含「…数据元项目缺失的，进行完善」→ 判 negative
  但这句是「问题描述 + 解决动作」，不是「未达标」

"投标人未通过资格审查" → 否定词「未通过」包含肯定词「通过」，判 neutral
"要求投标人具备资质"   → 这是招标方要求，不是我方状态，判 positive
```

**结论**：polarity 属于语义判断，规则判不准。**留空比填错好**（冲突检测会跳过无 polarity 的原子）。

### 坑 6：subject_key 语义不稳定导致去重失效

**现象**：同一政策事实被模型起了 **12 种 key 变体**：
```
policy:电子病历应用水平|三级医院
policy:电子病历应用水平分级|三级医院要求
policy:电子病历应用水平分级评价|三级医院基本要求
policy:电子病历应用水平分级评价|三级医院等级要求
...
```
后果：一次检索同时返回 3级/4级/5级 三个互斥要求（其中 3 级是 2019 年旧要求）。

**修法**：
1. 加 `POLICY_ALIASES` 归一主题部分
2. 剥掉限定部分的「要求/基本要求/等级要求」等后缀
3. 回填存量 69 条

修后 5 种变体全部归一为 1 个 key。

### 坑 7：语义去重差点误删有效知识

新增 `planSemanticDuplicates`（按「类型+级别+年份+主题」指纹去重），
实测把 25 条判为重复并删了，其中包含：

```
2019 年国家要求三级医院 ≥3 级   （历史政策）
2020 年国家要求 ≥4 级           （后续政策）
2025 年安徽省要求 ≥5 级         （地方政策，更严）
某医院已达 6 级                 （项目案例）
投标人须协助通过四级评审         （本项目具体要求）
```

**它们全是独立且有价值的**——删掉任何一条都会丢失「政策演进」或「地方要求」信息。

**已恢复这 25 条**，并把该函数标注为「只产出候选、禁止脚本自动 apply」。

### 坑 8：测试脚本硬编码查询词导致误判

A/B 对比跑「培训方案」章节时检索到 8 条**集成平台**原子，看起来像检索坏了。

根因是测试脚本把查询写成 `` `${CHAPTER_KEY} 架构 接口 平台 集成` ``，
任何章节都被这几个词主导。生产代码没这问题（用章节标题+条款文本）。

## 四、有效的做法（可复用）

### 4.1 抽取流程

```bash
# 1) 按高产出目录抽（排除标准规范库）
npx tsx scripts/extract-atoms-bulk.mjs \
  --tier=P1 --minscore=0.5 --exclude=03政策文件库 \
  --concurrency=2 --limit=400 --apply

# 2) 批量审核：先驳回低质量
npx tsx scripts/review-atoms.mjs --apply

# 3) 批量采纳推荐用途并通过
npx tsx scripts/approve-atoms.mjs --apply

# 4) 去重（key 级 + 内容级）
# （用 planDedupeGroups + planContentDuplicates，见 kbReview.ts）
```

### 4.2 并发与速率

- **并发 2 + 每路 1.2-1.5s 间隔**：无 429，约 27s/篇
- 并发 3 会触发较多 429（每篇约 0.5 个段被限流）
- 模型优先级：`minimax-m3`（最快 10s/篇）> `sensenova`（14s）> `agnes`（17s）

### 4.3 用途推荐映射（按类型给 1-2 个核心产出）

```
qualification → 只给 bid      （方案里很少逐条列资质）
script        → 只给 faq      （异议应答的主场）
policy        → 只给 proposal （编制依据）
metric        → proposal+ppt  （数据页）
product_capability → proposal+bid（技术章）
```

配内容信号补充（命中「报价/折扣/费用」→ 追加 quote；命中「汇报/演示」→ 追加 ppt）。

### 4.4 段落价值评估（kbParagraphValue）

跳过：目录行、封面、医院简介（"坐落于…创办于…三甲医院"）、背景套话。
加分：产品能力描述（"支持X功能/模块"）、案例业绩、资质认证、带口径指标。

实测效果：10 篇从 11 条 → 83 条（7.5 倍）。
