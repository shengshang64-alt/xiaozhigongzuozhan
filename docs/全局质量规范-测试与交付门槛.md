# 全局质量规范 · 测试与交付门槛 v1.0

> 本规范是售前工作台所有测试、优化、迭代工作的**质量宪法**。
> 与 `AI-ITERATION.md`（迭代流程手册）配合使用：流程按手册走，**质量标准按本规范判**。
> 生效日期：2026-09-26。起草：售前信息化专家 / 测试专家 / 前后端设计 / UI 设计 / 医院信息化 / 招投标专家联席评审视角。

---

## 0. 总纲：怀疑一切，举证一切

0. **真实性与严谨性是最高原则（用户 2026-09-27 明确要求）**：本工作站是**给医院看的**。界面上出现的每一个字、AI 输出的每一段内容、解析出的每一个字段、提示词产生的每一个结论，都必须真实、可溯源、可核验。
   - 严禁任何"编造填空"：AI 拿不到的事实就留空/标注待补，绝不虚构（医院等级、门诊量、联系方式等档案字段错一个都是灾难）。
   - AI 生成的字段必须带「AI 提供需核实」类标记并支持人工一键消除（现有机制，必须保持）。
   - 引用必须有出处（知识库引用、情报原文链接）；统计数字必须能对上明细。
   - 测试数据（"测试市人民医院"之类）与真实数据必须可区分、可批量清理，**给医院演示前必须清场**。
   - 招投标专业内容（评分办法、资质要求、废标条款）解析必须逐条可核对到原文位置，宁缺毋错。
1. **默认可疑原则**：任何功能在没有被实测验证之前，一律视为"可能有错"。上线时间长短、界面好看与否，都不构成"它是对的"的证据。
2. **数据正确性 > 一切体验**：售前工具的本质是**决策支持**。一条区域标错的情报、一个倒挂的截止时间、一段截断的摘要，都可能让售前人员错判商机、错失投标。数据错误是一票否决项。
3. **每个结论必须有证据**：问题记录必须带【复现路径 + 实际表现 + 期望表现 + 根因文件:行号】四要素，缺一项不算确认。
4. **用户可验证**：所有修复必须给出"用户自己点几下就能看到效果"的验证步骤（用户编程水平不高，报告不许出现裸 diff）。
5. **不引入回归**：任何修复必须跑本规范第 7 节的回归门禁，失败即回滚。

## 2. 数据质量规范（本系统实测教训固化）

以下条款全部来自 2026-09-26 实测发现的实锤问题，任何新抓取/解析/生成逻辑入库前必须自检：

1. **字段语义必须对位**
   - `region` 只能来自标题本体、条目自身的结构化元数据、或正文中的"采购人/政府采购网归属地"证据；**禁止**从相邻条目、代理机构名称等偶然命中中取值。
   - `published_at` 必须是**发布时间**：优先级 = URL 内嵌日期（如 ccgp `t20260925_...`）> 列表页条目自身时间戳 > 正文日期（且必须排除"递交/截止/开标"等上下文中的日期）。**禁止**取正文第一个日期充数。
   - `item_type` 徽章必须与公告真实类型一致（公开招标公告 ≠ 中标公告 ≠ 更正公告），宁标"未分类"不可错标。
2. **正文/标题不允许被处理逻辑污染**：HTML 剥离后不得引入多余空格/换行（关键词高亮标签剥离必须用空串替换）；摘要截取不得从半个词开始；片段非句子起点时展示层必须加省略号前缀。
3. **来源窗口纪律**：任何"取链接周边文本"的操作必须优先取**链接之后**的条目自身内容，向前取文本只能作为兜底且必须标记为低可信。
4. **统计口径一致性**：驾驶舱数字（待确认数、商机数、待办数）必须与列表页筛选结果一致；同一数据多处出现不允许出现两个口径。
5. **去重幂等**：同一 URL/同一公告重复抓取不得产生重复记录；重复判定必须做 URL 归一化（去 utm/尾斜杠/协议大小写）。
6. **失败可见**：源抓取失败必须聚合并可一键定位（当前 14/40 失败但缺乏逐源失败原因与最后成功时间，不达标）。

## 3. UI/UX 硬性条款

1. **每个等待都有反馈**：>300ms 的操作必须有 loading 态；>3s 的必须有进度或可取消。
2. **每个结果都有回执**：增删改成功要有 toast/状态变化，失败要有**人话错误信息**（不许裸抛英文异常）。
3. **每个空态都有出路**：空列表必须告诉用户"为什么是空的 + 下一步去哪做"（本系统空态做得好，保持住）。
4. **危险操作必须确认**：删除、批量清理、覆盖必须有确认弹窗且明确后果与数量。
5. **一致性**：同一概念全站同一叫法（"情报/线索/商机"不可混用）；同一操作（确认/忽略/收藏）交互模式全站统一；日期时间格式全站统一（建议 `YYYY-MM-DD HH:mm`，相对时间"刚刚/x分钟前"只用于 24h 内且悬浮显示绝对时间）。
6. **键盘与效率**：⌘K 全局搜索必须能覆盖高频跳转；列表页筛选条件变化必须即时生效且可一键清空。
7. **可访问性底线**：对比度达标、焦点可见、按钮有可读的 accessible name（供读屏与自动化测试）。
8. **中文排版**：标点悬挂、数字与汉字间空格、不出现孤字成行；时间显示"未来时间"必须带语义（如"截止 10-16"）防止误解为发布时间。

## 4. 测试方法：五步走查法（每模块必走）

1. **主流程走查**：以真实售前任务剧本跑一遍主路径，记录卡点。
2. **数据抽查**：≥10 条真实数据的字段正确性人工核验（对标权威源）；统计数字与列表交叉核对。
3. **边界与异常**：空数据、超长输入、特殊字符（`<>&"'\`、emoji）、断网/接口 500、重复提交、并发编辑。
4. **权限与隔离**：个人数据在他人账号不可见；管理员与成员权限差异符合预期。
5. **跨模块数据流**：上游改动能正确传导到下游（情报→线索→商机→标书→复盘）。

每个模块产出：问题清单（按第 5 节分级）+ 数据抽查记录。

## 5. 缺陷分级与响应

| 级别 | 定义 | 响应 |
|---|---|---|
| S0 致命 | 数据错误误导决策 / 功能不可用 / 数据丢失 / 越权泄露 | 立即修复，当日闭环 |
| S1 严重 | 主流程卡点、明显误导性展示、统计口径不一致 | 尽快修复（≤2 轮迭代） |
| S2 一般 | 体验差、文案歧义、非关键字段错误 | 排队修复 |
| S3 轻微 | 打磨项、一致性细节 | 攒批处理 |

## 6. 交付门槛（Definition of Done）

一次优化只有同时满足以下全部条件才算交付：

- [ ] `pnpm build` 通过（tsc + vite，最强单一校验）
- [ ] `pnpm test` 通过（vitest）
- [ ] 改到哪个模块就实测哪个模块（实机操作验证，非只看代码）
- [ ] 按 `AI-ITERATION.md` R1–R10 裁剪规则跑回归，全绿
- [ ] 改 `pb_hooks` 后已重启 PocketBase 并验证生效
- [ ] 问题台账（`docs/质量台账.md`）已更新：证据、根因、修复、验证四要素齐全
- [ ] 用户验证步骤已写入当轮报告

## 7. 回归门禁

直接引用 `AI-ITERATION.md` 第 9 节 R1–R10 清单及其裁剪规则，任何一项不通过 → 回滚，禁止在失败状态上叠加改动。

## 8. 红线（继承并再次确认）

不改 schema / 不改扣费 / 不改认证 / 不改导出交付物版式 / 不重构 bidTypes.ts·useBidWorkspace.ts 结构 / 不引入新依赖 / 不删业务数据 / 不动 VibeX 保护文件。拿不准就停下来问。

## 9. 前瞻性建设原则（为未来留门）

1. 新功能设计必须先回答"数据从哪来、错了怎么发现"——宁可少自动化，不可多静默错误。
2. 涉及 AI 生成的功能必须有：输入上下文裁剪策略、输出校验、失败降级路径、成本可见性。
3. 所有抓取/外部集成必须自带：健康度上报、限速尊重、失败重试上限、可手动兜底（手动录入）。
4. 多人协作场景（团队版）的每个新集合都要先回答可见性三问：谁能看、谁能改、谁能删。
