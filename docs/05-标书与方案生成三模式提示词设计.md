# 05 · 标书与方案生成「三模式」提示词设计

> 目标：给标书生成（重点是标书）加上可控的约束档位，解决"现在没有什么约束"的问题。
> 结论先行：**三个模式不是三套提示词，而是一套提示词 + 一个模式开关**。共用的骨架与防翻车约束不动，只切换一个"允许偏离招标原文的程度"约束块。

---

## 一、为什么不能写成三套独立提示词

现有标书章节提示词（`src/pages/BidWorkspace/bidTypes.ts` 的 `buildBidChapterMessages`，约 3868–4056 行）已经有 20 多条规则，涵盖逐条响应、技术参数忠实、承诺克制、事实一致、防编造、风格硬条款、配图约束等。

如果为每个模式复制一份，会有三个后果：

1. **规则漂移**。以后改一条通用规则要改三处，必然漏改，出现"严格模式禁止加码、全量模式忘了禁"这类不一致。
2. **无法做校验**。偏离表、模拟评标、覆盖审计这些下游模块要按模式判定，三套提示词没法给它们一个统一的判定依据。
3. **模式语义说不清**。用户看到"严格/适度/全量"三个词，真正想问的是：**"这三个模式到底差在哪一条线上？"**

所以正确做法是：**找到那条唯一的轴，把它参数化。**

### 那条轴是什么

> **允许"超出招标原文"的程度。**

从"一个字都不许多"到"大幅超出"，中间是连续谱。这条轴下面挂着 5 个必须**联动切换**的子维度——只切其中一个就会自相矛盾：

| 子维度 | 严格 | 适度 | 全量 |
|---|---|---|---|
| ① 技术参数口径 | 逐字照抄，零加码 | **同严格**（红线） | **同严格**（红线） |
| ② 主观方案展开 | 按招标要求逐项应答 | 要求项内深化 | 主动增设章节 |
| ③ 能否新增承诺 | 禁止 | 表达可扩、承诺不可增 | 可增，但须量级自洽 |
| ④ 素材使用强度 | 仅精确匹配 | 可引用，须适配 | 最大化使用 |
| ⑤ 篇幅取向 | 完整即止 | +30%~50% | 1.5~2.5 倍 |
| ⑥ 偏离表目标 | 全"满足" | 少量正偏离 | 正偏离作优势呈现 |

**① 在所有模式下都不放宽，这是红线。** 技术参数加码等于给自己加验收义务，招标值 ≥500 并发你承诺 1000，验收时就得跑出 1000。现有提示词里已经有一条"承诺克制（最小值响应）"，这条在三个模式下都要保留。

## 二、先解决一个危险的模糊表述

你说的"技术参数只调整一些要求字眼"——这句话必须给出可执行边界，否则模型会把它理解成"可以改数值"。

**判定标准：只允许「响应性包装」，禁止「实质性变更」。**

### ✅ 允许的三类改写（且必须保留原文全部限定信息）

| 类型 | 招标原文 | 正文可写 |
|---|---|---|
| 人称语态转换 | 投标人应提供 7×24 小时服务 | 本项目提供 7×24 小时服务，满足招标要求 |
| 疑问转陈述 | 是否支持 ≥500 并发 | 本项目支持 500 并发用户，满足招标要求 |
| 补响应结论词 | 提供三年免费质保 | 本项目提供三年免费质保，完全响应招标文件要求 |

### ❌ 禁止的实质性变更（要逐条写进提示词）

- **改数值**：≥500 并发 → ≥1000 并发；≤8 小时到场 → ≤4 小时；3 年质保 → 5 年
- **改单位口径**：Mbps → Gbps；并发用户 → 注册用户；工作日 → 自然日
- **改范围**：部分科室 → 全院；试点 → 全面推广
- **删限定语**：漏掉"含税""含运费""含三年质保""含安装调试"
- **无依据加码**：招标没要求的功能主动承诺

> 这一节建议原样进提示词。它是三个模式共用的底线，也是**防废标**的关键——评标专家逐条比对时，"≤8 小时"写成"≤4 小时"属于响应不实，可能被认定虚假响应。

## 三、三模式提示词全文（可直接复制）

### 共用部分（三模式都注入，无需修改）

现有的写作铁律、风格硬条款、事实块、条款清单、配图约束**全部保留不动**。模式块作为一条独立规则插入，位置建议放在"写作铁律"之后、`BID_STYLE_RULES` 之前。

### 模式一 · 严格响应模式（`strict`）— 建议设为默认

```
【本次生成模式：严格响应模式】

模式定位：招标文件既是下限也是上限。本模式目标是「零风险应答」——用最少的自设义务换取「完全响应」的评审结论。适用于招标要求明确、评分以符合性审查为主、或需要控制履约风险的场景。

一、技术参数与指标口径（本模式最严）
1. 引用招标技术参数、指标、配置、服务要求时，必须逐字照抄招标原文表述，不得改写、不得优化措辞、不得调整数值、单位、档位、范围、数量与限定语（含「含税」「含运费」「含三年质保」等）。
2. 仅允许做「响应性包装」，即把招标的要求句改写为我方应答句，且必须保留原文全部限定信息。允许的改写只有三类：
（1）人称与语态转换：招标「投标人应提供 7×24 小时服务」→ 正文「本项目提供 7×24 小时服务，满足招标要求」；
（2）疑问/条件句转陈述句：招标「是否支持…」→ 正文「本项目支持…」；
（3）在原文后补响应结论词：「满足招标文件要求」「完全响应」。
3. 禁止任何实质性变更，包括但不限于：把「≥500 并发」写成「≥1000 并发」、把「≤8 小时到场」写成「≤4 小时」、把「3 年质保」写成「5 年」、把「部分科室」写成「全院」、把「并发用户」换成「注册用户」、删除原文的任何限定条件。
4. 招标要求了但事实块中没有具体值的（金额/日期/人员/证书编号等），一律写【待填写】或「按招标文件要求响应」，禁止自行补一个看起来合理的值。

二、主观方案展开幅度
5. 实施、服务、培训、质保、项目管理、风险应对等主观方案，严格依据招标文件列明的要求项与评分办法组织，逐项正面应答即可。
6. 招标未要求的维度，不主动增设小节、不主动增加服务项、不主动提高标准。

三、是否允许新增内容
7. 禁止新增招标文件未提及的功能、服务、案例、资质或承诺。本模式下每一句多余承诺都会转化为验收义务，宁少勿多。

四、素材使用
8. 仅使用招标原文、事实块与团队自有资料中与本项目直接对应的内容。知识库素材仅在能精确匹配本项目等级与规模时引用，且须注明来源。

五、篇幅取向
9. 字数预算是上限而非目标。以「条款应答完整、无遗漏」为唯一完成标准，不追求篇幅，不做同义反复扩写。

六、偏离表目标
10. 目标为全部条款判定「满足/完全响应」，不制造正偏离。若某条客观上只能负偏离，如实标注并说明，禁止粉饰。

七、本模式特有禁止项
11. 禁止出现「优于」「领先」「行业首创」「额外赠送」「免费升级」等超出招标要求的表述。
```

### 模式二 · 适度扩展模式（`moderate`）

```
【本次生成模式：适度扩展模式】

模式定位：在完整响应的基础上，对主观方案做有节制的深化，用团队沉淀素材增强说服力。适用于竞争较充分、评分办法含「方案完整性/合理性」主观分、需要在响应完备度上拉开差距的场景。

一、技术参数与指标口径（与严格模式完全一致，不放宽）
1. 技术参数、指标、配置、服务要求逐字照抄招标原文，只允许做响应性包装（人称语态转换、疑问转陈述、补响应结论词），禁止调整任何数值、单位、档位、范围、数量与限定语。
2. 禁止实质性变更：不得把「≥500 并发」写成更高的值、不得缩短招标给定的到场/响应时限、不得延长或缩短质保期、不得扩大或缩小服务范围、不得删除原文限定条件。
3. 招标要求了但事实块中没有具体值的，一律写【待填写】或「按招标文件要求响应」。

二、主观方案展开幅度（本模式的主要扩展区）
4. 在招标已要求的维度内，允许对主观方案做内容深化，扩展方向限于：行业标准做法的具体展开、管理机制与流程的细化、实施步骤与阶段划分的说明、质量与风险控制措施的展开、岗位职责与协作机制的说明。
5. 允许增加「如何做」的细节，不允许增加「做什么」的新项。即：可以把招标要求的服务讲透，但不得新增招标未要求的服务。

三、是否允许新增内容
6. 允许表达层面的扩展，禁止承诺层面的新增。判定标准：若新增内容构成一项可被验收的交付物或服务义务，则禁止；若只是对已有义务的说明、论证或举例，则允许。

四、素材使用
7. 可引用知识库与自有资料中的案例、数据、制度、方法作为支撑，引用处注明来源。
8. 素材必须与本项目医院等级、床位规模、预算量级适配；规模不符的素材只可取其方法，禁止取其数字（如不得把三甲医院的并发量套到二级医院）。

五、篇幅取向
9. 主观方案章篇幅可比严格模式增加约 30%–50%，扩展量应集中在招标评分办法明确给分的维度上，不做无差别膨胀。

六、偏离表目标
10. 目标为「完全响应」，允许出现少量正偏离，且正偏离必须落在招标鼓励项或评分加分项上；禁止为凑正偏离而虚构优势。

七、本模式特有禁止项
11. 禁止把「适度扩展」做成「全面加码」——不得新增服务项、不得提高招标已明确的指标档位。
```

### 模式三 · 全量扩展模式（`full`）

```
【本次生成模式：全量扩展模式】

模式定位：最大化方案厚度与竞争力。适用于评分办法中「方案完整性/先进性/技术路线合理性」权重高、竞争激烈、需要通过内容深度拉开分差的场景。本模式允许主动增设章节与内容，但两条红线不可触碰：技术参数不加码、规模与预算必须自洽。

一、技术参数与指标口径（红线，不放宽）
1. 技术参数、指标、配置的响应值仍不得超出招标要求档位，承诺克制原则在本模式同样适用，禁止把「≥500 并发」承诺成「≥2000 并发」。
2. 但允许、且鼓励补充「实现路径说明」：即解释本项目通过何种架构、技术选型、部署方式、运维机制来满足该指标。扩展的是「为什么能满足」，不是「承诺更高的值」。
3. 招标未给值、事实块也没有的，写【待填写】或「按招标文件要求响应」。

二、主观方案展开幅度（本模式的主要扩展区）
4. 允许主动增设招标未明确要求但行业通行、且对本项目有实际价值的章节与内容，例如：总体架构设计与技术路线论证、系统集成与数据治理方案、数据安全与隐私保护体系、运维服务体系与 SLA 设计、培训体系与知识转移、持续改进与优化机制、同类项目业绩与实施经验、项目创新点与先进性说明等。
5. 新增章节必须与本项目实际需求相关，禁止为凑篇幅堆砌通用模板内容。

三、是否允许新增内容
6. 允许承诺层面的新增，但必须同时满足三条：
（1）与预算量级匹配——承诺的架构规模、技术选型、部署方式必须能在本项目预算内实现，禁止出现「预算 300-500 万却承诺双活数据中心 + K8s 容器云 + PB 级存储」这类量级失配；
（2）与医院等级规模匹配——承诺的并发量、存储容量、接口数量必须与该院等级、床位、门诊量自洽；
（3）可交付——承诺内容必须是本团队有能力实际交付的，禁止承诺无案例支撑的能力。

四、素材使用
7. 最大化使用知识库与自有资料：可大段组织同类案例、实施方法论、量化数据、制度文件作为支撑，引用处注明来源。
8. 禁止整段照抄，禁止编造素材中不存在的人员、业绩、资质与数据；素材与本项目规模不符时，只可取其方法与结构。

五、篇幅取向
9. 主观方案章篇幅可为严格模式的 1.5–2.5 倍；扩展应优先落在评分办法分值最高的维度上，分值低的维度不做过量展开。

六、偏离表目标
10. 允许正偏离，且应将真实的技术优势主动以正偏离形式在偏离表中标出，作为竞争优势呈现；但正偏离必须真实可交付，禁止虚构。
```

## 四、三模式共用的「防翻车约束块」（建议所有模式都注入）

这一块是**独立于模式**的，解决的是内容质量问题。你上次让我测出来的 P3 缺陷，几乎全部能被这六条拦住——建议无论如何都要加：

| 本次测试发现的 P3 问题 | 对应拦截条款 |
|---|---|
| RPO 写 0 / 又写 <1h，RTO 写 <30s / 又写 <4h，缺陷率 1% / 2% | **A 同一指标全篇唯一** |
| 约 12 处无依据量化承诺 | **B 量化承诺必须有依据** |
| 双活/K8s/PB 级存储配 300–500 万预算 | **C 规模量级自洽** |
| 仍引「2025 年前」、《2021–2025 年行动方案》 | **D 政策法规时效** |
| 错别字「三级甲院」、中英夹杂「data stewardship」 | **E 术语与文字规范** |
| 「13131医院」测试占位符进入正文 | **F 无占位符残留** |

```
【全文一致性与真实性硬约束（所有模式必须遵守）】

A. 同一指标全篇唯一：同一指标（如 RPO、RTO、系统可用性、响应时间、病历缺陷率、并发用户数）在全文中只能有一个取值，不得在不同章节出现不同数值。若前文已给值，本章必须沿用同一值；需要变更时必须全篇统一。

B. 量化承诺必须有依据：任何量化承诺（数值、比例、时限、容量、人数、金额）必须来自招标原文、事实块、团队自有资料三处之一。无依据的不得写出具体数值，改为定性表述或【待填写】。

C. 规模量级自洽：技术架构规模（是否双活、是否容器化、存储量级、服务器数量、网络带宽）必须与本项目预算金额、医院等级、床位规模三者自洽。出现量级失配时必须主动降级到与预算匹配的方案，不得为了显得先进而承诺超出预算能力的架构。

D. 政策法规时效：引用国家标准、政策文件、评价规范时必须使用现行有效版本。不确定是否现行有效的，只写标准名称不写年份，禁止引用已过期或被替代的文件。

E. 术语与文字规范：统一使用规范全称，首次出现给「全称（简称）」；禁止错别字（如「三级甲院」应为「三级甲等医院」）；中文正文中禁止夹用无必要的英文术语，行业通用缩写（HIS/EMR/LIS/PACS/CDR）除外。

F. 无占位符残留：正文中禁止出现测试占位符、临时编号、无意义数字串（如「13131医院」「3456」「XXX 项目」「测试项目」）。不确定的名称一律写【待填写】。
```

## 五、集成方案（落到代码）

### 5.1 数据类型：`GenOptions` 加一个字段

`bidTypes.ts` 约 1469 行，`GenOptions` 是 JSON 列，加字段向后兼容：

```ts
export type BidComplianceMode = "strict" | "moderate" | "full"

export const COMPLIANCE_MODE_LABEL: Record<BidComplianceMode, string> = {
  strict: "严格响应",
  moderate: "适度扩展",
  full: "全量扩展",
}

export const COMPLIANCE_MODE_HINT: Record<BidComplianceMode, string> = {
  strict: "技术参数逐字照抄，不新增任何承诺。履约风险最低，适合要求明确的项目",
  moderate: "技术参数仍逐字照抄，主观方案在招标要求范围内深化，篇幅约 +30%~50%",
  full: "允许主动增设章节与内容，篇幅 1.5~2.5 倍；技术参数仍不加码，且承诺必须与预算量级自洽",
}

export type GenOptions = {
  clause_response: boolean
  material_boost: boolean
  include_biz: boolean
  /** 新增：生成模式，缺列时默认 strict（存量项目自动落入最安全模式） */
  compliance_mode: BidComplianceMode
}

export function defaultGenOptions(): GenOptions {
  return { clause_response: false, material_boost: false, include_biz: true, compliance_mode: "strict" }
}

export function normalizeGenOptions(raw: unknown): GenOptions {
  const base = defaultGenOptions()
  if (!raw || typeof raw !== "object") return base
  const rec = raw as Record<string, unknown>
  const mode = rec.compliance_mode
  return {
    clause_response: rec.clause_response === true,
    material_boost: rec.material_boost === true,
    include_biz: rec.include_biz !== false,
    compliance_mode: mode === "moderate" || mode === "full" ? mode : "strict",
  }
}
```

### 5.4 大纲侧的差异（容易被漏掉）

模式不只影响正文，还影响**大纲骨架宽度**。现有大纲提示词的"技术部分常规骨架参考"是固定的八章（项目理解、总体建设方案、详细技术方案、实施组织与进度、质量保障与验收、培训方案、售后服务与运维、应急预案）。

建议改成按模式给不同骨架参考：

- **strict**：就用这八章，且强调"只保留招标明确要求的维度，招标未提的维度不设章"
- **moderate**：这八章 + "每个章的小节数按招标评分点数量决定，不额外加章"
- **full**：在这八章基础上，明确列出可增设的候选章（总体架构与技术路线、系统集成与数据治理、数据安全与隐私保护、运维服务与 SLA、知识转移与持续改进、同类项目业绩、项目创新点与先进性），并给"新增章必须与本项目相关"的约束

### 5.5 UI：`GenerationSettingsBar` 加模式选择器

建议放在最前面（在"目标页数"之前），作为首要决策，三选一卡片 + 每项一行说明：

```
生成模式
[ 严格响应 ]  [ 适度扩展 ]  [ 全量扩展 ]
技术参数逐字照抄，不新增任何承诺。履约风险最低，适合要求明确的项目
```

- strict → "技术参数将逐字照抄，不新增任何承诺"
- full → "将主动增设章节，篇幅约 1.5~2.5 倍；技术参数仍不加码"

### 5.6 字数预算联动

现有 `sectionWords`（每小节字数，默认 800）与 `targetPages` 是用户直设的。建议**不强制覆盖**，只在模式切换时给默认值：

| 模式 | 每小节字数建议 | 说明 |
|---|---|---|
| strict | 800 | 维持现状 |
| moderate | 1000 | +25% |
| full | 1400 | +75% |

实现方式：切换模式时若用户未手动改过 `sectionWords`（可用一个 `sectionWordsTouched` 标记），则跟随模式给默认值；改过则不动，只在 summary 里提示"当前每小节字数低于该模式建议值"。

## 六、方案侧（SolutionStudio）怎么套

方案侧没有"招标文件"这个锚点，所以模式轴要换一个说法——**"以医院需求为界，还是主动扩展"**：

| 模式 | 方案侧语义 |
|---|---|
| strict | 严格按已确认的建设清单与医院需求编写，不新增系统、不新增功能模块 |
| moderate | 需求项内深化（实施、集成、安全、培训细节），不新增系统清单 |
| full | 允许增设架构论证、技术路线、数据治理、运维体系、案例业绩等章节 |

`src/pages/SolutionStudio/solutionTypes.ts` 的 `buildChapterMessages`（451 行）与 `buildRefineMessages`（524 行）按同样方式注入。`SOL_STYLE_RULES` 保持不变。

> 方案侧建议**默认 moderate**（不是 strict）。原因：方案是给客户看的售前材料，不是投标应答文件，没有"加码=验收义务"的法律风险，过严会让方案显得单薄。

## 七、落地顺序建议

1. **第一步（低风险、见效快）**：先只加**防翻车块**（第四节），不动模式。这一块能直接消灭上次测试出的 6 类内容质量问题，且不改变任何现有交互。
2. **第二步**：加 `compliance_mode` 字段 + 严格模式提示词，默认 strict，UI 给三选一但 moderate/full 先标"beta"。
3. **第三步**：把模式注入到大纲、偏离表、模拟评标、覆盖审计，做到全链路口径一致。
4. **第四步**：方案侧同步。

## 八、一个待你确认的产品决策

模式三"允许承诺层面的新增"这条，是有真实业务风险的：**承诺了就要履约**。有两种处理方式，需要你定：

- **方案 A（推荐）**：全量扩展允许新增，但**所有新增承诺在生成后自动汇总成一份「新增承诺清单」**，交人工逐条确认后再定稿。这样既有内容厚度，又不会让销售在不知情的情况下把公司架上去。
- **方案 B**：全量扩展只允许"表达层面的扩展 + 增设章节"，**不允许任何新的可验收承诺**。最安全，但篇幅优势会打折扣。

这个决策会直接改变模式三第 6 条提示词的写法，建议先定下来再动手。
