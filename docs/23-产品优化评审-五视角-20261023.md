# 23-产品优化评审（五视角）· 2026-10-23

> 评审人立场：产品设计师 / 开发经理 / 医疗信息化售前 / 医院信息科（甲方）/ 评审专家。
> 依据：`pocketbase/pb_data/data.db` 只读盘点（32 个项目）、现有代码与测试基线（308 files / 3620 passed）、
> 以及 2026-10-21～23 这几轮真实项目实测。所有数字均为当场复算，不是引用旧审计稿。

---

## 零、一句话结论

**这个产品已经不缺"生成能力"，缺的是"把生成结果变成能交出去的投标文件"。**

数据上，用户走完了前 3 步（解析 → 大纲 → 正文），却在后 4 步（偏离表 / 废标检查 / 模拟评标 / 归档）几乎全部放弃；
而评审专家真正扣分和废标的地方，恰好就在后 4 步与正文质量上。继续加功能的边际收益已经很低，
**把"已经生成的东西"变成"可交付、可自检、可复盘"的东西**，是下一阶段唯一的主题。

## 一、硬数据：用户实际停在哪

| 环节 | 项目数 | 占比 |
|---|---|---|
| 有招标原文 | 31 / 32 | 97% |
| 有解析报告 | 31 / 32 | 97% |
| 有投标大纲 | 17 / 32 | 53% |
| 有正文 | 17 / 32 | 53% |
| 有技术偏离表 | 5 / 32 | **16%** |
| 有废标检查 | 2 / 32 | **6%** |
| 有查重报告 | 3 / 32 | **9%** |
| 有模拟评标 | 1 / 32 | **3%** |
| 有投标结果（中标/未中） | 0 / 32 | **0%** |

阶段分布：`pending_parse 9 / composing 20 / checking 2 / archived 1`。

三个补充事实：

1. **知识库是空转的**：17 个有正文的项目里，`material_boost`（素材优先注入）开启数 **0**。
   换句话说，知识库功能建了、文档也进了，但**从没进过任何一份正文**。
2. **★/▲ 条款深度响应默认关**：`clause_response` 只有 4/17 开着。实质性条款的逐条深度响应，绝大多数项目没启用。
3. **成稿质量离"真实交付"有明确差距**：真实中标《售后服务方案》段落中位 81.5 字、超 300 字占 0.7%；
   本库有正文的项目里，段落中位中位数 159 字，最差项目超 300 字占比 **57.9%**。

## 二、五个视角的判决

### 1. 产品设计师

- **7 步流水线是工程视角，不是用户任务视角。** 用户脑子里的任务是三件事：「这份标书要响应什么」「怎么写」「能不能交」。
  现在的 7 步把「查重 / 废标 / 评标 / 归档」拆成四个平级步骤，每一步都要单独点、单独花钱，于是没人走。
- **漏斗断在第 4 步，而产品没有任何机制把用户推过去。** 生成完正文就结束了，没有"离交卷还差什么"的清单。
- **主入口缺失。** 打开一个项目，最该看到的应该是「交卷倒计时 + 缺什么 + 下一步」，现在看到的是七个步骤的图标。
- **0% 的投标结果录入，意味着产品没有闭环。** 没有"哪类项目赢、哪类失分"的数据，下一代提示词只能靠猜。

### 2. 开发经理

- **`useBidWorkspace.ts` 10335 行 / 371 个返回句柄、`bidTypes.ts` 8555 行且是 barrel**，是最大的工程风险：
  任何一次改动的影响面都不可预判，这也是为什么每轮改动都要跑 3600+ 用例。
- **测试很多，但缺"端到端"**。308 个文件里，真正验证「上传 → 解析 → 大纲 → 正文 → 导出 docx」整条链的只有个别探针，
  而且是我临时写的、跑完就删。没有一条常驻的端到端快照，等于每次重构都在裸奔。
- **62 条提示词（标书模块 27 条）的维护成本已经超过收益**。这一轮实测里，同一个提示词口径要同步 3 处（源码、手册、分类手册），
  快照测试是唯一护栏。
- **上游数据质量是硬伤**：PDF 抽取丢 ★ 符号（某项目全文只有 11 行含 ★，10 行是裸的「★1」）、表格列错位。
  再好的提示词也救不回缺失的原文。

### 3. 医疗信息化售前（我自己干活时的视角）

- 售前交标书，卖的是**「响应质量 + 证据链」**：每个评分点后面必须挂得上截图、承诺函、合同、社保、证书。
  现在证据线是断的——正文里写「证明材料见【待填写】」，而没有任何一处把「评分点 → 材料 → 页码」串起来。
- **知识库 0 次注入**说明"素材"这件事在产品里是伪需求：不是不需要，是**没人有空先喂素材**。
  正确做法是反过来——从历史标书里自动抽素材（公司简介、案例、承诺函模板），而不是等用户上传。
- **★/▲ 条款是售前的命门**，而它在解析层经常是碎片（安中医 117 条里最长 35 字，全是目录页）。
  碎片化的 ★ 条款会一路传导到承诺函、技术参数响应表、正文 —— 这一条已经修了合并逻辑，但抽取源本身仍要盯。

### 4. 医院信息科（甲方视角）

- 甲方看技术标只看三件事：**你懂不懂我的现状、你能不能落地、出了事谁负责**。
  实测旧大纲对「第三章 定制软件开发清单」的 44 个子系统**覆盖率 0/44** —— 在甲方眼里这就是"没读我的文件"。
- **数据迁移、接口对接、驻场、维保**这四块是医院最在意的，也是标书里最容易写空话的地方。
  产品现在能解析出这些条款，但没有把它们组织成"可核对的实施承诺"。
- 甲方评标时会拿**技术参数表逐条对**。参数表必须是原文逐条、编号连续、证明材料可查——这轮修好了合并与越界，但要固化。

### 5. 评审专家视角（打分那 30 分钟）

- **评委是按评分表翻页的**：一个评分点找不到对应章节 = 直接丢分。这条产品已经解决（一级评分项一一对应成章 + 目录对照表）。
- **扣分点不在"有没有写"，在"写得实不实"**：量化指标、本项目特有信息、图表、证据编号。
- **演示 / 答辩类不该占章节**（已剔除）——评委看的是现场，不是标书里写"我们将演示…"。
- **废标项是零容忍**：资格、符合性、★负偏离、签章格式、电子标雷同。这块的检查产品有，但只有 6% 的项目跑过。

## 三、四个断层（诊断）

| 断层 | 表现 | 根因 |
|---|---|---|
| **交付断层** | 生成完就停，后 4 步 6%~16% | 后 4 步是"可选步骤"，没有交卷清单把它们串起来 |
| **证据断层** | 正文里【待填写】散落，无索引 | 没有材料台账，"评分点→材料→页码"没有载体 |
| **素材断层** | 知识库 0 次注入 | 需要用户先喂素材，而售前没这个时间 |
| **闭环断层** | 0% 投标结果 | 没有结果录入，无法反推"哪种写法能赢" |

## 四、优化路线（按可验收的最小批次）

### P0 · 把"能生成"变成"能交"（1~2 周）

1. **交卷清单（一键体检）**：正文生成结束自动串跑「偏离表 → 废标检查 → 查重 → 预评」，
   产出一张清单：已完成 / 未完成 / 阻断项（含原因与跳转）。**这是把后 4 步从"可选"变"默认"的唯一办法。**
   验收：任意有正文的项目，点一次就能得到清单，且清单上的每一项可点击直达。
2. **证据台账**：把正文与响应表里的【待填写】收敂成编号材料（M1、M2…），生成「评分点 → 材料编号 → 页码」索引，
   导出时附在技术标开头。验收：导出的 Word 里能查到"某评分点对应哪份材料"。
3. **素材默认开启 + 首次引导**：新项目默认开 `material_boost`；首次进入编制时提示"从历史标书/资质库一键导入素材"。
   验收：新项目生成正文时，`material_boost` 默认为 true 且有素材来源。
4. **正文质量门禁**：导出前校验段落中位 ≤120 字、超 300 字占比 ≤10%（对齐真实交付基准 81.5 / 0.7%），
   超标给"自动拆段"建议而不是硬拦。验收：最差项目（57.9%）导出前会提示并给出拆分后的预估。

### P1 · 产品结构（1 个月）

5. **7 步 → 3 视图**：`解析确认 / 编制 / 交卷`。7 步保留为内部状态，对外只暴露三个任务和一个倒计时。
6. **结果闭环**：交卷后录入"中标 / 未中标 + 失分点"，形成「评分点命中率」看板，反哺解析与写作。
7. **资信/业绩/人员库升为一等公民**：现在资质台账是独立模块，标书生成时靠人工复制；
   应做到"评分点提到团队/业绩/证书 → 自动带出可用的库内条目 + 有效期校验"。

### P2 · 工程与质量（1 个季度）

8. **God Hook 按域拆解**：先抽纯函数（解析后处理、检查规则、导出装配），不追求一次拆完。
9. **端到端回归网**：一个真实项目从上传到导出 docx 的产物快照（docx 解包后的 XML 摘要），
   每次改动比对差异。这是"改一处崩一处"的唯一解药。
10. **上游抽取**：★ 符号丢失、PDF 表格列错位——等真实 PDF 原件到手再做坐标聚类；在此之前，
    至少在界面上明示"本节抽取质量低，请人工核对"。

## 五、明确不建议做的

- **继续堆提示词**。62 条已经超过可维护边界，新增一条的成本是手册三处同步 + 快照重生成。
- **PDF 坐标聚类**（在没有原件样本的情况下）。做出来无法验证，等于赌。
- **对标易标做演示/资信库这类边缘功能**。你这轮已经证明：多数对标项你已有或不需要。
- **大改视觉**。当下瓶颈是流程与内容，不是好看。

## 六、附：评审专家视角的 10 条扣分自查（建议做成产品内置检查）

1. 每个评分项是否有且仅有一个对应章节，且章节名与评分项同名。
2. ★/▲ 条款是否逐条原文响应，且每条有证明材料编号。
3. 技术参数表是否逐条、编号连续、与招标原表行序一致。
4. 主观章节是否按「理解→思路→架构→措施→承诺」五段展开。
5. 每章是否有本项目特有信息（院区、系统、数据量、岗位），删掉项目名是否仍成立。
6. 量化承诺是否都有数字（可用性、响应时限、RTO/RPO、驻场人数）。
7. 付款、服务期、质保期、服务地点四项是否"完全响应"且无负偏离。
8. 电子标：CA 有效期、电子签章主体、加密上传、解密时限是否逐项核对。
9. 目录/页码/页眉页脚/字体字号是否与招标文件格式要求一致。
10. 全文是否无他项目残留、无占位符、无 AI 腔套话。

## 七、下一步（建议顺序）

1. 先做 **P0-1 交卷清单**：它是把 6% 变成 60% 的唯一杠杆，且不依赖任何模型改动。
2. 再做 **P0-2 证据台账**：它直接决定"专家能不能找到证明材料"。
3. 然后 **P0-4 正文质量门禁**：用真实交付基准倒逼写作提示词，而不是继续调提示词。
4. P1/P2 按季度排。**在拿到"中标/未中标"真实数据之前，不要做任何"智能推荐"类功能。**
