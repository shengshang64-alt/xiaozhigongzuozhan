## 二、R3 修的是什么（五项逐条）

R3 的共性不是「功能缺失」，而是**界面在说假话**。所以五项全部围绕「话要准、失败要留痕」：

### ① 模型配置 · 平台内置本地不可用必须标明（D4 点名）

**原状**：模型配置页「公共模型」卡写着「无需配置密钥，登录 RunningHub 账户后即可使用」，
且「设为默认」按钮**可点**。

**真因**（读 `pb_hooks/llm.pb.js` + `rhLogin.ts` 确认）：平台内置走 RunningHub 中转，令牌只来自
`x-rh-api-key` 头或 `RH_LLM_API_KEY`；本机域读不到 `Rh-Accesstoken`（cookie 属 runninghub.cn 域）、
项目里也没有 `/sso-popup-callback` 回跳路由 → **令牌恒空，必然 412**。

**后果**：用户把平台内置设为默认，之后每次生成都 412，而默认横幅仍写着它可用。这正是 D4 说的
「不得当默认成功路径」。

**已改**：
1. 新增 `src/lib/platformModelAvailability.ts` —— 判定收成一处（本地/内网域 + 存在个人通道）；
   边界沿用既有 `ModelSelect` 的口径（**只在一个个人通道都没有时不禁用**，否则退化成没有模型可选）。
2. `PlatformModelCard`：卡片头换成红字说明真因（不是假承诺）；每个模型行打「本地不可用」徽标；
   描述改成「本机运行时无法拿到登录态，调用必然失败——请改用下方个人模型」；
   **「设为默认」禁用**，title 给出真因。

### ② 方案工作室 · 自动保存不再静默冒充「已保存」

**原状**（`useSolutionStudio.persistSolution`）：

```ts
} catch {
  if (quiet) setAutoSaveState("idle")      // ← 失败也回 idle
  if (!quiet) toast.error("保存失败，请检查网络后重试")
}
```

`quiet` 是自动保存走的路径（不弹 toast）。于是**保存失败时界面从「保存中」直接消失**——
`ChapterEditor` 只在 state ≠ idle 时渲染，等于"看起来存好了"。用户刷新后正文丢失，全程零提示。

**已改**：
1. 新增 `failed` 档；失败时**常驻**「保存失败·未落库」红字，title 带服务端真实原因。
2. 本地 `apiFetch` 原来只抛 `HTTP ${status}`——服务端「字段超长 / 校验不通过」到界面上全变成
   「请检查网络」。改为读 body 走 `describePbError`，把真因保真到 `Error.message`（与标书侧 R56 同口径）。

### ③ 助手长答 · 分档提示 + 取消语义 + 不误报

**原状**：`ChatStream` 只有一个 30s 阈值和一句「长回答耗时较长；不想等可点取消」。三个数字散着：
网关 300s、客户端 330s、一轮最多 3 次调用（取数回填 2 轮 + 最终回答）——没有任何地方把它们关联起来。

**已改**：新增 `src/lib/longAnswerTiming.ts` 集中口径：
- 30s：说「仍在生成中」，给取消这条路，但**不催**；
- 60s：说明这轮可能要多次取数；
- 120s：按「接近上限」处理，给**可执行动作**（换更快的模型 / 拆成几步问）。
- `CANCEL_SEMANTICS_TEXT`：说清「已发出的那次调用撤不回」——旧界面只说「取消」，用户以为退钱。
- **措辞红线**：所有长答文案都不许出现「服务不可用 / 模型挂了」——慢 ≠ 挂，这是最常见误报来源。

### ④ 知识问答 · 真实语料命中率（把推断变成实测）

**原状**：M0 §1.2 的半残事实是「知识问答『有要点说找不到』」。`searchKbDocs` 是纯函数，
命中率完全取决于真实语料 + 真实问法——**合成夹具证明不了这件事**。

**已做**：新增 `src/pages/Knowledge/kbQaRealCorpus.test.ts`（只读打开 `data.db`，
读不到就 skip，与既有 `*RealDb.test.ts` 同口径）。**现场实测结果**：

```
语料：7004 篇含正文
✓ 文档编辑有什么规范要求        → 9 篇：首条《智业软件文档编辑使用规范 V2.1（全文）》
✓ 公司文档的字体字号怎么规定    → 7 篇
✓ 评审流程分几个阶段            → 9 篇
✓ 投标文件制作有哪些注意事项    → 10 篇
✓ 系统架构怎么描述              → 7 篇
✓ 数据备份多久做一次            → 6 篇
✓ 哪些情况需要走审批            → 8 篇
✓ 编制依据包括哪些标准          → 6 篇
命中率：8/8（100%）
```

**一个被实测推翻的假设要如实汇报**：我第一版写了「无关问题必须 0 命中」，跑出来**8 篇**
（分数低但确实有共同字）。这说明在 7000 篇标书语料上，「纯词面检索 0 命中」这个期望本身是错的。
现在断言改成**能不能区分强弱**（无关问题首条分数必须低于真实问法）——这才是「未命中 vs 真无资料」
可区分的技术基础，也是阶段 1 包 3 那条文案的前提。

### ⑤ 情报 · 关页即停要如实说 + 服务端计划任务试点

**原状**：抓取只在页面挂载/驻留时触发（每 15 分钟），关页即停。但文案写的是
「后台定时抓取为尽力而为」、空态写「可以等待下一轮自动抓取」——两句都暗示不关页面也会抓。

**真实代价**（只读查库实测）：40 个信息源里 **14 个 last_status=error**，其中「国家卫健委」连续失败
**15 次**、「中国政府采购网」连续 403 **15 次**。这类「长期失败」只有在**持续重试**下才看得出来是
「源死了」还是「今天抽风」——只靠开页面时抓一次，永远看不清。

**已改**：
1. 文案改为如实：`src/pages/IntelCenter/intelAutoFetchCopy.ts` —— 明说「本页打开期间抓取，
   关闭本页后停止」，并给出「关页也跑」的办法。**不再出现「后台」二字**（原句正是靠它误导）；
   跟踪 `visibilitychange`，页面不可见时如实说「已暂停，回到本页后会继续」。
2. 服务端试点：`scripts/health/intel-tick-timer.ps1` —— 计划任务载荷，调 `POST /api/intel/tick`，
   写 `pocketbase/logs/intel-tick-timer.log`。**已实测跑通**（`tick ok: no new items (checked 12/17)`）。
   注册命令写在脚本头注释里（`schtasks /Create ... /SC MINUTE /MO 30`，当前用户即可，不需管理员）。

**为什么用计划任务而不是 `cronAdd`**：本仓 `pb_hooks` 三处文件头（`intel_center` / `ai_hot` / `zx_guard`）
都写着「定时不用 cronAdd」的既有工程约束。计划任务是**仓外**动作：不改钩子、不需重启 :7000、
随时 `schtasks /Delete` 撤回，风险面最小。**这条我按既有约束走的，没有为了"服务端化"去改钩子。**
