1. **逻辑绝对闭环**：分支 100% 覆盖；边界值、空值、异常、并发、超时、非法入参逐一拦截；禁止静默失败、禁止未捕获异常、禁止 `if` 无 `else`、禁止省略兜底 `catch`。
2. **性能为实际最优**：杜绝冗余循环、重复计算、无效 IO、内存泄漏、全局变量滥用；循环体内禁止创建对象与查询；复杂度需注释标注；高频路径做分层缓存；并发场景做锁 / 限流 / 批处理。
3. **规范统一**：命名见名知意（禁止 `a`/`b`/`temp`/`data2` 这类无信息量命名）；魔法数字与固定字符串抽为常量；注释密度不低于每 10 行 1 行功能性注释（解释"为什么"，不解释"是什么"）。
4. **安全刚性**：防注入、防越权、参数过滤、数据脱敏、权限前置校验；外部输入强制清洗转义；敏感数据禁止明文存储 / 打印 / 传输；隐私数据禁止写日志；高危操作加二次确认开关。
5. **可维护可扩展**：单一职责；超长函数强制拆分；高耦合处解耦 + 依赖注入 + 抽象接口；业务规则配置化；每处改动标注**原因 / 影响范围 / 回滚方案**。

## 2. 你要重构的产品是什么

**一句话定位**：面向医疗信息化行业的 **AI 驱动的售前与投标全流程协作平台**——把"从一条情报线索，到一份能拿去投标的标书"这条链路，从散落在个人电脑里的 Word/Excel/微信，收敛成一个有数据、有护栏、有闭环的系统。

**解决的三个真问题**：
1. **投标是废标风险最高的环节**：★▲条款漏响应、资质过期、格式不合规，任何一处直接废标（不是扣分，是出局）。系统必须把"人的记忆力"替换成"机器的核对清单"。
2. **售前最高频的重复劳动是逐条响应**：一份招标文件 200 条技术要求，过去逐条手写、口径还不一致。系统要把"逐条手写"降级成"逐条确认"。
3. **知识与业绩没有沉淀**：方案、标书、技术材料散落在两万四千份文档里，每次投标重新翻找。系统要做的是"沉淀一次、复用百次"。

**使用规模基线**（用于容量与性能设计）：单部署 1 个售前团队（3–15 人）；知识库文档量级 1 万–3 万份；单份招标文件最大 9.2MB / 845 页 / 67.6 万字。

**当前部署形态**：单机自用（前端 `127.0.0.1:8000`，后端 `127.0.0.1:7000`）。重构必须**同时为"未来联网多人协作"预留能力**，但不得在未获授权时改变当前的单机部署契约。

## 5. 重构目标（To-Be 架构）

> 重构的总方针：**不是重写，是分层。** 保持业务行为 100% 等价，把"能跑的代码"变成"能维护十年的代码"。

### 5.1 目标一：模块化边界清晰（解决"万物耦合"）

**现状问题**：`bidTypes.ts`（370KB）反向依赖 `SolutionStudio/solutionTypes`；提示词构造器、类型定义、业务逻辑、文件 IO 混在一层。

**目标状态**：
```
src/
├─ features/<模块>/
│  ├─ domain/     纯业务规则（无 IO、无 React、可 100% 单测）
│  ├─ data/       数据访问（API 封装、缓存、序列化）
│  ├─ prompts/    提示词构造器（纯函数，与业务逻辑分离）
│  ├─ ui/         组件（展示与交互）
│  └─ index.ts    模块公开接口（唯一对外出口）
└─ shared/        跨模块共享（ui primitives、lib 内核、类型）
```
**硬性要求**：模块间**禁止深层路径互引**（如 `import ... from '../BidWorkspace/bidTypes'`），只能走 `features/<模块>/index.ts`。发现反向依赖必须在同一批内消除。

**收益**：单文件体积下降 ≥ 60%；模块可独立测试；新人能按目录定位代码。

### 5.2 目标二：提示词资产化（解决"提示词埋在代码里"）

**现状问题**：62 条 LLM 提示词构造器全部内嵌在 `bidTypes.ts` 等文件，改一句话要动 370KB 文件，且无法版本对比。

**目标状态**：提示词抽到 `features/<模块>/prompts/`，每个构造器一个文件，公共底座（真实性铁律、输出规范、防翻车块）独立成 `prompts/base/`。

**硬性要求**：
- 抽离是**纯搬家，逐个字符等价**，禁止"顺便优化措辞"（R2 红线）。
- 每条提示词携带版本号 `BID_PROMPT_VERSION`，便于回溯。
- 抽离过程必须有 **fixture 回归集**兜底（见 5.5）。

### 5.3 目标三：后端 CRUD 收敛（解决"36 份重复代码 + 并发丢字段"）

**现状问题**：36 个 `.pb.js` 各自手写 `find → set → save`；并发场景下"读整行-改-存整行"会丢字段。

**目标状态**：
- 抽出共享的 CRUD 工厂（`pocketbase/pb_hooks/_lib/crud.js`），统一处理：身份校验、归属校验（防 IDOR）、字段白名单、乐观锁（`updated` 版本比对）、审计日志。
- 每个集合 hook 只声明**差异部分**（路由名、字段白名单、特殊业务规则）。
- **注意**：`pb_hooks/` 下以 `_` 开头的文件被 PocketBase 视为共享库不注册路由，可用于放工厂。

**硬性要求**：抽取期间**集合 schema 一个字段都不能变**（R1）。

### 5.4 目标四：安全护栏补齐（解决"联网即高危"）

按 `02-SDD` 第 9 节的技术债清单，优先级从高到低：

| 序 | 事项 | 判定标准 |
|---|---|---|
| 1 | 下线或加门遗留 `/api/model_configs`，`api_key` 一律掩码 | 任何响应体不含完整密钥 |
| 2 | 写操作路由补归属校验（`zxIsOwner`），防 IDOR | 越权请求返回 403 |
| 3 | `personal` 可见性文档在**服务端**按调用者 uid 过滤 | 直调 API 读不到他人个人文档 |
| 4 | 高危路由（项目删除 / 模型配置写 / 知识库删除 / 导出）加 `role === "admin"` 判定 | viewer/editor 调用返回 403 |
| 5 | 成本确认下沉到网关库层，而非依赖页面自觉 | 任何 LLM 出站调用都经过确认 |

### 5.5 目标五：测试网建成（解决"零回归保护"）

**这是放开一切自动化重构的前提。** 没有它，任何重构都是赌博。

**目标状态（三层）**：

| 层 | 内容 | 覆盖目标 |
|---|---|---|
| L1 纯逻辑单测 | `domain/` 与 `lib/` 下所有纯函数 | 100%（分支覆盖） |
| L2 契约测试 | 前后端接口契约（请求/响应结构、错误码） | 全部自定义路由 |
| L3 fixture 回归 | 3 份历史招标文件的"金标准解析结果"，任何提示词变更跑 diff | 关键字段（★▲条款 / 废标项 / 评分办法）零漂移 |

**fixture 回归放行规则**：关键字段全部一致 → 放行；任一字段漂移 → 阻断并输出差异报告。

### 5.6 目标六：AI 能力层收口（解决"调用链散落"）

**目标状态**：所有 LLM 出站必须经过**唯一入口** `chatViaGateway`，且在网关内部统一处理：

```
业务调用
  → 模型解析（个人模型优先 → 平台内置兜底）
  → 成本确认（含预估金额与费用归属）
  → 参数注入（temperature 按任务性质、max_tokens、page 标签、signal）
  → 技能块注入（injectSkillBlock）
  → 出站（Idempotency-Key 防重复计费）
  → 响应解析（结构化输出容错链）
  → 缓存写入（仅 cacheable 任务）
  → 可观测（耗时 / token / 模型 / 成败）
```

**硬性要求**：
- **确定性任务必须 `temperature=0`**：解析、事实设定、JSON 修复、清单匹配、偏离表判定、废标判定、覆盖审计、查重复判、交卷体检。这是"同一输入两次跑出不同判定"的根因。
- 所有可中断操作（批量生成）必须接 `AbortController`，取消时在飞请求真正 abort，而非只在边界 break。
- 出站重试必须带幂等键，防 5xx 重试导致的重复计费。

### 5.7 目标七：UI 体验与一致性（解决"长表单按钮点不到"）

**目标状态**：
- 所有弹窗：`max-height: 94vh + overflow-y: auto`，底部操作区 `sticky`。
- 所有长表单：提交按钮可见（sticky footer），且必填项有即时校验反馈。
- 所有列表：区分"本页数"与"真实总数"（禁止把 `items.length` 当 `totalItems`），超出加载上限时显式标注 `N+`。
- 主指标可发现性：**用户 10 秒内能找到本页最该看的那个数字；主指标需要超过 1 次点击才能看到 = 设计缺陷。**
- 全部界面遵守 `02-SDD` 第 8 节的设计令牌，禁止硬编码颜色值。

## 6. 质量门禁（Definition of Done）

**每个改动批次必须全部通过，缺一不可：**

| 门禁 | 判据 | 不过怎么办 |
|---|---|---|
| G1 类型与构建 | `pnpm build` 零错误 | 立即修复，不得提交 |
| G2 静态检查 | `pnpm lint` 无**新增**错误（历史遗留单独列出） | 新增错误必修 |
| G3 单元测试 | `pnpm test` 全绿；新增逻辑必须有新测试 | 补测试 |
| G4 实机冒烟 | 涉及界面的：真实浏览器走查，控制台 0 error；涉及接口的：无 401/5xx、无脏数据、无重复创建 | 修复后重走 |
| G5 AI 输出质量 | 涉及 AI 的：至少跑 1 次真实生成，确认未跑偏、未幻觉、口径一致 | 回滚提示词改动 |
| G6 数据一致性 | 关键指标在各页面取值一致；接口返回与界面显示一致 | 定位单一口径真相源 |
| G7 fixture 回归 | 触及提示词的：3 份 fixture 关键字段零漂移 | 阻断放行 |
| G8 可回滚 | 每批改动独立可回滚；改动前有原始内容快照 | 先补快照再动手 |

**诚实原则（不可违反）**：
- 构建失败、验证未通过、没测到 —— **如实写入报告，禁止粉饰**。
- 严格区分"改动前就存在的失败"与"改动引入的失败"，前者单独列出。
- **严禁在没有验证的情况下写"已修复"**。不把"没做"写成"已做"，不把"计划做"写成"已完成"。

## 7. 工作流 SOP（每轮循环）

**一轮只做一件事。** 改完立即验证，禁止一次改一堆导致无法归因。

```
① 读状态 ──→ ② 发现 ──→ ③ 选题 ──→ ④ 取证 ──→ ⑤ 定位
                                                    ↓
⑨ 记账 ←── ⑧ 验证 ←── ⑦ 改造 ←── ⑥ 放行判断 ←──────┘
```

**① 读状态**：开工先读三处，合并出候选池——
- `.loop/ledger.json`（主账本：round / backlog / closed / noProgressStreak）
- `.loop/MORNING.md` + `.loop/reports/`（最近轮次的结论与未结项）
- `docs/` 下未落地的需求（`05` 三模式设计、`06` 功能缺口、`09` 重构建议）

**② 发现**（至少跑前三条）：待办池 → 构建与静态检查 → 代码考古（`grep -rn "TODO\|FIXME\|HACK" src/`；`grep -rn ": any" src/`；找"有 UI 无逻辑 / 有字段无引用 / 有函数无调用"三类半成品）→ 实机走查 → 数据口径核对 → 性能测量 → 需求侧对照。

**③ 选题**：取**一个**优先级最高项作为本轮唯一目标，并归类：

| 级别 | 判据 |
|---|---|
| **S0** | 数据错误 / 安全 / 资金 / 废标级 |
| **S1** | 功能跑不通：报错、白屏、点了没反应 |
| **S2** | 用户每天遇到的体验断点 |
| **S3** | 可量化的性能问题 |
| **S4** | 与已有能力直接衔接的缺口 |
| **S5** | 代码健康：死代码、重复逻辑、类型漏洞 |

优先级公式：**严重度 > 出现频次 > 改动性价比**

**④ 取证**：实机或接口确认问题真实存在，留下证据（截图路径 / 实测数字 / 接口返回原文）。**禁止基于"代码看起来有问题"就直接改。**

**⑤ 定位**：定位到具体文件与行号；给出**最小改动方案**；评估对既有数据的影响。

**⑥ 放行判断**（三类工作，门不同）：

| 类 | 范围 | 放行 |
|---|---|---|
| **A 类 · 修** | 确定的缺陷：构建报错、4xx/5xx、逻辑错误、数据不一致、样式破损 | 自动执行，做完报告 |
| **B 类 · 优化** | 不改产品行为的提升：性能、文案、可发现性、一致性、无障碍 | 自动执行，但必须报告"改前 / 改后" |
| **C 类 · 升级** | 新增能力、新增数据模型、新增页面、改交互范式 | **先写一页方案，等用户点头后才动手。本轮任务就是"写方案 + 等确认"** |

触碰第 4 节任一红线 → 一律按 C 类处理。

**⑦ 改造**：最小改动；风格与周边一致；只动本项范围内的代码；不留调试残留。

**⑧ 验证**：G1–G8 全跑，做 before / after 对比。验证不过 → **先回滚，再重新分析**，禁止在失败状态上叠加改动。

**⑨ 记账**：更新 `.loop/ledger.json`；写本轮报告（格式见第 10 节）。

**角色轮换（避免连续多轮只发现同一类问题）**：

| 轮次 mod 6 | 主导视角 | 关注 |
|---|---|---|
| 0 | 售前工程师 | 能不能帮我拿下项目 |
| 1 | 产品经理 | 是否更有价值而非更复杂 |
| 2 | 测试工程师 | 边界、异常、数据一致性 |
| 3 | 医院信息科 | 客户看这界面会不会觉得不专业 |
| 4 | 评标专家 | 输出内容是否经得起评审 |
| 5 | 商务 / 财务 | 报价、成本、合规风险 |

**镜头同时轮换**：流程通断 → 功能正确 → 界面习惯 → 交互反馈 → 内容质量 → 性能 → 数据一致性

## 8. 分批重构路线图

> 原则：**先止血 → 再抽离 → 再收敛 → 最后重构**。任何一批都必须独立可验证、可回滚。
> 每批 ≤ 10 项。明细见 `03-开发文档-EDD.md` 第 6 节。

| 批次 | 主题 | 核心内容 | 完成标志 |
|---|---|---|---|
| **第 1 批** | **安全止血** | 密钥掩码、IDOR 归属校验、个人文档服务端过滤、高危路由角色判定、判定类任务补 `temperature=0`、批量停止接 AbortController、长表单 / 弹窗可达性 | 越权请求返回 403；同一输入两次判定结果一致；解析配置弹窗在 883px 视口下按钮可点 |
| **第 2 批** | **口径一致** | 成本确认下沉网关层、数据口径统一（`totalItems` / 首页客户数）、模式块扩段、下游判定器透传 `compliance_mode`、缓存事务修复 | 全部 LLM 出站均经确认；同一指标全站单一取值 |
| **第 3 批** | **回归基线** | vitest 骨架补齐、3 份招标文件 fixture 金标准集、契约测试、`.loop` 台账对账机制、Windows 可跑的 health-loop | fixture 全绿；台账与代码现状一致 |
| **第 4 批** | **模块分层** | 提示词抽离 `prompts/`、消除反向依赖、`features/` 目录迁移、模块公开接口（`index.ts`） | `bidTypes.ts` 体积下降 ≥ 60%；模块可独立测试 |
| **第 5 批** | **后端收敛** | CRUD 工厂 + 乐观锁、schema 版本化迁移、知识库按需加载（轻量字段列表 + 单篇取正文） | 36 个 hook 中重复代码消除；换机器可复现 schema |

**收敛与停止条件**（满足任一即出总报告，停止自动推进）：
- 待办池未关闭项全部清零
- 连续 3 轮无可推进项
- 剩余全部为 C 类（需用户拍板的新功能）→ 汇总成建议清单交还用户
- 达到用户设定轮数上限或用户打断

**关于"找不到事做"**：待办池清空时，**不要为了显得有进展而发明工作**（无意义重构、改注释、换变量名）。正确做法是回到 ② 的七条发现通道重扫；仍无 → 出总报告，明确说"当前已收敛，需要新需求输入"。

**关于重复**：已关闭项不得重开，除非有**新证据**（须在报告中写明）；被用户否决过的项，不得在无新理由时再次提出。

## 11. 反模式清单（本项目已验证的错误做法，禁止重犯）

| # | 反模式 | 正确做法 |
|---|---|---|
| 1 | 台账标 `done` 但代码里没有对应改动（"done 注水"） | 每轮开工强制对账：open 项描述与代码现状不符 → 先修台账，再动手 |

| 12 | 修改提示词措辞时不跑 fixture 回归 | 触及提示词 → 必跑 fixture diff（G7） |

## 附录 B · 术语表

| 术语 | 含义 |
|---|---|
| **★ / ▲ 条款** | 招标文件中的实质性要求标记。★ 通常为否决项（不满足即废标），▲ 为重要参数 |
| **废标项 / 否决项** | 不满足即导致投标被否决的条款，最高优先级 |
| **偏离表** | 技术响应偏离表，逐条声明"完全响应 / 部分响应 / 偏离" |
| **暗标** | 匿名评审形式，要求文件中不得出现投标人身份信息 |
| **三档合规模式** | `strict`（严格对标响应）/ `moderate`（适度场景扩展）/ `full`（架构补充）。**参数边界在所有模式下均不放宽** |
| **反幻觉铁律** | 提示词公共底座：找不到依据必须如实标注缺项，禁止编造分值、金额、业绩 |
| **评分映射** | 招标评分项 ↔ 响应章节的双向映射（`[响应:Rx]` 承接标记） |
| **交卷闸门** | 5 个流程闸门（parse/outline/compose/check/eval），留痕不拦导航，但**拦导出** |
| **弹药库** | 已审核通过的问答对（QA Pair），命中可零 AI 成本直答 |
| **知识缺口** | 检索 0 命中自动入队的问题，待人工补答后反哺弹药库 |
| **fixture 回归** | 用历史招标文件的金标准解析结果做基线，比对提示词改动前后的输出差异 |
| **fixture / 金标准** | 人工确认过的正确解析结果，作为验收基准 |
