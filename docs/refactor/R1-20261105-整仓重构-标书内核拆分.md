## 二、职责边界图（拆之前先画）

`useBidWorkspace.ts` 实测 **10,908 行 / 553 KB**。按职责分成五层：

```
┌─────────────────────────────────────────────────────────────┐
│ ⑤ UI 编排层（useBidWorkspace 本体，仍是巨型 hook）            │
│    登录态 / 模型选择 / 七步流程状态 / 各步 useCallback          │
├─────────────────────────────────────────────────────────────┤
│ ④ 领域动作层（模块内普通 async 函数，非 hook）                  │
│    llmGenerate / parseSectionVia* / runEval*Call / generate*   │
│    ← 依赖模块级可变状态（activeModelRef / persistChain 等）     │
├─────────────────────────────────────────────────────────────┤
│ ③ 记录层（库列归一化 + 本地草稿）        ★ 本轮已拆出            │
│    asArrayField / normalizeRecord / sortOppsByHospital         │
│    readOutlineDraft / writeOutlineDraft / clearOutlineDraft    │
├─────────────────────────────────────────────────────────────┤
│ ② 正文取数层（"正文到底取哪一份"的确定性口径）★ 本轮已拆出      │
│    resolveBidText / bidChaptersFor / isExternalBid             │
│    chaptersToTextStub / auditLeafExcerpt / mapClausesToChapters│
├─────────────────────────────────────────────────────────────┤
│ ① 纯函数内核（早已在独立文件里）                                │
│    bidTypes / bidProseLinter / parseSchemas / outlineDraft …   │
│    （全仓 200+ 个同目录模块，已可直接单测）                      │
└─────────────────────────────────────────────────────────────┘
```

**本轮只动 ② ③ 两层**，因为它们的特征是「零 React、零 AI、零 hook 状态」——
搬出去不会改变任何调用时序与闭包语义，是行为守恒风险最低的一刀。

**本轮刻意不动**：④ 领域动作层。它依赖 11 个模块级可变变量
（`activeModelRef` / `activeAutoMode` / `activeRoleMap` / `persistChain` /
`scoringTruncationSink` / `kbEmptyHintShown` 等），这些变量由 hook 内的
`useMemo`/`useEffect` 异步同步。要拆它必须先设计「依赖注入 + 生命周期归属」，
那是 R4「巨型页面 hook 再拆一轮」的活，不是 R1 该冒险的地方。

## 四、R1 回归网设计（为什么这 23 例值得留）

拆分的真实风险不是"新模块写错"，而是**接线悄悄变了**——本仓历史上反复踩过
「同一个数字两处算法」。所以测试按风险来钉，不按覆盖率来凑：

| 组 | 钉什么 | 例数 |
|---|---|---|
| ① 导出 API 兼容 | `hook.resolveBidText === body.resolveBidText`（**同一引用**，不是两份拷贝） | 2 |
| ② 库列归一 | 只有 id 的最小记录 / JSON 列存成 `''`（归档页白屏事故值）/ 数组原样保留 / 越界回落 / 合法值不误伤 | 5 |
| ② 草稿留档 | 写入读回 / 项目互不串味 / 清掉不复活 / 空 id 视为无草稿 / localStorage 抛异常不连累编辑 | 5 |
| ③ 正文双模式 | internal 取章节 / external 取全文 / external 空全文不造假章 / 老数据缺列容错 internal | 4 |
| ③ 条款归章 | 命中归技术章、商务章不承接 / 无 coverage 相似度兜底 / 空输入不抛错 / 每章 ≤15 条 | 4 |
| ③ 节摘录 | 取到目标节且不含别的小节 / 缺章节返回空串 / 标题为空按 max 截断 | 3 |

**反证（证明测试真的能抓住缺陷）**：把 `bidRecord.ts` 里
`bid_chapters: asArrayField(rec.bid_chapters)` 临时改回 `(rec.bid_chapters ?? [])`
（即撤销 2026-10-27 那次白屏修复）→ `1 failed | 22 passed`，
失败项正是「JSON 列存成空字符串时归一为 []」。还原后 23/23 全绿。
