## 1. 产品概述

### 1.1 行业背景

医疗信息化（HIT）行业的售前工作有三个结构性特征：

1. **决策链长、周期长**：一个医院信息化项目从采购意向到开标通常 6–18 个月，涉及院领导、信息科、临床科室、财务、招标代理多轮博弈。
2. **交付物重、容错率零**：投标文件是法律级交付物。★▲条款漏响应、资质证书过期、格式不合规、密封标记错误——任何一处直接导致废标（出局，不是扣分）。技术评分方案里的量化指标（RPO/RTO/可用性/并发数）若全文自相矛盾，会被评标专家直接判定响应不实。
3. **知识复用率极低**：方案、标书、技术材料在团队内沉淀为海量文档，但每次投标仍需人工重新翻找、重新撰写、重新校对，且不同人写出的口径不一致。

### 1.2 产品定位

**AI 驱动的医疗信息化售前与投标全流程协作平台。**

把"从一条情报线索，到一份能拿去投标的标书"这条链路，从散落在个人电脑里的 Word / Excel / 微信聊天记录，收敛成一个**有数据、有护栏、有闭环**的系统。

### 1.3 价值主张

| 对象 | 价值 |
|---|---|
| 售前工程师 | 逐条手写 200 项技术响应 → 逐条确认；方案初稿从 3 天 → 3 小时 |
| 售前负责人 | 团队知识资产沉淀在系统里而非个人电脑里；中标率、失单原因可量化复盘 |
| 标书专员 | 废标风险清单化、格式合规可校验、交卷前有体检 |
| 团队管理者 | 项目进度、商机漏斗、模型成本可见 |

### 1.4 现状与规模基线

| 项 | 值 |
|---|---|
| 使用规模 | 单部署 1 个售前团队（3–15 人） |
| 知识库量级 | 1 万 – 3 万份文档（docx / pdf / pptx / xlsx / md） |
| 单份招标文件 | 最大实测 9.2MB / 845 页 / 67.6 万字 / 解析为 63 段 |
| 部署形态 | 单机（前端 8000 / 后端 7000）；需为联网多人协作预留能力 |
| AI 提示词资产 | 62 条构造器（10 个模块，公共底座 11 条） |

## 2. 用户角色与权限

### 2.1 业务角色

| 角色 | 核心任务 | 高频动作 |
|---|---|---|
| **售前工程师**（主要用户） | 跟进商机、编制方案、响应招标 | 情报浏览、方案编制、技术响应、报价 |
| **投标 / 标书专员** | 生产投标文件、控废标风险 | 招标解析、大纲编制、查重、废标自查、交卷体检 |
| **售前负责人** | 决策投哪个标、看整体进展 | 工作台驾驶舱、商机看板、胜负复盘 |
| **商务 / 财务** | 报价、成本、合规 | 报价单编制、折扣审批、保证金 |
| **医院信息科**（外部视角） | 审阅方案与标书 | 关注专业度、指标一致性 |
| **评标专家**（外部视角） | 评审投标文件 | 关注实质性响应、量化依据 |

### 2.2 系统权限（技术角色）

| 角色 | 权限 | 约束 |
|---|---|---|
| `admin` 管理员 | 全部操作 + 团队成员管理 | 团队管理入口仅本地域 + admin 可见 |
| `editor` 编辑 | 业务数据读写，不能管理成员 | — |
| `viewer` 只读 | 仅读取 | 写接口服务端返回 403，前端禁用并提示 |

**双重身份模型**：

| 身份 | 作用 |
|---|---|
| 业务数据身份（`X-Rh-User-Id`） | 决定数据归属与个人可见性。本地部署固定为 `local-user`，形成共享数据池 |
| 团队身份（`Authorization: Bearer <token>`） | 服务端鉴权与角色判定 |

数据可见性规则：
- **团队内容**：全员可见
- **个人信息 / 个人源 / 个人笔记 / 未公开手动录入**：仅创建者本人可见（**须在服务端过滤，不能只在前端隔离**）
- **确认 / 忽略 / 收藏**：每人独立状态

## 3. 核心业务链路

系统的价值不体现在单个模块，而体现在三条打通的主链路上。**重构必须保证这三条链路端到端不中断。**

### 链路 A · 项目获取到投标交付（主链路）

```
情报中心（采购意向/招标公告）
   ↓ 一键转商机 / 建标书任务
客户管理（商机建档、阶段流转、跟进记录）
   ↓ opportunity_id 关联
方案工作室（建设清单 → 大纲 → 逐章正文 → 导出 Word）
   ↓ solution_id 关联
PPT 与报价（演示文稿 + 报价单）
   ↓
标书工作台（招标解析 → 大纲 → 编制 → 查重 → 废标自查 → 模拟评标 → 归档导出）
   ↓
结果登记（中标/失单 + 金额 + 结构化失单原因）
   ↓ 回流
工作台首页（中标率、失单原因 Pareto、业绩沉淀）
```

**断链点（当前已知）**：
- 调研（需求发现）→ 方案：**断开**（无需求调研工具，见 7.1 缺口 7）
- 资质/业绩台账 → 标书响应：**断开**（无结构化台账，见 7.1 缺口 1、4）

### 链路 B · 知识资产沉淀到复用

```
上传文档（单文件 / 整目录，保留目录结构）
   ↓ 解析（docx/pdf/pptx/xlsx/md/txt）→ 摘要 + 关键词 + 分块索引
知识库（团队库 / 个人笔记双库 + 七档分类 + AI 策略）
   ↓ 检索（本地 BM25，TopN=5）
问答（命中弹药库 → 零成本直答；未命中 → RAG 拼上下文 → 带引用作答）
   ↓ 0 命中
知识缺口队列 → 人工补答 → 反哺弹药库
   ↓
标书 / 方案 / 助手 引用（带来源标注）
```

### 链路 C · 情报驱动商机

```
定时抓取（四类源：政策 / 竞品 / 招标 / 媒体，每 30 分钟）
   ↓ 清洗（剥离噪声行、HTML 实体解码）
   ↓ 去重（服务端）
情报条目 → AI 摘要打标（≤120 字售前视角 + 自动判定类型/地区/标签）
   ↓ 人工确认 / 忽略 / 收藏
   ↓ 一键转商机（抽取金额、医院名，生成深链 ?new_opp=1）
客户管理（预填商机）
```

### FR-03 标书工作台（`/bid-workspace`）· **核心模块**

**目标**：投标全流程流水线，把废标风险从"依赖人的记忆"变成"系统的核对清单"。

#### 主流程（7 步）

| 步骤 | 名称 | 准入条件 |
|---|---|---|
| 1 | 招标文件 | 上传或粘贴招标原文 |
| 2 | AI 解析报告 | 已有招标文本 |
| 3 | 投标文件编制 | 已有解析报告 |
| 4 | 标书查重 | 已有 ≥1 章正文 |
| 5 | 废标项检查 | 已有 ≥1 章正文 |
| 6 | 模拟评标 | 已有查重或废标报告 |
| 7 | 归档导出 | 无准入限制（但受交卷闸门约束） |

**交卷闸门**：5 个闸门（parse / outline / compose / check / eval）。闸门**只留痕、不拦导航**，但**拦导出**。未满足闸门强制放行需必填备注。

#### FR-03-1 招标解析

| 编号 | 功能 | 优先级 | 业务规则 |
|---|---|---|---|
| FR-03-01 | 招标文件导入 | P0 | 支持 `.docx`（mammoth）/ `.pdf`（pdfjs-dist）/ `.txt` / `.md`，拖拽 + 点击。**全程浏览器本地解析，不上传原文件**。另有两个独立文本槽：历史范本、团队写作资料 |
| FR-03-02 | 解析范围配置 | P0 | 关键项 6 项必选 + 全量可选；其他项三态复选；★▲重点条款本地扫描开关 |
| FR-03-03 | AI 分段解析 | P0 | 分块逐段调用，`temperature=0`。输出 7 大分区 |
| FR-03-04 | 解析报告阅读与修订 | P0 | 分区阅读、人工修订、单项重解析、重点条款重扫 |

| FR-03-07 | 合规矩阵 | P0 | 四类条款覆盖状态追踪：★▲条款 / 废标项 / 资格要求 / 符合性检查。状态：open / covered / na |
| FR-03-08 | **反幻觉护栏** | P0 | 找不到依据必须**如实标注缺项**，禁止编造分值、金额、业绩。实测已通过 |
| FR-03-09 | 重点条款本地扫描 | P1 | 本地正则扫描 ★▲ 标记，与 AI 结果交叉验证 |

## 7. 功能缺口与二期规划

### 7.1 已识别的功能缺口（按价值排序）

| # | 缺口 | 痛点 | 价值 | 工作量 |
|---|---|---|---|---|
| 1 | **资质与人员证书台账**（含到期预警） | 证书过期 = 直接废标；现状靠投标前临时找行政要材料 | 拦废标级事故 | 低（几十条数据） |
| 2 | **产品功能点矩阵库** | 技术参数逐条响应的支持程度（原生/配置/定制/不支持）口径不一致，评标被抓住即响应不实 | 把"逐条手写"变"逐条确认"，根治口径矛盾 | 中（难点在数据整理） |
| 3 | **倾向性 / 排他性参数识别** | 判断标的是否内定、是否值得投、有无质疑点，现全靠个人经验 | 决策级信息 | 极低（一个提示词 + 一个面板） |
| 4 | **业绩合同台账 + 同类业绩自动匹配** | 同类业绩是硬评分项（5–15 分），现靠人翻历史合同 | 直接得分 | 中 |
| 5 | **成本-毛利-折扣测算** | "最低能到多少"算不出，要么报高丢标要么报低亏本 | 资金安全 | 中 |
| 6 | **采购意向监测**（第 5 类情报源） | 招标公告挂网时项目已跟了大半年；意向公开早 30–90 天 | 最早介入时点 | 中 |
| 7 | **需求调研工具** | 拜访回来一堆录音照片笔记，纯手工整理；调研→方案链路断开 | 打通链路 | 中 |
| 8 | **投标日历 + 保证金台账** | 跨项目投标节点视图缺失；错过截止不可挽回 | 防不可逆事故 | 中 |
| 9 | **全文一致性检查器** | 实测发现同一文档指标自相矛盾（RPO 写 0 又写 <1h） | 评标级风险 | 中 |

**共性判断**：第 1、4 项本质同一类——**结构化台账 + 到期/条件匹配 + 投标时自动调用**。建议用**一套通用台账框架**承载，避免做三个独立模块。

**配套判断**：第 2 项（功能点库）解决"支持程度口径统一"，第 9 项（一致性检查器）解决"生成结果口径统一"。两者配套才能根治"同一功能在不同项目里说法不一致"。

## 8. 验收口径（可量化）

### 8.1 四维验收标准

| 维度 | 判据 |
|---|---|
| **A 功能流程** | 三条主链路端到端可走通，无阻断步骤；所有按钮点击有反馈 |
| **B 排版布局** | 无元素溢出 / 遮挡 / 叠字；关键按钮在 883px 视口下可达；主题令牌统一，无硬编码色 |

| **D AI 内容质量与合规** | 反幻觉通过；量化指标全文唯一且有出处；三模式口径一致；成本确认无遗漏 |

信息架构与交互密度对标：**Stripe / Linear / Datadog / Intercom / Mixpanel / Salesforce / HubSpot**。

**核心一句话标准**：
> 新用户 10 秒内能否找到"这页最该看的那个数字"；主指标需要超过 1 次点击才能看到 = 设计缺陷。
