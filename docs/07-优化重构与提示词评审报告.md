## 0. 结论速览

**一句话结论**：这是一个**功能完成度远超平均水准**的产品——标书全链路（解析→大纲→编制→偏离表→评标→覆盖审计→查重→废标自查→讲标→定稿）几乎没有短板，提示词工程也已经有相当成熟的约束体系。真正的风险不在"功能缺什么"，而在**三处结构性欠账**：

| # | 结构性欠账 | 一句话说明 | 严重度 |
|---|---|---|---|
| 1 | **数据层**：整份标书存在**单个 JSON 列**里 | `bid_projects.bid_chapters` 一个 json 列装全文，每次保存整块重写；并发写会丢字段 | 🔴 高 |

## 2. 优化项（按优先级）

### 2.1 P0 · 必须做

#### P0-1 知识库 6,000 条硬上限（账本 `kb-cap-01`）

- **证据**：`src/lib/kbCore.ts` `MAX_PAGES = 30` × `perPage = 200` = 6,000 硬上限。库内 6,423 篇 → **423 篇静默不可见**；首屏加载实测 **40–61 秒**。
- **影响**：数据静默丢失 + 性能问题，两个 S0/S3 级问题叠在一起。
- **建议**：目录树改**按文件夹懒加载**（只在展开时拉该文件夹），列表改**服务端分页 + 虚拟滚动**。这是唯一一个"数据正确性"级别的优化项。

#### P0-2 业务数据所有权仅凭可伪造请求头（账本 `B-10`）

- **证据**：`pocketbase/pb_hooks/*.pb.js` 的鉴权只读 `X-Rh-User-Id` 请求头（客户端可控）。例：`solutions.pb.js:214` PATCH 路由。
- **现状缓解**：服务只监听 `127.0.0.1`，外部不可达，**风险当前可控**。
- **建议**：一旦要多人/局域网部署，**必须先修**——把 `X-Rh-User-Id` 换成由 `Authorization: Bearer <teamToken>` 在服务端解出的用户身份。这是一行部署配置就能从"可控"变"不可控"的问题，建议提前排。

#### P0-3 提示词层缺 `docs/05 §2` 的防废标判定表

- **证据**：全库搜 `响应性包装` / `实质性变更` → **零命中**；`buildBidChapterMessages` 里只有 `bidTypes.ts:3648` 一句「技术参数忠实：…逐字照抄…」。

## 3. 重构建议

### 3.1 唯一现在就该动的重构：**提示词从 `bidTypes.ts` 抽离**

**为什么这是第一优先**

| 判据 | 说明 |
|---|---|
| 收益大 | 35 个提示词构造器 + 15 条 `BID_STYLE_RULES` + 3 条 `FULLTEXT_GUARD_RULES` + 6 条模式规则全部混在 6,344 行的类型文件里。**改一句提示词要在 6 千行里定位**，无法 review、无法 diff、无法回归 |
| 风险低 | **纯搬迁，零行为变更**——不改任何提示词文本、不改调用点签名（用 re-export 保持兼容） |
| 可验证 | 搬迁后 `git diff` 只应有「删除 + 新增」，无逻辑变化；`tsc -b` exit 0 即可证明等价 |
| 不触红线 | 你自己的红线写的是"**重构 `bidTypes.ts` / `useBidWorkspace.ts` 的结构**"——**这里建议的不是重构结构，而是"把提示词搬出去"**，属于"拆文件"不是"改结构"。请按你的红线判断，我倾向认为这属于可放行范围，但仍建议你先点头 |

**建议目标结构**

```
src/pages/BidWorkspace/
  bidTypes.ts              ← 只留类型 + 纯函数（预计 6344 → ~4200 行）
  prompts/
    index.ts               ← 统一导出（保持对 useBidWorkspace 的 import 路径兼容）
    shared.ts              ← BID_STYLE_RULES / FULLTEXT_GUARD_RULES / 模式规则
    parse.ts               ← buildTenderParseMessages
    outline.ts             ← buildBidOutlineMessages / buildOutlineLevel1Messages / buildOutlineChildrenMessages / buildOutlineFixMessages
    compose.ts             ← buildBidChapterMessages / buildBidSectionMessages / buildBidContinueMessages / buildBidRefineMessages / buildSectionResizeMessages
    checkers.ts            ← buildDeviationMapMessages / buildVoidCheckMessages / buildEvalMessages / buildSubmissionCheckMessages / buildCoverageAuditMessages / buildDupJudgeMessages
    facts.ts               ← buildFactSettingsMessages / buildFactCheckMessages / buildFactPatchMessages
    defense.ts             ← buildDefenseQuestionsMessages / buildDefenseAnswerMessages / buildDefenseOutlineMessages / buildSpeechNotesMessages
    system.ts              ← buildJsonRepairMessages / buildOrchestrationMessages
```

**顺带解决三件事**
1. **提示词版本化**：`shared.ts` 顶部加 `export const PROMPT_VERSION = "2026-09-22.1"`，随生成内容一起落库 → 以后"这份标书是哪版提示词生成的"可追溯（现在**不可追溯**）。
2. **提示词可测试**：抽离后可以写单元测试断言"严格模式必须包含 X 条规则、不得包含 Y"——现在无法测。
3. **跨模块复用**：方案侧 `solutionTypes.ts` 的 `SOL_STYLE_RULES` 与标书侧规则有大量同构内容（反 AI 腔/元话语禁令/排版惯例/防编造占位**几乎逐字相同**）。抽离后可以提到 `src/lib/promptShared.ts` 共用，**消灭双份维护**。

> **附带发现（建议一并处理）**：`bidTypes.ts:2` 从 `@/pages/SolutionStudio/solutionTypes` 导入 `Chapter` / `FigureSpec` / `OutlineNode`——**标书模块依赖方案模块的类型**。这是"共享领域类型放在了页面模块里"。抽离提示词时顺手把这三个类型提到 `src/lib/domainTypes.ts`，可以解掉这条跨模块耦合。

### 3.2 数据层重构：整份标书拆出 JSON 列

**现状**：`bid_projects` 有 **17 个 json 列**（`ai_review` `bid_chapters` `bid_defense` `bid_outline` `compilation_basis_extra` `dup_report` `format_check_items` `format_settings` `gen_options` `manual_review` `orchestration` `parse_config` `parse_report` `response_map` `stage_gates` `submission_check` `void_check`），其中 `bid_chapters` 装**全部章节正文**。

**问题**：
- 每次保存序列化整份文档；23 章项目每次 autosave 都是数百 KB 级写
- 与 P1-1 的 read-modify-write 叠加 → **并发编辑必然互相覆盖**

**建议（分两步，第二步可选）**
1. **第一步（低风险）**：不改集合结构，只改**保存粒度**——正文编辑改为「按章 PATCH」并只在 `content` 变化时提交，避免小改动触发全量重写。可先用「内容 hash 比对」跳过无变化的保存。
2. **第二步（需你拍板）**：新增 `bid_chapters` 独立集合（一记录 = 一章），`bid_projects.bid_chapters` 降级为「章节索引 + 摘要」。**这动的是数据模型，属于你的红线，必须先出方案等你确认。**

### 3.3 后端路由重构：抽公共 CRUD 工厂

- **现状**：37 个 hook 文件，每个都手写 list/get/create/update/delete + 鉴权 + 归属校验 + 字段逐个 `rec.set`。例：`solutions.pb.js` 与 `customers.pb.js` 的 update 路由**结构几乎逐行相同**。
- **建议**：抽一个 `_lib_crud.pb.js` 工厂（`makeCrudRoutes({ collection, fields, longTextFields })`），各业务 hook 只声明字段表。
- **收益**：P1-1 的乐观并发控制、`totalItems` 修复、字段白名单**只需改一处**，而不是改 37 处。
- **注意**：改 `pb_hooks/` 后**必须重启 PocketBase** 才生效（你手册里已记录）。

### 3.4 React hooks 债务：**不建议现在动**

66 处 `set-state-in-effect` 集中在三个巨型 hook 里。这是 React 19 + React Compiler 的适配问题，**改造面大、收益不可见、回归风险高**。建议：
- **不做**整体改造
- **只做**一件事：把 `useIntelCenter.ts`（27 处，最集中）在下次动到情报模块时**顺手**收敛

### 3.5 明确不建议动的（守住你自己的红线）

| 不要动 | 理由 |
|---|---|
| `bidTypes.ts` / `useBidWorkspace.ts` 的**整体结构** | 你自己的红线；6 千行文件里没有测试网，重构 = 高风险 |
| 三模式提示词的**语义** | 会让已生成内容与新生成内容口径不一致（你的红线写对了） |
| 下游校验器（评标/偏离表/覆盖审计/废标自查）的判定标准 | 见 §4.4，这是**故意的 mode-blind 设计**，不是缺陷 |
| 导出交付物（Word/Excel/PPT）版式 | 客户交付物 |
| 费用确认 / 扣费 / 身份认证逻辑 | 红线 |

| 输入 | 单次 `MAX_TENDER_CHARS = 14000`；超长 → `chunkTenderText(12000, overlap 800)` 分块串行（`useBidWorkspace.ts:386`） |
| 失败 | 每块重试 1 次，失败记 `failedChunks` 并在报告里给横幅（`bidTypes.ts:155`） |
| 输出 | 白名单键过滤（`sanitizeParseSections`）+ 字段去重 + 脏值黑名单 + 「未明确」归并（`cleanParseSectionContent`）+ 跨节行去重（`dedupeAcrossSections`） |
| 提示词 | 「提取铁律」（以原文为准、禁止编造、找不到省略）+「要点化铁律」（**≤60 字/条、≤25 条/项**）+「分块解析铁律」（非首段只输出新增字段） |
| 健壮性 | `extractJsonLoose` + `withJsonRepair` |

#### ★ 缺口 1：提示词里的数量约束**没有本地兜底**

- **证据**：`cleanParseSectionContent`（`bidTypes.ts:583`）做了去重/黑名单/归并，**但不校验「≤25 条/项」和「≤60 字/条」**。
- **风险**：模型不遵守 → 解析报告出现 200 条要点、单条 500 字，直接顶爆下游提示词的上下文预算。
- **建议**：在 `cleanParseSectionContent` 后追加一个**纯本地 validator**：
  ```ts
  const PARSE_MAX_LINES_PER_SECTION = 25
  const PARSE_MAX_CHARS_PER_LINE = 60
  // 超出则截断 + 在该 section 追加「（已截断 N 条，建议查看原文）」提示行，并计入 warnings
  ```
  这样"提示词是软约束、本地是硬约束"，双保险。

#### ★ 缺口 2：分块解析**不做键路由**，成本与重复率随块数线性膨胀

- **证据**：`parseTenderChunked`（`useBidWorkspace.ts:400`）对每块都调 `build(chunks[i])`，而 `build` 构造的提示词包含**全部 `requestedKeys`**。`buildTenderParseMessages` 的 `onlyKeys` 参数**存在但只用于"单项重解析"**。
- **量化**：100k 字招标 ≈ 9 块 → **9 次全键抽取**。每块都重复抽「预算金额」「采购人」等首段就能确定的字段（靠提示词的"分块解析铁律"和事后去重兜着）。
- **建议**：加一层**本地章节切分 + 键路由**：
  1. 先本地按「第X章 / 一、二、三 / 评分办法 / 资格要求 / 技术要求」等标题模式切段（纯正则，零 AI，和已有的 `extractImplicitConstraints` 同源）
  2. 按段标题把 `requestedKeys` 分组路由（「评分办法」段只问 `scoring`，不重复问 `purchase_list`）
  3. 无法路由的段才走"全键抽取"
- **预期收益**：token 降 40–60%，且重复行减少 → `mergeChunkReports` 的去重压力下降。

#### ★ 缺口 3：缺「解析完整度」门槛与高风险项人工确认

- **现状**：勾了但没提取到的项**保留为 pending**（`bidTypes.ts:842`），可单独重解析。这是好的。但**没有"解析完整度"总览**，也没有"高风险项必须人工确认才能进下游"的门禁。
- **建议**：
  - 解析报告顶部加**解析完整度**指标：`已解析 N / 勾选 M`、`分块失败 K 段`、`字段冲突 J 处`
  - **高风险项**（`scoring` 评分办法、`void_clauses` 废标条款、`star_clauses` ★▲条款、`bid_nodes` 关键节点）标「**必须人工确认**」；未确认时下游（大纲/编制）给阻断式提示
  - 理由：这四项错了**直接废标或丢分**，比"少解析一个采购清单"严重一个量级

#### 缺口 4：解析结果**不可回溯到原文位置**

- **现状**：每条要点是纯文本，**没有原文定位**（页码/条款号/句段）。
- **风险**：人工核对时要在招标文件里全文搜索，效率极低；出错也无法举证。
- **建议**：让模型每条要点附一个 `[原文位置]`（如「第 3 章 3.2.1」或首句摘录 10 字），本地做**存在性校验**（能在原文里找到才算有效）——这同时也是**防幻觉的硬手段**（找不到 = 疑似编造）。

### 4.2 招标参数生成 / 技术参数响应（**你点名的环节，也是风险最高的**）

#### 现状

| 位置 | 现状 |
|---|---|
| 标书正文 | `BID_STYLE_RULES` 有「技术参数忠实：逐字照抄」+「承诺克制（最小值响应）」；`FULLTEXT_GUARD_RULES` 有「规模量级自洽」 |
| 偏离表 | `buildDeviationMapMessages`（`bidTypes.ts:4577`）逐条判定响应程度 |
| 方案侧产品库 | `check_products.tech_params`（`TechParam`：参数名/参数值/竞品备注）可导出「**产品参数响应表**」xlsx（`checklistExports.ts:152`） |
| 事后检查 | `metricConflictHits` 只覆盖 **RPO/RTO/系统可用性** 三个指标 |

#### ★ 缺口 1（**最高优先**）：`docs/05 §2` 的允许/禁止判定表**没进提示词**

- **证据**：全库搜 `响应性包装`、`实质性变更` → **零命中**。目前只有一句「逐字照抄」，**模型不知道"改哪些字算响应性包装、改哪些算实质性变更"**。
- **建议**：见 §5.1 的可粘贴片段，注入 `buildBidChapterMessages` / `buildBidSectionMessages` / `buildBidContinueMessages`。

#### ★ 缺口 2：**没有"数值加码"的机器校验**

- **现状**：写了「≥1000 并发」时，**没有任何本地逻辑**去比对招标要求的「≥500 并发」并告警。
- **建议**：复用已有的 `METRIC_SPECS` + `timeToSeconds` 归一化思路（`content-guard-02` 已实现），把**招标参数值**与**正文参数值**做配对抽取：
  ```
  招标原文 "并发用户数 ≥ 500" → { metric: 并发用户数, op: "≥", value: 500 }
  正文   "支持 1000 并发"      → { metric: 并发用户数, op: "≥", value: 1000 }
  → 正文值 > 招标值 → warn「疑似参数加码：招标要求 ≥500，正文承诺 1000，将形成更高验收义务」
  ```
  这是**防废标/防超额承诺的机器兜底**，比提示词可靠一个量级。可作为 `content-guard-03` 的落地内容（账本里该条仍 open，正是"需 LLM+KB 接地"的三条规则）。

#### 缺口 3：没有「支持程度」结构化库 → 同一功能点口径不一致

- **证据**：`docs/06 #2` 已识别，实测确认**未落地**——全库搜 `支持程度` 零命中；`TechParam` 只有「参数名/参数值/竞品备注」，**没有"原生支持 / 配置实现 / 定制开发 / 不支持 / 规划中"这一维度**。
- **风险**：A 说"支持"、B 说"需定制"，评标时被抓住就是**响应不实**。
- **建议**：`TechParam` 加 `support_level` 字段（五档枚举）+ 响应话术模板；参数响应表导出时带支持程度列。**这是数据整理活，不是开发活**，建议先挑一条主力产品线试点。

#### 缺口 4：正文与参数表**两套口径**

- **现状**：参数响应表从 `check_projects` 的 `tech_params` 导出；正文参数由 AI 生成。**两者不互通**。
- **建议**：正文生成时把该项目的参数表作为「事实基线」注入（和 `global_facts` 同机制），让正文参数与参数表**同源**。

### 4.3 方案生成

| 维度 | 现状 | 缺口与建议 |
|---|---|---|
| 约束锚点 | 方案无招标文件锚点，已换成「医院项目事实基线 + 已确认建设清单」（`solComplianceModeRule`，`solutionTypes.ts:483`） | ✅ 设计正确 |
| 默认模式 | moderate（`SOL_COMPLIANCE_MODE_DEFAULT`）——方案是售前材料，无"加码=验收义务"风险 | ✅ 合理 |

### 4.4 下游校验器：**"模式中立"是故意的，不是缺陷**

- **现状**：`buildEvalMessages` / `buildDeviationMapMessages` / `buildCoverageAuditMessages` / `buildVoidCheckMessages` **都不注入生成模式**。账本 `bid-mode-checkers-01` 明确记录为 **won't-do**，理由是"检查器对漏项放松 = 危险方向，审计要保持中立"。
- **评价**：**这个判断是对的**。检查器是防废标安全网，让它随生成模式放宽标准，等于"自己给自己放水"。
- **但有一个残留风险值得处理**：报告读者不知道当前是哪档模式 → 「full 模式生成的内容被评标器按 strict 标准判『无依据加码』」会显得莫名其妙。
- **建议（不改判定标准，只改可解释性）**：在评标/偏离表/覆盖审计**报告头部透出**「本标书生成模式：full」+ 一行说明「校验按中立标准执行，未随模式放宽」。**判定逻辑一行不改**，只是让结论可解释。这条兼顾中立与口径一致。

## 5. 提示词还能再优化吗？——能，以下是具体改法

### 5.1 ★ 补 `docs/05 §2` 判定表（最高性价比，可直接粘贴）

**注入位置**：`bidTypes.ts` 的 `BID_STYLE_RULES` **之后**、`FULLTEXT_GUARD_RULES` **之前**；注入到 `buildBidChapterMessages` / `buildBidSectionMessages` / `buildBidContinueMessages` 三个正文生成器（`buildBidRefineMessages` 按模式限定）。

```text
【技术参数响应边界（防废标硬约束，所有模式均不放宽）】
判定标准：只允许「响应性包装」，禁止「实质性变更」。

一、允许的三类改写（且必须保留原文全部限定信息）
1. 人称语态转换：招标「投标人应提供 7×24 小时服务」→ 正文「本项目提供 7×24 小时服务，满足招标要求」；
2. 疑问/条件句转陈述句：招标「是否支持 ≥500 并发」→ 正文「本项目支持 500 并发用户，满足招标要求」；
3. 在原文后补响应结论词：「满足招标文件要求」「完全响应」。

二、禁止的实质性变更（逐条自检）
1. 改数值：≥500 并发 → ≥1000 并发；≤8 小时到场 → ≤4 小时；3 年质保 → 5 年；
2. 改单位口径：Mbps → Gbps；并发用户 → 注册用户；工作日 → 自然日；
3. 改范围：部分科室 → 全院；试点 → 全面推广；
4. 删限定语：漏掉「含税」「含运费」「含三年质保」「含安装调试」；
5. 无依据加码：招标未要求的功能主动承诺。

三、自检动作（每章输出前执行一次）
逐句核对本章出现的每一个数值、单位、范围与限定语，确认其与招标原文逐字一致；
无法逐字对应的，改写为「按招标文件要求响应」或【待填写】，不得自行给一个看起来合理的值。
```

**收益**：把"逐字照抄"从**原则**变成**可执行清单 + 自检动作**。这是 `docs/05` 作者自己写下的建议，且**零风险**（只加约束、不改语义）。

### 5.2 ★ 解析与 JSON 类任务显式设 `temperature = 0`

- **证据**：全库只有竞品模块设了温度（`useCompetitorAnalysis.ts:206` = 0.3、`useCompetitorTalks.ts:110` = 0.4）。**标书解析、大纲、评标、事实核查、JSON 修复全部走模型默认温度**（`llm.ts:111` 只在 `gpt-5` 时跳过温度）。
- **影响**：结构化抽取任务本质是**确定性任务**，默认温度会引入不必要的输出方差（同一份招标文件两次解析结果不同 → 用户会认为系统"不稳定"）。
- **建议**：`llmGenerate` 增加任务类型参数，按任务给温度：

  | 任务 | 建议温度 | 理由 |
  |---|---|---|
  | `bid-parse`（解析抽取） | **0** | 确定性抽取 |
  | JSON 修复 `buildJsonRepairMessages` | **0** | 只修语法，不许发挥 |
  | 大纲/正文生成 | 0.3–0.5 | 需要一定表达多样性 |
  | 评标/事实核查/覆盖审计 | **0–0.2** | 判定类任务要稳定可复现 |

- **成本**：改一行调用；**风险**：几乎为零（`temperature` 参数链路已通）。

### 5.3 补「输出前自检」收尾段

- **现状**：全库搜 `自检` / `输出前` → 在提示词里**零命中**（`ChapterSelfCheck` 是生成**之后**的独立评审调用，不是生成前的自检指令）。
- **建议**：在所有长文本生成提示词末尾加 3–5 条自检清单，例如：
  ```text
  【输出前自检（不输出自检过程，只输出正文）】
  1. 本章是否出现招标未要求的服务项或功能承诺？有则删除。
  2. 本章每个数值是否能在招标原文或【全局事实】中找到出处？无出处则改【待填写】。
  3. 本章指标是否与前文已给值一致？不一致则沿用前文值。
  4. 是否残留「待补充 / TODO / 占位」等元话语？有则删除。
  5. 是否出现装饰符号（【】★●→）或 Markdown 标记？有则改为纯文本。
  ```
- **收益**：把事后检查器的规则**前移成事前约束**——`docs/06 #9` 自己说了"提示词层是事前约束，检查器是事后拦截，两个都做才稳"。

### 5.4 补「负例锚定」：把已发现的历史缺陷写进提示词

- **现状**：提示词只有正向规则（"禁止编造"），**没有具体反例**。模型对抽象禁令的遵守度远低于对具体反例。
- **建议**：把测试报告里**实测出的缺陷**作为反例写进提示词（这是最真实的负样本）：
  ```text
  【历史缺陷反例（同类错误禁止重犯）】
  - ❌ RPO 写 0，同文又写 <1 小时；RTO 写 <30s，又写 <4h → 同一指标全篇只能一个值
  - ❌ 病历缺陷率写 1%，又写 2% → 同上
  - ❌ 预算 300–500 万却承诺「双活数据中心 + K8s 容器云 + PB 级存储」→ 规模与预算量级失配
  - ❌ 仍引用「2025 年前」「《2021—2025 年行动方案》」→ 政策时效已过期
  - ❌ 出现「三级甲院」（应为三级甲等医院）、「data stewardship」中英夹杂
  - ❌ 测试占位符「13131医院」进入正文 → 禁止任何占位符残留
  - ❌ 「确保通过五级评定」「确保获得满分」「数据准确率 100%」→ 绝对化承诺，改可核实口径
  ```
- **收益**：6 类实测缺陷**一一对应**提示词条款，是最高密度的负样本。

### 5.5 `strict` 模式补**正向定义**

- **证据**：`complianceModeRule("strict")` **返回空串**（`bidTypes.ts` 设计为"strict/缺省 = prompt 字节级不变"，为了不破坏存量项目口径）。
- **副作用**：strict 模式下**提示词里没有任何一句说明"当前是严格模式"**，模型只靠 `BID_STYLE_RULES` 的负面约束行事。
- **建议（兼容做法）**：**不改变 strict 的字节**，而是把 strict 的正向定义作为**独立的新增规则**注入（与 `FULLTEXT_GUARD_RULES` 同级），这样：
  - 存量项目：多了"严格模式"的明确约束，**方向更严不会跑偏**
  - 但仍属"**加**约束"，符合你的红线（"加约束可以做，改已有约束的含义必须问"）
- **建议文本**：
  ```text
  【本次生成模式：严格响应】招标文件既是下限也是上限。目标为零风险应答：
  只按招标列明的要求项与评分办法逐项正面应答，不主动增设小节、不新增服务项、
  不提高任何指标档位；字数预算是上限而非目标，条款应答完整即止。
  ```

### 5.6 提示词工程机制层：三件"以后省大钱"的事

| # | 事项 | 现状 | 建议 |
|---|---|---|---|
| 1 | **提示词版本化** | 生成内容**不可追溯**是哪版提示词产出 | `PROMPT_VERSION` 常量随内容落库（见 §3.1） |
| 2 | **提示词回归集** | 已有 `MockEvalPanel.tsx`（模拟评标面板） | 扩成**固定用例集**：N 份真实招标文件 + 期望断言（必须包含/必须不包含），改提示词后一键回归 |
| 3 | **提示词单元测试** | 无 | 断言"strict 必须含「逐字照抄」、不得含「允许新增章节」"这类**结构性断言**（不需要 LLM，纯字符串断言，零成本） |
