## 二、马上做（3 项，都是低成本高价值）

### 1. 资质与人员证书台账（含到期预警）

**痛点**
投标材料里最容易出事的不是方案，是**证书过期**。营业执照、软著、ISO9001/27001、CMMI、ITSS、涉密资质、等保测评资质、社保证明、审计报告……每一份都有有效期，且不同项目要的组合不同。现状是"投标前临时找行政要材料"，一旦漏了或过期，**直接废标**。

人员证书同理：项目经理的 PMP、系统集成项目管理工程师、各类职称、社保记录，投标要按招标要求凑人数与资历，**证书过期或人员离职**是高频事故。

**现状缺口（已核查）**
- `资质证书` 只作为**知识库的七档分类之一**存在（`lib/kbPolicy.ts:17`），是文件级分类，不是结构化台账
- 无有效期字段、无到期计算、无预警
- 更麻烦的是：`资质证书` 分类默认策略是 `ai_context_mode: "sanitized_summary"` + `is_sensitive: true`（`kbPolicy.ts:33`），即**默认脱敏摘要、不进 AI 原文**。结果是投标文件里要引用资质时，AI 反而用不上这些资料——这是个隐性摩擦点

**建议设计**
- 新增「资质台账」：证照名称 / 类别 / 编号 / 发证机关 / 有效期起止 / 扫描件 / 适用项目类型 / 是否对外可提供
- 新增「人员证书台账」：姓名 / 岗位 / 证书名 / 等级 / 编号 / 有效期 / 社保状态 / 可参与项目
- **到期预警**：复用现有 `FollowUpReminderCard` 的提醒机制，提前 90/60/30 天在首页告警
- **投标联动**：招标文件解析出「资质要求」后，自动比对台账，标出"满足/缺失/即将过期"
- **策略放开**：给台账开一个显式开关，允许将指定证照以原文形式授权给 AI 引用（用于生成资质章节与商务响应），而不是被 `sanitized_summary` 一刀切

**为什么排第一**：数据量小（几十条），开发成本低，但拦的是**废标级**事故。

### 2. 产品功能点矩阵库

**痛点**
售前最高频的重复劳动是**技术参数逐条响应**。招标文件列 200 条技术要求，每条要判断"我们产品是原生支持、要配置、要定制开发、还是不支持"，然后写响应说明。这件事每个月都在做，每次都在重新判断，而且**不同人答的口径不一致**——A 说"支持"，B 说"需定制"，评标时被抓住就是响应不实。

**现状缺口（已核查）**
- `功能点` 在 11 个文件里出现，但都是**提示词层面**（让 AI 去写），没有结构化产品功能库
- 没有"支持程度"这个维度（原生支持/配置实现/定制开发/不支持/规划中）
- 没有版本维度

**建议设计**
- 结构化库：功能模块 / 功能点名称 / 功能描述 / **支持程度**（五档）/ 适用版本 / 响应话术模板 / 备注
- **批量导入**：从现有产品白皮书、历史标书的技术响应表反向抽取（这是启动数据的关键，可以 AI 辅助）
- **投标联动**（核心价值）：招标文件解析出技术条款后，自动做**语义匹配**，预填"支持程度 + 响应说明"，人工只做复核。这把 200 条从"逐条手写"变成"逐条确认"
- **口径一致性**：同一个功能点在所有项目里输出同一个支持程度，杜绝自相矛盾

**为什么排第二**：开发不难，**难点在数据整理**——但这件事做一次，之后每个项目都省。而且它直接喂给你已有的偏离表生成，衔接成本为零。

### 3. 招标文件倾向性/排他性参数识别

**痛点**
医疗信息化招标里，**参数抄某厂商**是常态（"必须支持 XX 架构""具有 XX 专利""指定 XX 品牌"）。这类条款有两个用途：
1. **判断这个标是不是内定的**——如果是，投不投、投多少，决策完全不同
2. **找质疑/投诉点**——招标文件不得以不合理条件限制排斥潜在投标人，这是法定救济途径

现在这件事全靠售前个人经验肉眼看。

**现状缺口（已核查）**
- 全库搜 `倾向性`/`排他`/`唯一性`/`指定品牌` → **零命中**（只有"质疑/异议截止"作为一个时间节点，以及竞品话术里的"化解质疑"）
- 解析报告里没有这个维度

**建议设计**
- 在招标文件解析环节增加一路扫描，识别并分级：
  - **高**：指定品牌/型号、要求特定专利、参数组合只有一家能全中
  - **中**：指标明显高于行业常规（如要求"双活+PB级存储"但预算只有几百万）
  - **低**：表述模糊但可解释为倾向
- 输出：条款原文 + 命中理由 + 风险等级 + **建议动作**（可质疑 / 需澄清 / 需评估是否值得投）
- 与已有 `ComplianceMatrixPanel`（提取 ★▲/废标/资质/符合性四类条款）并列，作为第五类

**为什么排第三**：**几乎零开发成本**——一个提示词 + 一个展示面板即可（你已经有四类条款抽取的成熟模式），但提供的判断信息是决策级的。

## 三、排期做（3 项）

### 4. 业绩合同台账 + 同类业绩自动匹配

**痛点**
同类项目业绩是**硬评分项**，通常占 5–15 分。投标时要按招标要求筛选"哪些合同能算同类业绩"（金额门槛、时间范围、项目类型、是否要求验收报告），然后生成业绩表并附证明材料。现在靠人翻历史合同。

**现状缺口**：`业绩` 出现 6 个文件，但都是**提示词层面**（让 AI 引用"自有资料"），无结构化台账。

**建议设计**
- 台账字段：合同名称 / 客户 / 金额 / 签订日期 / 验收日期 / 项目类型 / 建设内容 / 是否可提供证明 / 证明文件
- **自动匹配**：按招标的业绩要求（金额≥X、近Y年、类型为Z）自动筛出可用业绩，生成业绩表初稿
- **投标联动**：与标书工作台的「团队写作资料」打通，让业绩成为可引用的结构化事实而非自由文本

---

### 5. 成本-毛利-折扣测算

**痛点**
售前最常被问的一句话是"**最低能到多少**"。现在报价模块有单价和折扣，但**没有成本价**，所以算不出毛利，也就给不出折扣底线。结果要么报高了丢标，要么报低了亏本，全靠个人经验。

**现状缺口（已核查）**：报价模块字段为 `item_name/spec/unit/qty/price/discount/ref_price`，**无成本字段**；全库搜 `毛利` → **零命中**。

**建议设计**
- 每个行项增加「成本价」字段（可继承标准成本表，不必每次手填）
- 自动测算：毛利率、让利空间、**折扣审批线**（如毛利率低于 25% 需上级审批，与你已有的 GateChecklist 审批机制衔接）
- **竞对价格参考**：与第 9 项（中标报价情报）联动，显示"同类项目历史中标价区间"
- 税负口径已有（`DEFAULT_TAX_NOTE`：软件服务 6%、硬件 13%），可直接复用

---

### 6. 采购意向监测

**痛点**
情报中心现在抓的是**招标公告**——但招标公告挂网时，项目往往已经跟了大半年。**采购意向公开**（预算单位须提前公开）比招标公告早 **30–90 天**，这是最早能介入的时点，也是从"被动应标"转向"主动做项目"的关键。

**现状缺口（已核查）**：`IntelSourceType` 只有 `policy | competitor | bid | media` 四类，**没有采购意向**；全库搜 `采购意向` → **零命中**。

**建议设计**
- 新增第 5 类源 `intent`（采购意向）
- 抓取各级政府采购网的采购意向公开栏目（通常按季度/月度批量发布）
- **价值在于时间差**：意向公开 → 提前接触 → 影响需求 → 参与参数制定。这是售前最高价值的动作，但没有工具支撑
- 复用已有的一键转标书任务，改为"一键转商机"

## 四、以后做（3 项）

### 7. 需求调研工具

**痛点**：售前拜访回来一堆录音、照片、笔记，要整理成结构化需求清单，纯手工。全库搜 `调研`/`访谈` → **零命中**，完全空白。

**建议设计**
- 科室访谈提纲生成（按门诊/住院/检验/影像/药房分科室，带针对性问题）
- **纪要转需求清单**：粘贴访谈记录 → 结构化输出"科室 / 痛点 / 需求描述 / 优先级 / 对应系统模块"
- **痛点-方案映射表**：把调研出的痛点直接映射到建设清单与方案章节，打通"调研→方案"这条链（现在方案工作室与客户管理是断开的）

---

### 8. 投标日历 + 保证金台账

**痛点**
- **投标日历**：报名截止、答疑截止、保证金缴纳截止、投标文件递交截止、开标时间——跨项目视图缺失。现有 `bid_nodes` 只在**单个项目内**解析，首页只有"商机跟进到期"，没有全局投标节点视图。**错过投标截止**是不可挽回的
- **保证金台账**：交了多少钱、什么时候该退、退没退。这是财务对账的真实痛点，全库搜 `保证金` 只有 2 个文件（且是招标解析用），无台账

**建议设计**：跨项目投标日历（月/周视图）+ 保证金流水（缴纳/退还/逾期未退告警）

---

### 9. 全文一致性检查器

**痛点**：这是**上次实测直接发现的问题**——同一份生成文档里指标自相矛盾：

- RPO 写 `0` / 又写 `<1h`
- RTO 写 `<30s` / 又写 `<4h`
- 病历缺陷率写 `1%` / 又写 `2%`
- 架构规模（双活 / K8s / PB 级存储）与 300–500 万预算严重失配
- 政策时效过期（仍引"2025 年前"、《2021–2025 年行动方案》）

现有 `buildFactCheckMessages`（`bidTypes.ts:5311`）是**事实核查**，方向对但覆盖不到上述几类。

**建议设计**：独立检查器，五项规则
1. **指标唯一性**：同一指标（RPO/RTO/可用性/响应时间/缺陷率/并发数）全文只允许一个值
2. **量化依据**：所有数值承诺必须能追溯到招标原文/事实块/自有资料，否则标记
3. **规模量级自洽**：架构规模 vs 预算 vs 医院等级，三者交叉校验
4. **政策时效**：引用的标准/政策文件校验是否现行有效（可对接已有政策库 `kbPolicy`）
5. **占位符与术语**：查测试占位符残留（如"13131医院"）、错别字、中英文混杂

> 这项与 `docs/05` 里的「防翻车约束块」是**互补关系**：提示词层是"事前约束"，检查器是"事后拦截"。两个都做才稳。

## 六、落地建议

**顺序**：1（资质台账）→ 2（产品功能点库）→ 3（倾向性识别）→ 4/5/6 并行

**理由**：
- 1 和 3 是**低成本高价值**，一个防废标、一个给决策依据，可以先做
- 2 的价值取决于**数据整理投入**，建议先小范围试点（挑一个主力产品线），跑通"导入→匹配→预填响应"闭环再铺开
- 4/5/6 需要新的数据模型，建议一起设计（都是台账型）

**一个共性判断**：这三项（资质台账、业绩台账、人员证书台账）本质是同一类东西——**结构化台账 + 到期/条件匹配 + 投标时自动调用**。建议**用一套通用台账框架**承载，不要做三个独立模块。这样以后加"维保到期台账""合同台账"都是配置而非开发。

**另一个共性判断**：第 2 项（产品功能点库）和第 9 项（一致性检查器）是**配套**的——功能点库解决"支持程度口径统一"，检查器解决"生成结果口径统一"。两个一起做，"同一功能在不同项目里说法不一致"这类问题才能根治。
