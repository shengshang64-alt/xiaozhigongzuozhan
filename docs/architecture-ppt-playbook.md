## 一、架构图六步画法（核心方法论，来自 a23_04）

> **画图不是堆组件，而是降低沟通成本、指导技术决策。**

| 步 | 动作 | 关键产出 |
|---|---|---|
| ① | **从业务架构推演技术骨架** | 业务能力 → 技术服务，1:1 或 1:N 映射 |
| ② | **从用例场景推导非功能模块** | 高并发→Redis；异步处理→Kafka；一致性→事务/幂等 |
| ③ | **提炼横向模块** | 分层：API / Application / Domain / Infrastructure |
| ④ | **提炼纵向模块** | 复用下沉：认证中心、消息平台、ID 生成器、二方库 |
| ⑤ | **添加支撑与稳定性模块** | 监控、日志、Tracing、熔断、限流、配置中心 |
| ⑥ | **形成分层 + 分片逻辑架构** | 按职责分层，按业务域分片 |

### 视觉语法（必须遵守）
- **实线框** = 有边界的组件
- **实线箭头** = 同步调用 / 强依赖
- **虚线箭头** = 异步消息 / 弱依赖
- **虚线无箭头** = 配置 / 编译依赖
- **颜色 = 语义**：蓝=业务、绿=中间件、橙=边界、灰=支撑、红=风险

### 黄金法则
> **连线交叉超过 5 处，优先检查分层或分域是否混乱。**

### 自检项
- ✅ 图里要看得出 **QPS、一致性、延迟、可用性**
- ❌ 只画业务功能、看不出瓶颈和稳定性方案 = 还停留在"功能实现思维"
- ✅ 关键动作：不要只画业务功能，要把技术方案画进架构

## 二、分层架构图版式（a19_00 范式）

```
┌─────────────┬──────────────────────────────────────────────┐
│ 渠道与入口   │ [移动App] [Web商城] [开放API] [运营后台]        │  ← 最外层
├─────────────┼──────────────────────────────────────────────┤
│ 接入与安全   │ [Gateway] [Auth认证] [WAF] [RateLimiter]      │
├─────────────┼─────────── ↓ HTTP/gRPC ──────────────────────┤
│ 业务服务层   │ [用户域] [商品域] [订单域] [支付域] [库存域]      │  ← 每个域内含领域服务+能力项
├─────────────┼─────────── ↓ 数据访问/事件发布 ───────────────┤
│ 平台能力层   │ [Config] [Registry] [Tracing] [Metrics] [Log] │  ← 支撑类，灰底
├─────────────┼──────────────────────────────────────────────┤
│ 数据与中间件 │ [MySQL] [Redis] [Kafka] [ES] [ObjectStorage]  │  ← 基础，绿底
└─────────────┴──────────────────────────────────────────────┘
```

**规律**：
1. 左侧用**彩色竖条**标层名（一色一义），右侧该层组件用白底圆角卡片
2. 层间用**向下箭头 + 协议标注**（HTTP/gRPC、数据访问/事件发布）
3. 业务域内部再分层：域标题 + 服务名 + 3 个能力项（小字条）
4. 色块宽度统一、层高一致，形成"砖墙"视觉

## 三、DDD 四层架构图（a21_02 / a22_03 范式）

```
┌─ 订单域 Order Domain（自治边界，虚线大框）─────────────┐
│ 1. 接口层 API/Adapter  [订单API][管理后台API][事件订阅Adapter] │
│         ↓                                                │
│ 2. 应用层 Application  [创建订单用例][取消订单用例][事务编排]   │
│         ↓                                                │
│ 3. 领域层 Domain（核心心脏）[Order聚合][状态机][定价引擎]      │
│         ↓                                                │
│ 4. 基础设施层 Infra  [OrderRepo][MySQL][Redis][Kafka]     │
└──────────────────────────────────────────────────────────┘
        ↓ 虚线（异步/弱依赖）        → 实线（同步调用）
   外部域：[支付域] [库存域] [积分域]  ← 放在右侧独立卡片
   横切：[监控][日志][链路追踪][配置中心] ← 放在底部一行
```

**关键**：
- 用**虚线大框**圈出"自治边界"（一个限界上下文）
- 每层左侧有**编号 + 中英双语层名**
- 外部域放**右侧**，用实线/虚线区分同步异步
- 横切关注点放**底部**，用虚线连上去（不打断主链路）

**进阶细节（来自 a26_07）**：
- 左侧竖排标注 **"依赖方向：上层调用下层"**（一个长箭头贯穿全图）
- 每层左侧加**一句话职责说明**：如"网关、鉴权、协议转换、参数校验" / "用例编排、事务控制、权限校验、流程协调"
- 层间箭头标 **"同步调用 / 编排"**；跨层异步用 **虚线 + "异步事件发布"**
- **领域层**额外标红框："领域层不依赖 Spring / ORM / MQ"（核心约束）
- 右侧竖排标注 **"变化隔离：外层可替换，领域层保持稳定"**
- 领域层底部加一条"可进一步拆分：规则引擎 / 定价引擎 / 任务调度 / 故障感知"

## 三·B、业务架构 → 技术骨架 映射图（a24_05 范式）

三栏递进，最适合向非技术领导讲清"技术从哪来"：

```
[业务架构输入]  --职责映射-->  [映射与补充]  --输出-->  [技术骨架输出]
 用户管理                      ① 直接映射               UserService
 商品管理         ────────→     业务能力→技术服务         ProductService
 订单交易                       按职责边界映射为独立服务    OrderService
 支付结算                      ② 补充纯技术模块          PaymentService
 库存履约                       网关/鉴权/配置/链路追踪    InventoryService
                               "业务图不会说，但系统必须有"
                               ③ 粒度对齐（1:1 或 1:N）  ── ┬→ Gateway 网关
                               避免服务过粗或过细           ├→ Auth 认证中心
                               对齐业务边界与团队边界        ├→ Config Center
                                                          └→ Tracing 链路追踪
```

**视觉**：
- 三栏用**彩色表头**（蓝 / 绿 / 深蓝）
- 左中两栏之间的箭头标注**映射类型**（"职责映射"）
- 右侧前 5 个是**实线箭头**（业务推出来的），后 4 个是**虚线箭头** + 标注"业务图不会说，但系统必须有"
- 每栏每个条目 = 图标 + 主标题 + 一行说明小字

## 四、从业务到技术模块的推导图（a25_06 范式）

三列对照表，最适合讲清"为什么需要这个中间件"：

| 典型业务用例/场景 | → | 技术问题 | → | 技术解法 | → | 推导出的非功能模块 |
|---|---|---|---|---|---|---|
| 商品详情页高并发读 | | 读流量突增、热点数据 | | 缓存前置 | | Redis 缓存层/本地缓存 |
| 服务间调用 | | 服务发现、负载均衡、超时重试 | | 注册发现+LB | | 注册发现+负载均衡 |
| 订单完成后发积分 | | 解耦、削峰、最终一致 | | MQ 异步 | | Kafka/MQ 消息队列 |
| 扣库存与下单一致性 | | 事务边界、幂等、补偿 | | 分布式事务 | | Saga/幂等表 |
| 秒杀活动 | | 瞬时流量、排队、公平性 | | 限流+队列 | | 限流器/排队队列/缓存预热 |
| 金融转账 | | 资金安全、对账、重复请求 | | 审计+幂等 | | 对账模块/审计日志/加密 |

## 五、医疗售前 PPT 版式规范（来自 19 张成品页）

### 5.1 视觉基调
- **主色**：深藏青（#1B3A5C 附近）+ 白底，稳重专业
- **辅色**：墨绿 / 赭石 / 紫灰 / 中灰（每页最多 4 色，一色一义）
- **字体**：标题用粗黑（思源黑体 Heavy / 微软雅黑 Bold），正文用常规黑体
- **风格**：扁平化 + 细线图标 + 大留白，不用阴影渐变

### 5.2 封面页（a0_00）
```
┌────────────────────────────────────────────────┐
│ 三甲医院                                        │
│ "十五五"          ┌──── 医院建筑渲染图 ────┐    │
│ 运营管理方案      │  + 数据可视化元素叠加    │    │
│ 2026—2030        └────────────────────────┘    │
├────────────────────────────────────────────────┤
│ [🏥公益与质量]  [📊资源与效率]  [💰成本与绩效]  [🔗数智与治理] │
└────────────────────────────────────────────────┘
```
- 左侧**超大标题 + 副标题 + 年份区间**
- 右侧**实景建筑图**（半透明叠加数据图表元素）
- 底部**4 个图标+文字的分类卡片**，作为全篇骨架预告

### 5.3 内容页通用骨架
**顶部**：左对齐大标题（28-32pt 粗体）+ 可选副标题（灰色小字）
**正文区**：用 **01/02/03 编号色块**切分模块，每块一个圆角容器
**底部**：可选"口径说明/备注"灰条

### 5.4 五类高频版式

| 版式 | 结构 | 适用 |
|---|---|---|
| **四列对照表** | 表头带色块（依据/要求/动作/边界），每格图标+文字 | 政策依据、职责分工 |
| **指标进度表** | 行=指标，列=基线/年度目标，每格下方带横向进度条 | 目标体系、KPI |
| **①-⑥ 流程卡** | 6 个等宽卡片横向排列，卡内编号+标题+图示 | 方法论、六步法 |
| **三栏并列卡** | 每栏 = 编号+标题+图标矩阵+实景图+关键指标条 | 资源协同、场景拆解 |
| **四象限图** | 2×2 坐标系 + 气泡/卡片定位 | 改进判断、优先级 |

### 5.5 图表细节
- **进度条**：满宽浅灰底 + 深色实心条，条内不写字，数值写在格子里
- **指标表**：表头深底白字，隔行浅灰底，数字右对齐
- **色块编号**：深色圆角方块 + 白色 "01"，后面跟竖线和标题
- **图标**：统一线性风格（Feather/Lucide 风格），尺寸一致
- **实景图**：圆角裁切，用来增强行业代入感（病房/手术室/CT）

## 六、画架构图的工具与实现路径

### 6.1 工具选择
| 场景 | 推荐 |
|---|---|
| PPT 内嵌架构图 | **SVG 手写**（精确控制层次/配色/连线） |
| 快速原型 | draw.io / Excalidraw |
| 代码化生成 | Mermaid（适合流程，不适合精美分层图） |

### 6.2 本项目（小智工作站）PPT 生成的落地建议
现有 `PptQuote` 模块已支持：
- `deckChart`：ECharts 图表
- `figures`：结构化配图（architecture / flow / demo 三类）

**建议扩展**：新增 `layered-architecture` 图型，参数化：
```json
{
  "type": "architecture",
  "title": "智慧医院信息化架构图",
  "layers": [
    { "name": "渠道层", "color": "blue", "items": ["互联网医院", "移动App"] },
    { "name": "业务层", "color": "blue", "items": [...] }
  ],
  "crossCutting": ["信息安全", "运维管理"],
  "sideDomains": [...]
}
```

## 七、检查清单（出图前逐条过）

- [ ] 分层是否清晰？每层职责单一
- [ ] 颜色语义是否一致？同色同类
- [ ] 连线交叉是否 ≤5 处？
- [ ] 是否体现了非功能要求（性能/一致性/可用性）？
- [ ] 外部系统/边界是否明确标出？
- [ ] 横切关注点（安全/运维/监控）是否单列？
- [ ] 文字是否可读？最小字号 ≥10pt
- [ ] 是否有行业实景图增强代入感？
- [ ] 页内信息密度是否适中？一页一个主题
