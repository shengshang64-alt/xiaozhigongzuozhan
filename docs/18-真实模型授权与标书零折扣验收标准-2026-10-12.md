## 二、「零折扣」六条铁律（可机器判定，不是口号）

| # | 铁律 | 判定方式 | 不达标后果 |
|---|---|---|---|
| 1 | **全量输入**：真实招标文件（含扫描件）整份进链路，不抽样、不截断 | 解析报告条目数 = 招标原文条目数 | 直接判不合格 |
| 2 | **逐字引用**：凡引招标原文，必须字符级一致 | L2 逐字比对，改写数 = 0 | 直接判不合格 |
| 3 | **零编造**：不得出现招标原文与素材库都不存在的数字/名称/承诺 | 逐字比对，编造数 = 0 | 直接判不合格（废标风险） |
| 4 | **零漏答**：招标要求条款 100% 逐条响应 | 覆盖审计，漏答数 = 0 | 直接判不合格（废标风险） |
| 5 | **交付物干净**：导出 .docx 无【待填写】/XXXX/TODO/空章/截断 | 交付门禁 BLOCKER = 0 | 直接判不合格 |
| 6 | **降级必须声明**：任何未做到项的降级验证，必须写进报告诚实清单 | 报告含诚实清单且与实测一致 | 视为谎报，本轮作废 |

> 铁律 5 的判定工具：**`scripts/bid-delivery-gate.mjs`**（本次新建，只读、零 AI 费用、退出码即判定）。

## 三、新增工具：标书交付门禁

**为什么必须新建**：既有验证门禁是 `tsc -b && vite build && vitest && eslint` —— 它们证明**程序是好的**，证明不了**交付物是干净的**。实测中两者同时成立：`vitest 2143 passed` 全绿，而标书正文里躺着 **103 处致命空缺**。

```bash
node scripts/bid-delivery-gate.mjs              # 全量体检（退出码 0=无致命 / 1=有致命 / 2=脚本故障）
node scripts/bid-delivery-gate.mjs --project 三明   # 只查指定项目
node scripts/bid-delivery-gate.mjs --json       # 机读输出
```

**判定分级**：

| 级别 | 含义 | 含哪些规则 |
|---|---|---|
| **BLOCKER** | 致命，必须清零才能交付 | 承诺数值空缺 / 前置承诺句空缺 / 未替换模板变量 / 待办标记 / done 章节过短 / gen_status=failed / **项目编号未注入正文** / **项目依据可回取却留空** |
| **WARN** | 警告，须人工确认后方可交付 | 材料清单类空缺 / 编号类占位 / 下划线空栏 / 其他待填写 |

**归责分类**（把「一堆空缺」变成「谁去办」）：

| 责任方 | 含义 | 验收动作 |
|---|---|---|
| ① 商务决策 | 质保延长年限等承诺值 | **须用户/商务拍板，AI 代填 = 承诺风险** |
| ② 人工附材料 | 证书 / 截图 / 名单 / 检测报告 | 由投标文件制作者附真实原件，系统无法生成 |
| ③ 系统可回取 | 项目依据 / 项目编号等招标原文已有的事实 | **须查注入链路为何失效 —— 属系统缺陷** |
| ④ 待人工判定 | 未能自动归责 | 逐条人工确认 |

## 五、已确证的 3 类真实缺陷（硬证据）

### 缺陷 1：项目依据「招标原文里有，系统没回取」（③ 类，致命）

**证据**：建阳项目招标原文第 1 处「初步设计与概算」上下文：

> …依据该总体项目的《**建阳区边远山区乡镇卫生院灾后重建项目总医院设备及信息化建设初步设计与概算**》，总医院信息化建设遵循"统一规划、分步实施…"

**事实完整存在于招标原文**；而生成正文对应位置为：

> 建阳区边远山区乡镇卫生院灾后重建项目总医院设备及信息化建设初步设计与概算 **【待填写】** 项目依据

**影响项目**：建阳、建阳区总医院（2 个项目，共 8 处）。
**性质**：**不是人工缺料，是系统未回取** —— 属提示词/注入链路缺陷，可自动修复。

### 缺陷 2：项目编号未注入正文（③ 类，致命）

| 项目 | 库中 `tender_no` | 正文中出现次数 |
|---|---|---|
| 13（贵港分行） | `GXKLG202630843` | **3 次**（含「招标编号 GXKLG202630843」） |
| **贵港项目**（同源同院） | `GXKLG202630843` | **0 次**（全文无「项目编号/招标编号/GXKLG」） |

**同源材料、同一招标，一个项目注入了编号，另一个完全没注入** → 注入链路不稳定。

> 注：三明与演练项目的 `tender_no` 本身即含 `XX`（`[350000]SMZC[GK]2026-XX`，真实编码未公示），正文带 XX 属**忠实传递，不算缺陷** —— 门禁已按此排除。

### 缺陷 3：商务决策项与人工材料项混用同一标记（①② 混杂，交付风险）

**证据**（建阳·售后服务与运维保障方案，同一章内）：

> 我公司承诺针对整个采购包所有产品提供**【待填写】年**免费质保期…
> …在 3 年的免费质保期基础上，承诺整个采购包所有产品的免费质保延长**【待填写】年**，该延长承诺以质保期承诺函为准…

「质保延长年限」是**商务评分项**（"质保期每延长 1 年得 1 分，满分 2 分"），必须由商务拍板；而同一份文档里「人员证书编号【待填写】」是**人工附材料**。两者用完全相同的标记，导致：

1. 交付前无法快速回答「还有几项在等我拍板」
2. 拍板项淹没在几十项材料项里，**极易漏掉 → 评标丢分**
