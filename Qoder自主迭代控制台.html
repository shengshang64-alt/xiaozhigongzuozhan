三层防护，从松到紧

第一层 · 规则约束（软）

.qoder/rules/30-redlines.md 把红线写成可判定的具体行为，而不是"注意安全"这类套话。 例如不是"谨慎删除数据"，而是"不执行 rm -rf / git push / 改 PB schema / 删业务数据"。

第二层 · 权限白名单（中）

.qoder/settings.json 里：

类别数量内容
allow40 条项目内文件编辑；pnpm build/lint/test、npx tsc/vite/eslint/vitest、node、只读 git（status/diff/log/add/commit/stash/restore）、本地 curl、启停服务脚本
ask2 条WebFetch / WebSearch（headless 下无人确认即自动拒绝）
deny27 条删除类（rm/rmdir/del/批量通配符）、格式化磁盘、git push/reset --hard/clean、提权、注册表、taskkill、装全局包、读 .env 与 pb_data、读写私钥

权限模式默认 accept_edits：工作目录内文件编辑自动批准，其余走上面的规则。 这个组合是确定性的——比 auto（靠 AI 分类器概率判断，分类器不可达时动作会被拒）更可预测， 比 yolo 安全得多。

第三层 · Hook 硬拦截（硬，不可绕过）

.qoder/hooks/guard.mjs 挂在 PreToolUse 上。 Qoder 的 Hook 权限决策优先级高于权限模式——也就是说， 即使有人用 --yolo 启动，Hook 返回的 deny 依然生效。 这是整套机制里唯一不可绕过的防线。

它拦截的东西包括：递归强制删除、磁盘格式化、git push、提权、注册表写入、 结束服务进程、装全局包、下载内容直接管道给 shell 执行、写/读 .env、 写 .git / pb_data / node_modules / .vibex 平台目录。

Hook 自身的失败策略是"放过"：若脚本异常或 stdin 超时，它输出 ask 交回正常权限管道， 绝不因为守卫自身故障而阻断你的正常工作。

权限模式怎么选

模式headless 下的行为建议
accept_edits 默认文件编辑自动批准；命令按 allow/deny 规则推荐。配合白名单完全确定性
auto由 AI 分类器逐个决策授权想更少人工干预时可用，但需在用户级 ~/.qoder/settings.json 里写 autoMode 引导（工作区配置会被刻意忽略）
dont_ask需要确认的一律拒绝最保守。实测会拒掉 pnpm build，AI 跑不了验证门禁，不建议用于本流程
bypass_permissions全部放行仅在你完全信任当前任务时使用；Hook 仍会拦危险操作

刹车机制

触发条件行为
连续 3 轮没产出报告判定为"空转/伪完成"，自动停机
连续 2 次环境预检失败自动停机（避免反复撞同一个墙）
CLI 未登录立即停机并给出登录指引（重试不会好转）
单轮超时（默认 45 分钟）终止该轮进程，记录为超时
工作区不干净拒绝开跑（除非显式 --allow-dirty）
AI 判定为 C 类（新增能力）只写方案不动代码，报告里列进"需要你决定"

容易踩的坑

坑 1：把 IDE 的 qoder 当成 CLI（最容易搞错）

D:\Program Files\Qoder IDE\bin\qoder 是 IDE 启动器（一个 VS Code 外壳）， 不能用于 headless 自动化——它会试图拉起图形界面。 自动化必须用独立的 qodercli 命令（本机已装 v1.1.62，在 C:\Users\Administrator\AppData\Roaming\npm\）。

坑 2：装了 CLI ≠ 能跑（还要登录）

实测未登录时 CLI 会返回 {"is_error":true,"result":"Not logged in · Please run /login"}， 退出码 1。驱动器已识别这个状态并立即停机 + 打印修复办法， 不会把它误判成"AI 没写好报告"。

坑 3：npm 全局安装会拦截 postinstall

本机 npm 有 allow-scripts 策略，安装 @qoder-ai/qodercli 时 postinstall.cjs 与 sharp 的安装脚本被跳过（终端会打 warning）。 实测不影响使用——qodercli --version 正常返回 1.1.62。 若将来出现异常，用这条补跑脚本：

备用
npm install -g @qoder-ai/qodercli --allow-scripts=@qoder-ai/qodercli,sharp

坑 4：改 pocketbase/pb_hooks/ 后必须重启 PocketBase

PB v0.40.4 的行为：改了后端钩子不重启不生效，会表现为"改了没反应"， 很容易被误判成"修复失败"。协议里已写明，AI 也知道。

坑 5：不要让 Vite 在沙箱环境下重建依赖缓存

start-local.cmd 启动 Vite 前会清空 NODE_OPTIONS， 因为安全守卫会在 Vite 批量删除 deps_temp_*（一次上百个文件）时误杀 dev server。 这个处理不能删。

坑 6：浏览器自动化会话不跨调用保持

相关规则已写进知识层，AI 每轮都会读到：会话不跨 bash 调用保持，必须每次重新 open + 登录； 点击 Radix 按钮必须用 agent-browser click @ref，在 eval 里写 .click() 会产生 "点了没反应"的假阳性；open 与 eval 必须压在同一个 bash 调用内。

常见问答

Q：一轮大概跑多久？花多少钱？

A：单轮墙钟默认上限 45 分钟。费用取决于模型与轮次用量，驱动器每次运行结束会打印 本次总费用（从 CLI 返回的 total_cost_usd 汇总），运行记录也存进 .loop/autoloop-state.json，方便你回溯哪一轮最贵。
省钱的关键不是限制轮次，而是协议里的"零费用优先"：静态读码 / 接口直查 / DOM 快照 / 本地复算能得出结论的， 就不该调 AI。

Q：它会把我的代码改坏吗？

A：三层防护 + 两道刹车。更实际的三条保障：
① 每轮改动小而可独立回滚，跑完自动 commit，出问题 git revert 一条命令；
② 验证门禁是硬性的——tsc -b && vite build 不过就必须先回滚再重来，禁止在失败状态上叠加改动；
③ 本轮只做一件事，禁止一次改一堆导致无法归因。

Q：它会不会为了"看起来有进展"而瞎改？

A：协议里专门堵了这条。待办池清空时禁止发明工作（禁止无意义重构、改注释、换变量名）， 正确做法是回到七条发现通道重扫；仍然没有就出总报告，明确说"当前已收敛，需要新需求输入"。 驱动器还会独立校验报告文件是否真的落盘——没落盘就计为"无产出"，连续 3 轮即停机。

Q：能不能让它自动加上新功能？

A：能发现，但不能自己动手。AI-ITERATION.md 把工作分成三类：
A 类修 bug / B 类优化 → 自动执行；C 类新增能力 → 只写方案，等你点头。
所以它会把新功能想法整理成"做什么 / 为什么 / 动哪些文件 / 对已有数据有无影响"的方案交给你， 而不是半夜自己把功能加上去。

Q：我只想让它在某个模块里干活怎么办？

A：加范围限定即可，范围外的问题它只记账不修改：

只在知识库模块迭代
node scripts/qoder-loop.mjs --rounds 1 --scope /knowledge

Q：跑偏了怎么紧急叫停？

A：在跑的那个终端窗口按 Ctrl+C 即可。驱动器与日志都落盘， 重跑时会从账本里的 round 继续，不会重复已完成项。 若已产生不想要的改动：git log --oneline -5 找到上一轮提交， git revert <hash> 或 git reset --hard HEAD~1 回滚。
