## 四、三来源链路验证
- 粘贴/Excel：文本逐行 + `parseCustomerLinesFile`（复用建设清单同源）。
- 从招标文件：`/api/bid_projects`（按 rh_user_id 过滤）→ 取 `parse_report` 的 `req_structure` / `purchase_list` section 逐行；未解析项目提示先去标书工作台解析。
- 从方案/需求：`/api/solutions` → 读 `hospital_info.ref_checklist_snapshot`（company_systems + customer_requirements 去重保序）。
三来源统一产出 `rawLines` 进入同一匹配流程；空数据均有 toast 兜底提示。

## 六、公司方法论对齐（参考 tm.py 对照表生成器）
借鉴同事项目离线 CLI「招标清单↔产品清单对照表生成器」（`tm.py` + `README.md`）的领域方法论，
落地三项增强（用户确认全量借鉴 A+D / B / C）：

| 项 | 借鉴点（tm.py/README 出处） | Web 落地 |
| --- | --- | --- |
| A+D | README §4 映射四条硬规则（按建设内容而非名称字面 / 分类取真实值 / 一对多选主干其余写备注 / 命名错位靠描述） | AI system prompt 注入匹配铁律；`parseMappingJson` 解析带 `note` 的 AI 结果；`MatchRow`/`MappingCompareRow`/hook/导出/页面全链路新增「备注」维度（`collectRowNotes` 仅收集 AI 命中行 note） |
| B | README §4.2「映射唯一依据是功能需求/建设内容分节描述，系统名清单不足为据」 | 新增 `bidContextFromReport`，从招标 `parse_report` 取技术需求/建设内容/功能要求分节正文（截断 4000 字）作为 AI 上下文 `【客户建设内容/功能需求摘要（映射依据）】`，随 `importFromBid` 传入 |
| C | tm.py `write` 机制：骨架原列一字不动、只在右侧新增列回填、时间戳命名不覆盖 | 新增 `exportFillSkeletonXlsx`：读取上传骨架首 sheet，表头右侧追加「产品名称/模块分类/模块名称/备注」四列，按归一化双向包含匹配命中行回填，时间戳命名下载 |

边界与取舍：
- tm.py 用 openpyxl/pymupdf/python-docx 离线可保留富样式；Web 端只能走 SheetJS（CE），写回**不保留原表字体/边框等富样式**，仅保证「原有单元格值一字不动、只新增列」，已在函数注释中说明。
- 修复一处 build 崩溃：`productMappingExports.ts` 时间戳曾用正则 `/[-:T]/`，其独立 token `[-:T]` 被 Tailwind 扫描器生成非法 CSS（`.\-\:T`）致 lightningcss minify 失败；改为手动 `pad` 拼接，杜绝任何紧凑方括号 token，`vite build` 恢复 exit 0。
