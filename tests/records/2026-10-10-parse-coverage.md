# 场景自测 — 长文档解析覆盖率可见性 + 生成门禁（R258 / 全局优化汇总 R-038③ Slice A）

日期：2026-10-10 ｜ 轮次：R258 ｜ 记录人：自动迭代（纯函数自检 + 面板/门禁接线）

## 场景口径（AGENTS 强制）
模拟一所三甲医院（天坛级 41.7 万字）长文档招标「批量解析（回落检索）→ 报告显式呈现极低覆盖率 → 生成大纲前被硬阻断 →
用完整档/分段覆盖重解析后放行 → 短文件精简输出不被误伤」全流程，验证 R-038③ 门禁真实行为，不破坏正常解析与既有项目。

## 操作步骤
1. 建医院 → 建项目 → 招标文件步上传 41.7 万字长文档 → 「完整档」批量解析（超段数上限回落检索，仅抽约 1.8 万字）。
2. 打开解析报告：头部「解析覆盖率 4%（过低，已阻止生成）」红字 + 顶部红色横幅（成因=长文档大部分原文未进入解析、
   补救=完整档/分段覆盖/扫描件先 OCR）即时可见。
3. 点「生成大纲」：`runGenerateOutline` 覆盖率门禁 `block` → `toast.error` 并 return，**不进入生成**（废标风险拦截）。
4. 用「完整档」重解析并让分段覆盖全文，使覆盖率升至 ≥30% → 门禁放行；落在 30%~50% 之间 → 生成时 `toast.info` 告警但放行。
5. 短文件（如 3 千字段）即便输出占比低：原文非空白 < 8000 → 不阻断，最多 warn（精简输出不误伤）。
6. 无原文 / 空报告：覆盖率返回 null → 不显示横幅、分级 ok（不臆断）。

## 自动化验证（零模型，纯函数）
`src/pages/BidWorkspace/parseCoverage.test.ts`（5 例）：
- 覆盖率 = 产出/原文非空白，空白不计；
- 原文空返回 null、超 1 截断到 1；
- 分级 block(<30%且原文够大)/warn(<50%)/ok（2000/4000/6000 三档）；
- 短原文(<阻断下限字数)即便占比低也只 warn 不 block（防误伤）；
- null→ok 不臆断 + 百分比取整 + 阻断阈值<告警阈值。

## 端到端回归（负控 + 正控）
- 正控：正常多章节覆盖充分（≥50%）→ 无横幅、无阻断（不干扰正常流程）。
- 负控：长文档回落检索 4% → 阻断触发 + 横幅显示（若逻辑反向，假数据即可发现，故单测即覆盖负控对照）。
- 四提示同屏复核：R-029 parse_quality（扫描件）+ R-030 requiredWarn（必选失败）+ R-026③ voidFloorWarn（废标偏少）
  + R-038 coverageBanner（覆盖率过低）均汇入 ParseReportPanel 顶部，可叠加显示；覆盖率由 sections+tenderText 实时派生，
  刷新后自动恢复、无需持久化新字段。天坛/建阳真实长文档样例本次会话未落磁盘（微信附件），端到端以纯函数负控 + 面板派生承载；
  现场部署时以真实 41.7 万字件复核阈值（50%/30%/8000）。

## 预期 / 实际结果
- 预期：长文档覆盖率极低时被显式呈现并在生成前硬阻断，给出可操作补救指引；短文件精简输出与空原文不误伤；四提示同屏持久。
- 实际：四门全绿（tsc0 / eslint 新 2 文件 0 problem + useBidWorkspace+ParseReportPanel 前后 6 errors·13 warnings 计数一致 /
  vitest 161/1863+2skip（+1 文件 +5 用例）/ build exit0）。

## 发现问题
- 本轮为「可见 + 拦截」安全网，未真正拉高覆盖率（长文档仍回落检索）；Slice B 提高段数上限/跨块汇总涉额外 AI 成本，另拍板。
- 阈值(50%/30%/8000 字)取汇总文档口径，属保守经验值，需以现场真实长文档校准；阻断为生成侧硬拦（废标风险不容静默放行），
  非导航锁。
