# 红线清单（违反即回滚，并在报告中说明）

以下每一条都写成了**可判定的具体行为**，不是套话。拿不准时，默认"不做"，把选择交回用户。

## 一、停下问用户（不要自作主张）

| # | 禁止行为 | 为什么 |
|---|---|---|
| 1 | 改 PocketBase 集合 schema / 数据模型 | 会让已存数据与新代码不匹配 |
| 2 | 改费用确认 / 扣费逻辑 | 涉及钱 |
| 3 | 改身份认证逻辑 | 涉及权限 |
| 4 | 改导出交付物格式（Word/Excel/PPT 版式） | 那是给客户的交付物 |
| 5 | 重构 `bidTypes.ts` / `useBidWorkspace.ts` 的文件结构 | 高危大文件，顺手重构必出事故 |
| 6 | 引入新依赖 | 改变供应链与体积 |
| 7 | 删除任何业务数据 | 不可逆 |
| 8 | 动 VibeX 平台保护文件 | 上传会返回 `platform_lib` 被跳过，改了白改 |

## 一点五、可自主替换但必须备份的（用户 2026-09-25 授权）

| 类型 | 自主权限 | 强制条件 |
|---|---|---|
| **AI 提示词** | 发现更优方案可替换旧提示词 | ① 原文完整备份（注释或 `.loop/prompt-backups/`）② before/after 对比证明严格更优 ③ 如果导致任何回退→立即回滚 |
| **UI 布局** | 发现更合适的布局可重做 | ① 先画静态原型（`.diag/ui-prototype-*.html`）② 自评“医院主任看了会不会觉得更专业”③ 不改变功能行为 ④ 原组件备份后落地 |

判定标准：**"新方案是不是让产出内容更接近招标文件要求、让界面更像专业售前工具而不是草稿？"**
是 → 替换（备份后）。不确定 → 不动。

## 二、一条总判据（拿不准时问自己这句）

> **"这个改动，会不会让已经生成的内容、或已经存下的数据，变得不一致？"**
>
> 会 → **停下来问用户**。不会 → 可以自己做。

## 三、执行安全

- **不执行破坏性命令**：删库、批量删文件、`rm -rf`、`git push --force`、`git reset --hard`
- 文件操作走编辑工具，不要用 shell 重定向批量改写
- **批量操作先 dry-run**，确认影响范围后再真实执行
- 每轮改动**小而可独立回滚**；改动前记录原始内容（`git diff` 或备份文件）
- 一旦验证不过：**先回滚，再重新分析**。禁止在失败状态上继续叠加改动

## 四、数据与凭据

- **不把下列内容打进任何交付/上传包**：
  `.env` / `.env.local` / 任何凭证 / `pb_data` / `*.log` / `node_modules` / `dist` / 缓存 / agent 工作目录
- 不在日志、报告、提交信息里打印密钥、token、密码
- 跑测试前备份 `pocketbase/pb_data`；破坏性测试必须隔离

## 五、诚实原则（这一条最容易被违反）

- 构建失败、验证未通过、没测到 —— **如实写进报告**，不粉饰
- 区分"改动前就存在的失败"与"改动引入的失败"，前者单独列出
- **严禁在没有验证的情况下写"已修复"**
- **不谎报验证结果；不把"没做"写成"已做"；不把"计划做"写成"已完成"**
- 用了降级手段（如浏览器不可用改接口直调）**必须在报告里注明降级**

## 六、成本

- **零费用手段优先**：静态读码、后端 API 直查、DOM 快照、本地复算 —— 这些都能得出结论，不要一上来就调 AI
- **AI 调用是最后手段**：跑真实 AI 生成前确认额度；接近余额阈值时停止 AI 类测试
- 不为了"看起来跑了很久"而空转轮次
