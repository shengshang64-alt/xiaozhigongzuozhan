# 迭代协议与放行门

**唯一入口是项目根目录的 `AI-ITERATION.md`。** 本文件是它的压缩执行版；两者冲突时以 `AI-ITERATION.md` 为准。

## 一轮 = 9 步（一步不能跳、不能合并）

1. **读状态** —— 读全三个来源（`.loop/ledger.json` + `.nightrun/state.json` 及晨报 + `docs/`），合并出候选池
2. **发现** —— 至少跑通道 1–3（见下），服务可用必须加跑通道 4，补充新候选
3. **选题** —— 选**一个**优先级最高的项，实机走查模块 = 轮次 mod 9（表见 `AI-ITERATION.md` 第 7 节），确定它属 A / B / C / D 哪一类
4. **取证** —— 实机或接口确认问题**真实存在**，留下硬证据（截图路径 / 实测数字 / 接口原文）；界面数字必须当场实测，禁止复述记忆
5. **定位** —— 定位到具体文件与行；给出**最小改动方案**；评估对已有数据的影响；**归因先查代码与数据链路，最后才怀疑提示词**（归因到提示词前必须本地复算出示证据）
6. **放行判断** —— A/B 类继续；C 类或触碰红线 → **停下写方案，等用户确认**
7. **改造** —— 最小改动面，风格与周边一致，只动本项范围内的代码
8. **验证** —— `pnpm build` + `pnpm lint`（对照基线无新增）+ `pnpm test`（不低于基线）+ 实机复测 + 按 `AI-ITERATION.md` 第 9 节跑 R1–R10 回归 + before/after 对比
9. **记账** —— 更新主账本；按固定格式写本轮报告（含 json 块）；推翻旧结论须写「诚实更正」

> **一轮只做一件事。** 改完立即验证。禁止一次改一堆导致无法归因。

## 四类工作与放行门（**本协议最重要的一条**）

| 类 | 内容 | 放行 |
|---|---|---|
| **A 类 · 修** | 确定缺陷：构建报错、接口 4xx/5xx、逻辑错误、数据不一致、样式破损、废标风险 | **自动执行**，做完报告 |
| **B 类 · 优化** | 提升质量：性能、文案、可发现性、一致性、无障碍；**提示词替换（备份+对比后）**；**UI布局重做（原型先行+自评后）** | **自动执行**，但必须说明"改前是什么、改后是什么" + 备份位置 |
| **C 类 · 升级** | 新增产品能力、新增数据模型、新增页面/模块、改交互范式 | **先写一页方案，等用户点头才动手** |
| **D 类 · 记录** | 真实存在但不属于本轮范围 | 记入账本 backlog（带证据与优先级），本轮不动手 |

> 选到 C 类时，**这一轮的任务就是"写方案 + 等确认"**。不要顺手把代码也改了。
> 剩下的全是 C 类 = 停止自动推进，汇总成建议清单交还用户。

## 严重度分级（选题排序用）

| 级别 | 判据 |
|---|---|
| **S0** | 数据错误 / 安全 / 资金 / 废标级 |
| **S1** | 功能跑不通：报错、白屏、点了没反应 |
| **S2** | 每天遇到的体验断点 |
| **S3** | 可量化的性能问题 |
| **S4** | 与已有能力直接衔接的缺口 |
| **S5** | 代码健康：死代码、重复逻辑、类型漏洞 |

排序公式：`严重度 > 出现频次 > 改动性价比`。

## 八条发现通道（待办池会耗尽，不能只靠它）

1. **待办池** —— 读主账本取最高优先级未关闭项
2. **编译与静态检查** —— `pnpm build` / `pnpm lint` 报的错是**最确定的缺陷**，优先修
3. **代码考古（找半成品）**
   ```bash
   grep -rn "TODO\|FIXME\|HACK\|XXX" src/
   grep -rn ": any" src/ | head -30
   grep -rn "console.log" src/ | head -30
   ```
   重点找三类：**有 UI 无逻辑**（按钮点了没反应）、**有字段无引用**、**有函数无调用**
4. **实机走查** —— 浏览器真实进入页面，按角色轮换换视角走一遍（最容易发现"代码没问题但用起来别扭"）
5. **数据与口径核对** —— 接口返回 vs 界面显示是否一致；同一指标在多处取值是否一致
6. **性能测量** —— 关键页面与接口耗时，超 3 秒的交互要记账
7. **需求侧对照** —— 读 `docs/05` `docs/06`，找"文档说了但代码没做"的落差
8. **完美主义体验审计**（用户 2026-09-24 常设指令）—— 以苛刻售前专家视角实机体验，每步产出都要过目，重点验"内容对不对、能不能用"；发现的瑕疵先记 backlog 后面统一修，不顺手改

## 角色轮换（每轮主导视角不同，避免反复发现同一类问题）

| 轮次 mod 6 | 主导视角 | 关注什么 |
|---|---|---|
| 0 | 售前工程师 | 这个功能能不能帮我拿下项目 |
| 1 | 产品经理 | 是否让产品更有价值而非更复杂 |
| 2 | 测试工程师 | 边界、异常、数据一致性 |
| 3 | 医院信息科 | 客户看这个界面会不会觉得不专业 |
| 4 | 评标专家 | 输出内容是否经得起评审 |
| 5 | 商务/财务 | 报价、成本、合规风险 |

镜头同步轮换：`流程通断 → 功能正确 → 界面习惯 → 交互反馈 → 内容质量 → 性能 → 数据一致性`

## 停止条件（满足任一即停，出总报告）

- 主账本未关闭项全部清零
- 连续 3 轮 `noProgressStreak`
- 达到轮数上限，或用户打断
- **剩下的全是 C 类**
- 全链路回归（R1–R10，表见 `AI-ITERATION.md` 第 9 节）**连续 2 轮不通过**——先全部回滚，写清根因再停
- 服务不可用且 `start-local.cmd` 拉不起来

## 关于"找不到事做"

待办池清空时，**不要为了显得有进展而发明工作**（无意义重构、改注释、换变量名）。
正确做法：回到七条通道重扫；仍然没有 → 出总报告，明确说"当前已收敛，需要新需求输入"。

## 关于重复

- 已关闭项**不得重开**，除非有新证据证明问题仍存在（须在报告里写明新证据）
- 被用户否决过的项，**不得在无新理由的情况下再次提出**

## 报告的说话方式（这个用户不是程序员）

用户原话：**"对程序开发了解不是很高"**。因此：

- 不假设他能看懂 diff
- 每份报告都要让他**自己动手点几下就能验证**（给到"打开哪个页面 → 点什么 → 看到什么算成功"）
- 需要技术判断的地方，**给出明确推荐并说明理由**，不要把选择题丢回去
- 报告写入 `.loop/reports/YYYY-MM-DD-HHmm.md`，并把一句话结论追加到 `.loop/MORNING.md` **顶部**（最新在最上）
- 本轮什么都没做成，**也要写报告说明原因，不要静默结束**
