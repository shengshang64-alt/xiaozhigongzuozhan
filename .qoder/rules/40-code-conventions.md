# 代码规范（改这些目录时生效）

## 1. 风格对齐优先于个人偏好

**周边代码怎么写，你就怎么写。** 命名风格、注释密度、惯用法、文件组织都要与同目录既有代码一致。
不要引入外部风格（不要顺手格式化整个文件、不要把现有命名改成你偏好的）。

## 2. lint 存量债务（不要把它算成本轮新增）

改动前先跑一次基线，记录你改动**之前**的错误数：

```bash
npx eslint src --format json > 改动前.json   # 或直接看输出计数
```

改完再跑一次，**只对"新增"的错误负责**。
历史遗留错误在报告里单独列出，**不算本轮失败，也不要去顺手清理**（会污染 diff 与归因）。

## 3. TypeScript 硬约束

`tsconfig.app.json` 开了：

- `noUnusedLocals` —— 未使用的局部变量 = **构建失败**
- `noUnusedParameters` —— 未使用的参数 = **构建失败**

所以：**删代码必须连带清引用**。删了一个函数，所有 import 它的地方都要处理，否则构建直接挂。

## 4. 注释规范

- 注释密度 ≥ 每 10 行 1 行**功能性**注释
- 注释写"**为什么**"和"**边界条件**"，不写"这行在赋值"这类废话
- 修 bug 时在改动处留一句为什么这么修（既有代码已有此习惯，例如 `// p2-perf：路由级 code splitting——…`），便于下轮回归时理解意图
- **不写**：调试残留（`console.log`）、占位注释（`// TODO: 以后优化`）、废弃代码注释块

## 5. 状态与副作用

- 不要引入模块级可变全局状态；状态放 React hook 或明确的 store
- 接口写入要串行化（本项目有历史教训：并发 PATCH 导致"读整行-改-存整行"丢字段）
- 异步失败必须给用户**可理解的原因 + 下一步**，禁止空 catch、禁止只报"失败"

## 6. 忽略目录（不要在这些目录里找问题）

```text
dist/  node_modules/  pocketbase/pb_data/  vibex-local/bin/
.nightrun/  .loop/  .diag/  .cursor/  .vibex/  .workbuddy-ai/
_qa/  _shots/  _edgeprofile/  ui-redesign-pro/
_vite_dev.log  pb.log  vite.log
```

这些是构建产物、运行时数据、历史备份、循环账本、验证辅助产物。
在它们里面发现的问题**不是产品缺陷**（`eslint.config.js` 已把它们全部 ignore）。

## 7. 改动的最小性

- 一次只改本轮 Issue 范围内的东西，改动**自洽、可单独回滚**
- 不顺手优化范围外的代码（哪怕看着不顺眼）—— 记为待办项，下一轮再说
- 不为了"更优雅"而改变对外行为
