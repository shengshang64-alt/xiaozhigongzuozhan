# C 类方案 · 格式刷新补全「产出」能力（导出刷新后 docx + 模板真正应用）

> 提出轮次：R56（2026-09-25）· 状态：**等用户确认后动手** · 预估 1–2 轮
> 来源：用户实测反馈「格式刷新没有导出功能、没有应用之前的格式功能」（附截图）

## 做什么（两件事，一条管线）

1. **导出刷新后的 .docx**（核心缺口）
   第 3 步对比确认后新增「导出刷新后文档」按钮：纯前端用 fflate 解包用户上传的原始 docx → 按模板 FormatSpec **精确改写** `word/styles.xml`（正文/各级标题的字体、字号、加粗、行距、首行缩进）与 `word/document.xml` 的 `sectPr`（页边距）→ zipSync 打包下载。
   **文字零改动**——只动样式定义与节属性，与页面承诺「只统一排版样式，不改动任何文档文字」一致。
2. **模板真正「应用」**
   第 2 步选中的已存模板直接作为改写依据（现在只是对照展示）——即"应用之前的格式"。上传新文档 → 选老模板 → 一键得到套用老格式的成品。

## 为什么是它

- 用户实测指出的两大缺口；模块目前止步于"看对比"，无产出，售前拿到对比表仍要手工改 Word
- `formatSpec.ts` 头注释本就预留「② 第二阶段刷新任意 docx 时按原始值精确改写 styles.xml」——设计意图早有，实现没落地，属补完而非新发明

## 技术可行性（已核实）

- `fflate@0.8.3` 已在依赖（识别阶段就在用它解包），**不引新依赖，不触红线**
- 模板记录已存完整精确 `FormatSpec`（任意字体名/pt/twips 边距），改写不受导出枚举限制
- `formatSpec.ts` 已会读 sectPr/pgMar，改写是对称操作

## 对已有数据的影响

**零 schema 变更**（format_templates 现有字段够用，模板只读使用）；上传文件仍只在浏览器本地处理、不落库不上传（与现状一致）；不删除/修改任何业务数据。

## 边界（本轮不做）

PDF 导出、批量多文件、页眉页脚/目录改写、加密 docx 破解（给出明确报错）。

## 验证计划

单测（mini OOXML 断言）+ 往返一致性（导出文件重新上传识别，FormatSpec ≈ 模板值）+ 实机走查四步向导（用户截图同路径）+ R5 导出回归。
