## 三、缺陷 2：判据把 `miss` 当失败 → 对所有真实项目永久假阻断（R290，提交 `aabc45c`）

R288 把 `bid_outline_req`（投标文件目录要求）列为「关键项缺一即阻断」，判据是「status 非 ok」。

**逐字取证**：真实招标文件里根本没有「投标文件目录」这一专章，该要求是通过「投标文件格式」章表达的。

> 安庆二院原文 §11.1：「投标文件应该按照"投标文件格式"规定的内容和顺序进行编写」
> 全文「投标文件目录」**0 次**、「投标文件的组成」**0 次**、「投标文件包括」**0 次**

即：模型如实回答「原文未提及」（`status=miss`）是**正确且完整**的解析结果，不是失败。
R288 的判据等于把**所有真实项目**永久挡在生成之外。

修法：
- 新增 `isBlockingMissingStatus`：只有 `failed`（技术失败）与 `pending`（未产出）才阻断；`miss`/`ok` 不阻断；status 缺失（旧数据）不据其阻断，交由内容空判据兜底。
- `missingCriticalSections`：`status=miss` 时提前返回 `false`，**优先于**空态文本判据（第一版修复漏了这点，被测试当场抓住）。
- 与既有 `requiredParseFailures`（UI 红幅）判据对齐——那个函数本来就排除 miss，两处现同源。
- 测试：改写 3 个把 miss 锁死为「缺失」的旧断言（**原断言与取证结论冲突，属测试本身错误**），新增五态覆盖 + miss 优先级断言。

## 四、缺陷 3：大纲生成静默失败 —— 最危险的一个（R291，提交 `1e1a81c`）

在实测项目上点「AI 生成大纲」，装 `fetch` 钩子抓到完整调用链：

```
调用1  67774ms  status 200  body 3000+ 字符 →
  "Let me analyze the requirements carefully: 1. **商务部分 (biz)**: 6-10 skeleton chapters…
   Wait, the directory is: 一 投标函 …"
  —— 纯英文推理散文，通篇没有任何 JSON

调用2   1665ms  status 200  body 226 字节 →
  {"ok":true,"text":"{\"note\":\"原始输出为纯散文式分析文本，不含任何 JSON 结构，
   无法在不编造内容的前提下修复为合法 JSON\"}","usage":{"completion_tokens":28}}

最终：bid_outline=[] bid_chapters=[] 无 outline 快照 界面无任何报错，只显示「大纲为空」
```

**根因**：`withJsonRepair` 把「本地解析失败」一律当作「语法坏了」，于是把散文送去「只修语法不改内容」的修复器——散文里根本没有 JSON 可修，这一步在原理上必然失败，白花一次调用，还把真实原因掩盖成**空交付物**。

**为什么这是最危险的一类缺陷**：静默产出空结果 + 无报错。大纲是后续正文的唯一输入源，用户只会看到"大纲为空，点右上角「添加章」手动搭建"，以为系统正常。

修法：
- `withJsonRepair`：解析失败且 `extractJsonCandidate(raw)` 为空（判定「模型压根没给 JSON」，覆盖纯散文/推理过程/空回复）时，**跳过无意义的语法修复**，直接抛带根因与处置建议的中文错误。该函数是大纲/废标检查/事实清单/查重的**公共出口**，一处修复全线受益。
- 大纲空结果兜底文案改为「大纲生成结果为空，未产出任何章节…」，避免落进"正常使用中"的页面文案。
- 测试 `jsonRepairGuard.test.ts`（5 例）锁定判定契约，不锁活数据、不锁具体模型输出。
