## 本轮做了什么（人话）

标书正文里有一张"编制依据"表，格式是四列：`序号  名称  编号  类型`。里面有些依据**天生没有编号**——比如：

- 《建阳区边远山区乡镇卫生院灾后重建项目总医院设备及信息化建设初步设计与概算》——这是**这个项目自己的立项文件**，不是国家标准，没有编号；
- 《国家及行业现行有效的相关政策与标准》——这是一句**泛指**，也没有编号。

模型生成时，看到表头写了"编号"这一列，就**硬给这些行填了【待填写】**。于是正文长这样：

```
1  建阳区边远山区乡镇卫生院灾后重建项目总医院设备及信息化建设初步设计与概算  【待填写】  项目依据
3  电子病历基本数据集  国家卫健委现行有效版本  行业标准          ← 这条有编号，正常
```

评委读到"编号【待填写】"，**会当成"这一行没写完"**——观感和合规都是负面。实测建阳两个项目一共 **15 处**，全被交付门禁判为**致命**。

本轮的修复分三层：

| 层 | 改什么 | 解决什么 |
|---|---|---|
| **源头** | 生成规则句补一句：「清单中未给出编号的依据（如项目立项/初步设计文件、原则性政策表述），编号列填「／」，**禁止写【待填写】**」 | 以后新生成的正文不再出现这种占位 |
| **导出件** | 新增纯函数 `normalizeBasisPlaceholders`，导出前对**已有正文**就地规整（`【待填写】` → `／`） | 存量标书不用重新花钱生成，导出件一样干净 |
| **验收判据** | 交付门禁判定前先做**同一套规整**，并收窄归责匹配窗口 | 门禁的 BLOCKER 数字与"客户实际拿到的东西"对齐，不再虚高 |

## 为什么做这个（现象 + 对售前工作的实际影响）

**现象（真实库内原文，非构造）**：

```
编制依据如下（序号  名称  编号  类型）：1  建阳区边远山区乡镇卫生院灾后重建项目总医院设备及信息化建设
初步设计与概算  【待填写】  项目依据；2  数据互联互通平台建设包招标文件  [350703]FJXW[GK]2026009  采购文件；
3  电子病历基本数据集  国家卫健委现行有效版本  行业标准；4  国家及行业现行有效的相关政策与标准（含互联互通
测评、电子病历分级评价、网络安全等级保护、商用密码应用相关标准）  【待填写】  政策标准。
```

第 1、4 行的"编号"列都是 `【待填写】`，而第 2、3 行是正常的。

**对售前工作的实际影响**：
1. "编制依据"是标书的**门面页**（通常在总体建设方案/实施方案开头）。评委扫一眼看到一片 `【待填写】`，第一印象是"这份标书没做完"。
2. 交付门禁把它判为**致命（BLOCKER）**——也就是说，**这份标书按判据是不能发的**。15 处致命卡在那里，谁也答不出"到底还差什么"。
3. 它还是**系统性问题**：不是某一章写错，而是**生成规则没定义"没有编号该怎么写"**，所以每个项目、每个章都会复发。

**根因定位过程（零成本，全部本地取证）**：
1. 交付门禁先归责：103 处致命里，有 **14 处**被标为"③ 系统可回取（招标原文/项目字段里已有该事实，系统却留空）"。
2. 直接从 sqlite 只读打开 `pb_data/data.db`，把建阳两个项目的正文原样取出来（`bid_projects.bid_chapters`）——看到真实的表格行。
3. 逐条比对发现：**"名称"列其实是填对的**，空的是"编号"列；而这些依据本来就没有编号。
4. 回到代码：`bidTypes.ts` 的 `basisStyleRule()` 生成规则句时，**只说了"列为序号、名称、编号、类型"，没说"没有编号怎么办"**。模型面对空列只能自己发挥 → 填 `【待填写】`。
5. **结论**：不是"系统漏填事实"，而是**规则空缺导致的占位污染**。这也解释了为什么门禁的"系统可回取"归责会误报——它按关键词匹配，把"依据表行"当成了"该回取的事实"。

1. 占位符后紧跟"短词 + 依据类后缀"的类型词，且以条目分隔符/句末/行尾收束（`；`、`。`、换行、或"空格+下一条序号"）；
2. 占位符之前有名称文本；
3. 名称文本**不含标准编号特征**（`GB/T 22239` 这类）——**含则属真漏填，保留占位暴露问题，绝不掩盖**。

## 没做到的部分（不粉饰）

1. **端到端导出是在 vitest(node) 环境跑的，不是浏览器真机点击**。原因：前端 `/bid-workspace` 需要**登录**，而我没有可用的业务账号密码（`users` 表里只有 bcrypt 哈希，不可逆；`AGENTS.md` 未记录明文凭据）。替代验证 = 直接调用**同一个导出函数**（`exportBidDocx`）、生成**同一份真实 .docx 字节**、解包核对内容。**差异**：未覆盖"浏览器下载动作本身"（`triggerBlobDownload`）——该函数在轮次内被 mock 拦截。
2. **门禁 BLOCKER 从 103 降到 88，其中既有"真修"也有"判据修正"**，必须分开看：
   - **真修**（规整生效 + 判据与导出物对齐）：约 12 处；
   - **判据修正**（`system-refetch` 匹配窗口 30→10 字）：3 处。这 3 条经人工核对确认是**误报**——"提交采购人确认，…考核依据【待填写】"、"采购人可选择…费用为【待填写】元/年"、"采购人报备并完成工作交接，交接期不少于【待填写】个工作日"，全是**商务/材料项**被"采购人"这个自然语句高频词跨句误命中。收窗后"采购人为【待填写】"这类字段式短语仍能命中，未损真阳性。
3. **库内原文未改**：界面/数据库里仍是 `【待填写】`，只有导出件被规整。这是刻意设计（见上"你怎么自己验证"第 2 条）。若您希望**库内也一并规整**，需要单独授权（属改业务数据）。
4. **只修了"编制依据表"这一类**。同类"表格空列被填占位"的模式，在**其他表格**（如参数响应表、材料清单表）里可能有类似形态，本轮**未普查**。
5. **未重新生成任何章节**（零 AI 费用）。修复效果在**存量正文的导出件**上验证，未验证"新规则下模型是否真的不再写【待填写】"——这需要真实调用模型生成一章才能确认。
